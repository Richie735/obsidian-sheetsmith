# Sheetsmith - Spec

Feature specification. Describes what the plugin does, not how it is built.

## 1. Purpose

**Sheetsmith** is an Obsidian plugin for designing and using TTRPG character sheets, tied to no game system.

The user designs a sheet by placing components on a grid and defining the formulas that connect them, then saves it as a named layout. A character is an ordinary markdown note that names a layout and holds only values. One layout serves many characters.

The plugin knows arithmetic and nothing about any game. Every rule specific to a system lives in the layout the user builds.

## 2. Core concepts

**Layout.** A reusable sheet design: which components appear, where they sit, their configuration and formulas, its own function library, and its reset triggers. Stored as a file in the vault, so it syncs, versions, and can be shared. Examples: "DnD 5e Standard", "DnD 5e Caster", "Pathfinder 2e", "Call of Cthulhu".

**Character.** A normal `.md` note naming a layout in frontmatter. Holds values only, never structure.

**Component.** A placeable block on a layout. Deliberately generic in *capability* (Card set, Pool) rather than system-specific (AbilityScore, SpellSlots): what a component can do is never tied to one game's rules, and every rule lives in the layout.

A component's *name* is a separate matter, settled per component, and the rule is that a component is named for **what it is on the page**: Card, Pool, Track, Table, Group, Image. Not one of them is named for a job in a game, which is the same discipline as being generic in capability, applied to the label rather than the behaviour.

**Table** was called "Skill card" until open rows shipped, and the correction is worth recording because it is the second time the catalog has made it. The block is generic — named rows, typed columns, per-row formula scope — and §4.2 has it covering inventory, attacks, spells, and features as readily as skills. A name taken from one of those five jobs made the other four unfindable: nobody building an inventory looks for a skill card. The card pair made the same move twice: "Abilities" became "Stat group" (§12), and "Stat" and "Stat group" became **Card** and **Card set** once a coin purse and a denomination were as much of the job as an ability score (§13). What a shape name does not carry — that the columns are typed, that rows hold their own expressions — is what a component's config descriptions are for, exactly as "Pool" says nothing about its buffer.

**Formula.** An expression on any numeric field, referencing other fields and layout-defined functions.

**Reset trigger.** A layout-defined named event (Long Rest, Downtime) that restores bound components in one click.

The terms below were coined as the catalog grew and are collected here so one page defines them. Where a term has a wrong twin already in use, the twin is named so it stops spreading.

**Card.** The presentation a value wears — label, value, an optional derived number over it, an optional note line under it — and the DOM in `src/components/card-face.ts`. It is a component name as well, and deliberately: a **Card** is the component that is nothing but one card, a **Card set** is a strip of them under one heading, and Pool borrows the look without being either (§4.2). The word names one shape, which is what §2 asks a component to be named for, so it is the right name for the component that is that shape and the wrong name for anything else. *Avoid* stretching it past the card itself: what a sheet author calls an inventory card is a Table, and a region holding other components is a Container.

**Row.** One record in a Table, identified by its position in the note's table rather than by the text of its first cell.

**Container.** A component that holds other components instead of a value: Group, and Tab set (§4.2). It stores nothing, publishes nothing, resets nothing, and adds no segment to the names its children publish, so containment is arrangement and never addressing. Its children sit on the container's own grid, which is the container's width in columns by its height in rows. A container may hold containers one level deep and no further (§13). *Avoid* calling one a card: a card is one value's presentation, and a container is what a component sits inside.

**Leaf.** Any component that is not a container. Every component built so far is one.

**Tab.** One child of a Tab set, shown by pressing its name in the strip. A tab is a container itself where it holds a region, and a leaf where it holds a single card; either way the tab's name is that child's own `label`, and it has no placement of its own because it fills the panel (§4.2). *Avoid* "tab order" for the order of a Tab set's tabs: that phrase means keyboard focus order throughout this document.

**Declared row.** A row the layout defines, so every character has it. Its name is stable and knowable when a formula is written, which is what lets a formula reference it (§4.2).

**Open row.** A row the character adds, enabled by `openRows`. It publishes nothing, because a name a formula can write has to be knowable when the formula is written. What an open list publishes instead is a column total.

**Column type.** The kind of a Table column: `text`, `number`, `level`, `toggle`, `computed`, `target`. `computed` is read-only, `target` holds a name rather than a value, and the rest hold character data.

**Total.** A sum over a stored column, published as a name the rest of the sheet can read. Taken over `number`, `level` and `toggle`, refused on `computed`, which stores nothing to sum.

**Published row.** A declared Table row carrying a `key`, whose cell in the card's published column answers to `<id>.<key>`. The column says which value on a row is worth publishing; the row carries the name. A row the character added never publishes.

**Publish.** What a component offers to other components' formulas through `scopeValues` (§4.1): a `self` value under the bare component id, and `named` entries under `<id>.<name>`. Rendering a value and publishing it are separate: a component may show a number no formula can reach.

**Modifier.** A change one row of a Table declares against a value published elsewhere on the sheet. The direction is push — the row names the value, and the value names no source however many rows push at it — which is what stops an armour class having to be edited every time the character buys a seventh thing that touches it. *Avoid* calling the amount a bonus: a modifier may be a penalty, and "bonus" is already the word for a **bonus type**.

**Modifier cell.** Where a row says what it changes: **one** cell, in a column of type `modifier`, holding `;`-separated **parts**. Each part is either the name of a **modifier definition** or a **typed modifier** written on the row itself, and one cell may hold both. A blank cell enrols in nothing and is the ordinary state of most rows. *Avoid* "modifier column" for the amount, which is what it meant before the cell held the whole modifier.

**Modifier definition.** A modifier the layout declares once, under `modifiers`, and any row on any character may enrol in by naming it: a `name`, a `target`, an operator, an amount, an optional bonus type and an optional condition. **Editing one moves every character on the layout**, which is the point of the tier and also its exposure — nothing is cached, so a note holds the name and never a copy of what it says (§10).

**Typed modifier.** A modifier written into a row's own cell rather than named — `<target> += <amount> [as <type>] [when <cond>]`, or `=` for an override. It belongs to that row, refers to nothing, and is what a one-off is: an item that is *almost* the Ring of Protection. A typed part may be **promoted** into a definition from the sheet (§7), and a named part may be detached back into a typed one, which copies the definition's fields onto the row and is thereafter owned by it.

**Target.** The published name a modifier points at, spelled as a formula would — `armour_class`, `abilities.DEX`. It is the definition's `target`, or the name to the left of a typed part's `+=` or `=`. A name reference and never an expression: it never reaches the parser and is compared byte for byte against what the sheet publishes (§4.2). *Avoid* using it for the row, which is the modifier.

**Modifier slot.** The one number pushed at a target, published by the sheet under a reserved `mod.` namespace: `mod.armour_class`, and `mod.self` inside the formula that becomes that name (§5). A slot is a name in the sheet-wide table like any other, and is not a component's to publish — `mod` is a reserved component id for that reason. **A target only takes a modifier because its own formula reads its slot**, which is the whole of what makes the engine pull while the authoring is push.

**Bonus type.** A named category a modifier declares its amount to be — item, status, circumstance — from a list the layout owns under `modifierTypes`. Two modifiers of one type do not add: the best bonus and the worst penalty of a type apply, and types add (§5). It is carried by the definition, or by a typed part's `as` clause — **so a note may name one**, which the column model made impossible and §10 now carries a rule for. *Avoid* "modifier type", which was this field's first heading and read as a second word for the same thing.

**Breakdown.** What a modified number is made of, one line per contributor, including the ones the stacking rule suppressed and why. Reached by a press on the number itself (§4.2), which is the feature's answer to "why is this 17" and the thing nothing in the comparable prior art puts at the number.

**Scope.** The names a formula may reference from where it sits: the sheet-wide name table (§5), plus, inside a Table row, that row's own values.

**Run.** One sequence of targets on a Track, filled in order.

**Row set.** Several runs on one Track, through `rows`, rather than a second component. *Avoid*: set of runs, multi-run.

**Slot.** One target within a run.

**Flag.** A Track card every run of which is one segment of one mark, so each run has two states and stores `yes` or `no` rather than a count. This is what Toggle folded into (§13). Declared rather than resolved: the length has to be a literal for the card to be one. *Avoid* using it for a `toggle` column's cell, which is a flag in the ordinary sense and not this card.

**Level.** A named step below the stored unit, used as both a Track granularity and a column type. A colon in a level name says what its ring shows.

**Option.** One choice a Card offers: a `value`, which is what the note stores and what a formula reads, and an optional `label`, which is what the card shows. Declaring any is what makes a card a dropdown, so there is no setting saying which control it wears (§13). Unordered and ungraded, which is the whole of what separates it from a **Level**: a level's position *is* its arithmetic, so it stores an index, and an option's position is display order, so storing one would move every note whenever the list was reordered. *Avoid* calling the pair a key and a name: a Card's `key` already names its entry in the fenced block, and one word meaning two things on one component is the defect the card pair's rename was taken to fix (§13).

**Reset layer.** The shared path a reset trigger runs through: every bound component restored in one batched write, undone in one step.

**Catalog.** The component types a layout may name, which is what the registry holds and `listComponentTypes()` returns.

**Palette entry.** How the layout editor offers a component to the author. One type may appear as several entries with configuration prefilled, such as Table offered as "Inventory" with `openRows` on and Item, Qty and Weight columns ready, which needs no new type (§13). An entry carries a name, a description and a partial config, and is declared on the component itself (§4.1, §4.2). A layout stores the component an entry produced and never the entry, so an entry is a starting point the author edits and nothing a file ever names.

**Tracker.** A counter belonging to a scene or a party rather than to a character, such as a Blades clock or a doom pool. Whether one has a home here is open (§13). *Avoid* using it for a Track, which is a component on one character's sheet.

## 3. File model

### 3.1 Character note

````markdown
---
sheet-layout: DnD 5e Caster
---

## Abilities
```sheet
STR: 8
DEX: 16
WIS: 12
```

## HP
```sheet
current: 22
temp: 0
```

## Inventory

| Item | Qty | Weight | Equipped |
|---|---|---|---|
| [[Bag of Holding]] | 1 | 15 | yes |
| [[Sunblade]] | 1 | 3 | yes |

## Backstory

Grew up in [[Neverwinter]] under [[Sildar Hallwinter]].
````

Rules:

- **Frontmatter holds one key by default**, `sheet-layout`. Character data does not go in frontmatter, so it never pollutes the vault's property namespace or appears in autocomplete on unrelated notes.
- **Each component gets its own `##` section** in the body. Adding a component adds a section. The format stays uniform and expandable.
- **Format follows the component.** Components holding only numbers and flags store their data in a fenced block, which gives unambiguous boundaries and real types. Components that can hold wikilinks store their data as plain markdown, because Obsidian does not index links inside code blocks. **The rule reaches a component whose whole value is one line, not only a table**: Image stores one embed and Rich text stores free prose, and in both the section body *is* the value with no wrapper at all — which is what makes Constraint 3 hold by construction rather than by canonicalisation, since there is no canonical form to normalise free text towards. `parse/markdown-body.ts` is that half, shared by the two: the body's own leading and trailing whitespace is the note's spelling and survives a write, and only what sits between it changes. It also fixes the one piece of reserved syntax such a component has, which is `## ` at the start of a line — §3.1 gives a note one `##` section per component, so a body holding one splits the note there. Not escaped, since that would put a plugin's syntax into a file the user owns, and `read` is not failed, since every other body is legal: the **write** is declined instead, naming the line and the fix, so the split never happens. `parse/character.ts` exports `startsSection` so a component can ask, rather than holding a second copy of the pattern. A note that arrives already split — hand-edited, or written before this — is still read under §10, with the remainder an unmapped section and nothing lost.
- **The note stays readable and hand-editable** as ordinary markdown.
- **Single-value components store their value under the key `value`** in their fenced block, so hand-editing any of them looks the same.

### 3.2 Layout file

Stored in a configurable vault folder, `Sheetsmith layouts` by default. Contains the component list with grid positions and sizes, per-component configuration, the function library, reset trigger definitions, and the promoted field list. Contains no per-character data.

Layouts export and import as single files, so a layout can be shared or published.

## 4. Components

### 4.1 Shared contract

Every component carries the same core properties, whatever its type. Settling this before building the first component is what stops the tenth from forcing a rewrite of the first.

| Property | Set in | Purpose |
|---|---|---|
| `id` | Layout | Stable identity that survives label renames. What formulas reference. |
| `type` | Layout | Which component this is. |
| `label` | Layout | Display name, and the section heading in the note body. |
| `position` | Layout | Grid column, row, width, height. |
| `storage` | Fixed by type | `fenced`, `markdown`, or `none`. A property of the component type, never a user choice. `none` is a container: it has no section, so nothing reads it and nothing writes it. |
| `children` | Layout, optional | The components this one contains, each with its own position on this component's grid (§4.2, §8). Shared config the plugin itself reads, like `position` and `reset`, because the parser checks every child's own shared properties and the sheet has to flatten the tree before its name table can be complete. A container inside a container may hold only leaves, and a third level refuses the layout. A component never declares it in `configFields`; the editor owns it. |
| `reset` | Layout, optional | Which named triggers this component responds to, and what each one does to it (§6). A list, because the triggers a system declares overlap. Only for components that hold state. |

Every component implements five things and nothing more:

- **`read`**. Parse its section of the note body into data.
- **`write`**. Serialise data back into a section, byte-identical when nothing changed.
- **`render`**. Display itself, given its data, the resolved values from the formula engine, a resolver for evaluating formula fields against internal scopes (one ability, a table row), a callback for reporting user edits, and — where its text may hold a note reference — a way to resolve, open and preview one. The sheet view owns writing reported edits back to the note, and owns the vault: a component draws a wikilink from the text alone and asks the context whether the note exists, where to go, and what to preview, so it still imports nothing from Obsidian. Components never touch the file.
- **`formulaFields`**. Declare which of its config fields accept an expression rather than a literal. Usually a config key. A component whose structure repeats declares a path with `*` standing for one segment (`columns.*.formula`), because its expressions live one per column or one per row and a flat list could not name them.
- **`configFields`**. Declare its component-specific config fields (key, input kind, label, a description of what the setting does to the note, optional group for subheadings, optional visibility condition on another field's value) so the layout editor can render a configuration form without knowing the component's type. Shared fields such as label and position are the editor's own business. The description is required rather than optional: it is the only explanation of the setting the layout author is given, and the registry contract fails a field without one.

Beyond those five are the optional members, and they exist under a rule rather than to a count. **A member is optional only where the alternative is code outside the component knowing that component's data shape.** Counting them invites the next one; the rule is what refuses it. Every one below passes it: the sheet-wide name table cannot publish a value it has no way to read, a reset button cannot write "restore to full" into a shape it does not know, and the layout editor cannot work out on its own which half of containment a component reaches for. Most candidates will not.

- **`scopeValues`**. Publish this component's values to the sheet-wide name table (§5): a `self` value referenced by the bare component id, and `named` entries referenced as `<id>.<name>`. Each entry says what the note stores, reachable as `<name>.value`, and what the bare name is worth where the card shows something else. That second half is one of two things, never both. A **`display`** names one of the component's own `formulaFields` and the internal scope to run it in. A **`compute`** is a function the component supplies, handed a resolver bound to the finished sheet, for a value nothing declarative could state: a Track's filled segments are `floor(marks / marks-per-segment)`, which is arithmetic over a config field no formula on the sheet can see, and a published Table row's cell is a column formula evaluated in a row scope only that component can build. Both are evaluated lazily, since either may reference another component, and both publish nothing where they fail rather than falling back to the stored value. A component holding nothing a formula could reference, such as a heading, an image, or a block of prose, leaves the member off, and nothing else learns it exists.

  **A component that could publish through `display` must not use `compute`.** A `display` names a field, so a reader of the layout can follow the edge from one component to the next and §5's save-time cycle check has an edge to see. A `compute` is the component's own code, which that check can never see through, and that opacity is the price of it. An entry declaring both is refused by the contract test rather than resolved in some order: one name saying two things has no right answer.
- **`scopeRows`**. Publish the rows an aggregate walks (§5), so a formula elsewhere can write `sum(inventory, Qty * Weight)` over the rows a character added. Named for its sibling: `scopeValues` publishes this component's *names*, and this publishes the rows that have none — each row is what to call it, for wherever an error has to name one, and the names it holds, with a name that would not resolve absent rather than zero. A factory over a resolver bound to the finished sheet, for the same reason `compute` is one: a row may hold a computed column, which is a formula reading the rest of the sheet. It passes the rule squarely, and that is the whole of the argument for it: the alternative is the formula engine knowing that a Table has columns and rows, that a cell is text mapping to a number by column type, that a blank number cell is zero, that declared rows come first and the character's follow in note order, and that a row carries named expressions layered over its cells. That is the entirety of one component's data shape. A component with no rows leaves the member off and an aggregate naming it says it holds no rows, which is a different answer from naming nothing on the sheet at all — and it says so in one sentence that also covers the two cases where the component *is* a list and is refusing to answer, a configuration it will not accept and a section that would not read, because nothing at the sheet level can tell those three apart and "your inventory is empty" would send the author looking in the wrong place.
- **`scopeModifiers`**. Declare the modifiers this component pushes at names that are not its own (§5), so a row of a Table can change an armour class the Table has never heard of. The third reading of the same job, which is why it sits beside `scopeRows`: `scopeValues` publishes this component's names, `scopeRows` the rows that have none, and this the changes it declares against somebody else's. **A factory over a resolver, and nothing more.** Each push carries **one part of one cell as the cell spells it** — raw bytes, a definition's name or an assignment — plus the component's own label, the row's label as a reader sees it, and the names the row's expressions may read. It carries no target, no bonus type, no amount and no reason, and that is the load-bearing part: **`scopeModifiers` cannot know what a modifier is.** The component splits a cell on `;` and pushes each part; deciding which tier a part is, resolving it, and saying why a slot was refused all happen on the formula side, where the layout's definitions are. It passes the rule squarely — the alternative is the formula engine knowing that a Table has a modifier column, that a blank cell enrols in nothing, and that a row's names are its stored cells under its declared values under its computed columns. `scopeRows` cannot be reused for it, because `RowValues` carries cells by column key with no way to say which of them names a definition. A component that pushes nothing leaves the member off, and nothing else learns it exists.
- **`hasBuffer`**. Declare that this component holds a secondary buffer a trigger may clear on its own, so the editor can offer `buffer: 'clear'` on a binding. Declared rather than inferred for exactly the reason the rule above gives: the alternative is the layout editor knowing that a Pool has temporary points and a Track does not.
- **`showsOneChild`**. Declare that this container shows one child at a time rather than all of them together, so **a child of it has no placement**: it fills the region the container gives it, and the container's own `width × height` is the box (§4.2). `hasBuffer`'s argument exactly, one level up — the alternative is the layout editor knowing that a Tab set shows one tab and a Group shows every child, which is the one thing it cannot work out, since both hold `children`, both take the same context, and which half of containment a component reaches for is invisible from outside it. What it decides is a grid schematic against an ordered list, and whether a child's four position numbers are offered at all. Absent is the common case, a container that places its children; only the exception declares it, and a component holding no children may not, since a flag with no reading is worse than none.
- **`applyReset`**. Apply a reset trigger to this component's data (§6), given the binding and the same resolve-and-explain pair `render` gets. It takes the binding rather than a finished value because only the component knows what `full` means for it: a Pool's max, a Track's count, a flag's yes. Resolving that is a formula that can fail, which is why it reports an outcome rather than returning data. A caller that knew would be holding exactly the per-type knowledge the contract exists to keep out of it. A component without it holds no state, is offered no reset binding in the editor, and stays untouched when a trigger fires.

- **`palette`**. Offer this component in the layout editor with its configuration already filled in for a job (§4.2, §7). Each entry carries a name — which is also the label the new component starts with — a description, and a partial config that may not touch the keys the editor owns. It passes the rule for the reason §13 gives when it settles the mechanism: the alternative is a table in the editor holding Table's column shape and Track's count, which is code outside a component knowing what that component is. A component with nothing worth prefilling leaves it off and is offered as its bare type, which is what every component did before the member existed.

- **`configName`**. Say what one *configuration* of this component is called, where the type's own name is not the honest answer, so the editor shows that instead of the type. A Card with options is a Dropdown, and an author who chose Dropdown out of the add menu should not be told a line later that they have a Card. Derived from the config on every read and never stored, which is the same rule a palette entry follows (§13): the layout keeps the component an entry produced and not the entry, so the only honest source for the name is what the configuration now says — clear the last option and it is a Card again. Optional, and here for the reason `palette` is optional: the alternative is the editor asking whether a config has options, which is code outside a component knowing what that component is.

Adding a component means implementing those five, and an optional member only where that rule says it must. Nothing else in the system needs to know the component exists.

### 4.2 Catalog

For each component: what the layout configures, what the character note stores, what it does in sheet view, which config fields accept formulas, and — where it has any — the palette entries it is offered as (§4.1, §7).

**What earns a palette entry.** §13 settled the mechanism and said outright there was no rule for which jobs deserve one, and named the cost of not having one: the palette is where system flavour collects, a wrong entry is cheap, and many entries are not, because a menu nobody can read is worse than the type list it replaced. So the rule, applied to every entry from here on:

> **An entry earns its place where a job an author would go looking for is one component's configuration away, and the name of the component that does it would not lead them to it.**

Two things an entry must satisfy besides, both of which the registry contract fails a component for rather than leaving to review. **Every key an entry prefills is a config field that component also renders**, because an entry is a starting point the author edits and a prefilled key with no field is configuration they can neither see nor undo. And **no two entries on one type share a name**, since those are two identical lines in the menu differing only in something nobody sees. Names are not unique across the palette on purpose: the menu is grouped by type with each entry under its own, so one job's name may appear under two types where two blocks genuinely offer it.

Both halves of the rule do work. The first is §13's own check — the generic block has to cover the job rather than nearly cover it, and a job needing two components has nothing for one entry to be. The second is why an entry exists at all, and it is §2's argument for renaming Skill card turned into an entrance test: an entry makes a findable job findable, and is not a way to save an author typing. Configuration they would have found anyway is a worse menu line for no gain. Checkbox passes both: `count: 1` is one field, and nobody wanting a checkbox looks for a component called Track — which is the whole of why Toggle looked like it needed to exist.

**Card**. One named value on a single card, with an optional derived display and a free-text note line. Covers armour class, initiative, speed, passive perception: the standalone numbers a sheet is littered with.

- *Config:* `label`, `key` (entry name for the value in the note; defaults to `value`), `options[]` (each a `value` plus an optional `label`; any at all make the card a dropdown), `derived` (formula reading the stored value as `value`), `notePlaceholder`, `hideLabel`, `hideValue` (meaningful only with a `derived`), `hideNote`, `signed`
- *Data:* `fenced`, the value under `key` and the note line under `note`
- *Sheet view:* the label sits above the value, the note line below it, on the shared card rules below. The note is prose rather than a number, so it is the one field the arrow keys do not step. The card fills the cell it was placed in, on the shared rule below that a component occupies the columns the layout gave it: a two-column Card is two columns of card. It used to cap itself at tile width and centre in the remainder, so a wide component did not become an expanse of clickable card around a two-digit number. That is a placement the author chose, though, and a one-column placement is how to ask for a tile. Vertically it holds the top edge and pins the note to the bottom, so cards sharing a grid row line their labels up with each other and their notes with each other, even when one of them carries a pill the others do not. Where the layout declared options the value is a dropdown over them rather than a field: it has no draft, so it writes on the change and takes none of the card's Enter, Escape or arrow rules, exactly as a `level` column's dropdown already does. A press anywhere on such a card opens the menu, where the same press on a field puts a caret in it — a menu's own box is only as wide as the chosen option, so the card is the hit target or most of it answers nothing
- *Formula fields:* `derived`
- *Palette:* **Dropdown**, two placeholder options

**The key is storage, and only storage.** It names the value's entry, so the file reads `AC: 15` while the card reads "Armour class 15". It is not what formulas reference. That is the component's `id` (§5), so a formula says `armour_class`, and neither the card nor the arithmetic has to know how the note happens to be spelled. Hiding the key from the card is the one thing that separates a Card from a one-entry Card set, where the key *is* the card's abbreviation. `note` is reserved as an entry key, and a key holding a colon cannot be stored. Either one shows a configuration error on that component alone rather than writing a block that will not parse. Entries under any other key are preserved on write, and renaming the key does not move the stored value. The old entry stays in the note under the old key, as with a Card set entry.

**A card with options is a dropdown, and there is no setting that says so.** The editor calls it one, too: `configName` (§4.1) is what makes the add menu's **Dropdown** and the component list agree about what was just added, and it is derived rather than stored, so a card whose last option is cleared goes back to being called a Card. The control follows from whether the layout declared any choices, the way a Track's storage follows from its run being one segment (§13): a card with no options is a field, a card with options is a `<select>` over them, and neither an `input: 'text'` beside a declared list nor an `input: 'select'` beside an empty one has a reading. This is what withdrew the Field entry that used to sit below Card set (§13). Text against number needs no setting either, and never did: a card's arrow keys already step a value that is a number and move the caret in a value that is not, so the kind is a property of what is stored rather than of what is configured.

**An option stores its `value` and shows its `label`, and only the value is ever a name.** That split is what four independent tools landed on — Custom System Builder's drop-down takes "one key and one Label per row" and says outright that "you can only reference the value of the key in formulas, it's not possible to do so with the Label"; Meta Bind writes `option(1, bad)` for a stored 1 displayed as "bad"; Roll20 stores an option's `value` attribute and never its text; Notion gives an option both an id and a name and refuses to rename the latter in place — and here it is what lets a dropdown reach the formula engine at all. The expression language has no string literals, deliberately (§13), so `race == Elf` reads `Elf` as a name and fails: a dropdown whose stored values are words publishes something no formula can compare, add to, or branch on. A layout that wants arithmetic from a choice writes the arithmetic into the value — `2` labelled "Expertise" — and `Training * prof` works on a card exactly as it works in a `level` column. The cost is the other half of the same fact: **a label is display and is unreachable from a formula**, so a sheet wanting to show "Expertise" somewhere else shows the card. `label` defaults to `value`, so a list of plain words is the ordinary case and the split is paid for only where it buys something.

**No option is a default, and an unset card stores nothing.** The dropdown's first line is the card's own `—`, which is not one of the options, and only choosing an option writes. That is the existing rule that an empty value shows `—` rather than a new one, and it closes the trap this control is best known for: a Roll20 sheet that gained a placeholder option at the top appeared to reset every character, because a select with nothing stored had always been showing its first option and players "leaved the select at that, not touching it and therefore not creating a corresponding attribute". Nothing was lost there, because nothing had ever been saved; the defect was that the list's order was acting as a default. Here it never is, which is also why the five edits an author can make to an options list are all safe: **renaming a label** changes every card and no note; **reordering the list** changes the menu and no note; **adding an option** changes nothing already stored; **renaming a value** and **removing an option** leave every note holding what it held, and the card then shows a value the list no longer offers.

**A stored value that is no longer among the options is rendered, not corrected**, which is the rule a Track's run already follows — a stored value outside the run is rendered rather than fixed — read on a card that has no run. The dropdown carries the stored value as one extra line at the end, showing it raw, with a `title` saying it is not one of the layout's choices; choosing anything else drops the line. Snapping to the first option or to blank would be a layout edit deleting character data, which Constraint 4 and §10 both refuse, and it is the one case in this control's prior art that no tool documents at all — so it is decided here rather than copied. A card with two options sharing a value, or an option with no value, is a configuration error on that card alone (§10): a `<select>` holding one value twice cannot say which was chosen. **The comparison is exact — case included, byte for byte — between two trimmed strings**, and the trim is on the layout's side only: the fenced block's own values arrive trimmed, so an option declaring surrounding space could never match one and could not survive writing its own choice, which would come back as a stray on the next render. It is what makes an exact match possible rather than an exception to it, and it is what the duplicate check compares, so two options differing only in trailing space share a value. A label is stored and shown exactly as authored, being display.

**Card set**. An ordered set of named entries rendered as a strip of cards. Covers the six D&D abilities, Call of Cthulhu characteristics; a single-entry set is a lone card. A currency block is this component with its denominations as entries, offered as a palette entry rather than a type of its own (§13).

- *Config:* `label`, `entries[]` (each a `key` plus optional full `name`, in display order), `derived` (one formula computed per entry, where `value` is that entry's value), `direction` (`horizontal` | `vertical`), `sizing` (`fill` | `fixed`; fixed sizes cards at one per grid unit of the component's width, floored at a minimum), `align` (`start` | `center` | `end`, shown and meaningful only with fixed sizing; legacy layouts that carried sizing inside `align` still read correctly), `hideLabel`, `labelAlign` (`auto` | `start` | `center` | `end`; `auto` is the default and follows the cards), `hideValue` (meaningful only with a `derived`), `signed`
- *Data:* `fenced`, one entry per declared key, as in the `## Abilities` example in §3.1
- *Sheet view:* the set's name renders above its cards unless `hideLabel`. At `auto`, its default, its position follows the cards' own alignment. A heading belongs over the thing it heads, and centred cards under a name pinned to the far left do not read as one block. Any other `labelAlign` pins it there, `start` included: the default needs a name of its own, or "follow the cards" and "hold the start edge" become the same unset key and one of them cannot be chosen. Each entry edits inline on the shared card rules below. This covers "DEX 16 (+3)" without the plugin knowing what a modifier is. `derived` may reference the entry's own `value`, anything the sheet publishes (§5), the standard helpers, and the layout's own functions
- *Formula fields:* `derived`

An entry in the note that the layout does not declare is preserved on write, never dropped. Renaming a declared key does not move its stored value: the old entry stays in the note under the old key, and migrating it is part of the §10 rename story.

**Card interaction, shared by Card and Card set.** Both render through one card, so both behave identically under the hand.

- **Feedback is continuous, persistence is discrete.** The derived display recomputes on every keystroke. The file is written only on commit: leaving the field, or pressing Enter.
- **Enter commits in place** and moves to the next field on the card if there is one. It does not drop focus out of the sheet: committing and abandoning your position in the document are different intentions.
- **Escape abandons the draft**, restores the stored value, and announces the restore. An undo nobody can perceive does not read as one.
- **Arrow keys step a numeric value** like typing: live display, committed on blur. Shift steps by ten, for the numbers that move in tens. An empty field steps from zero, because pressing up on a fresh card is the obvious first gesture and should not be a dead key. Text that is not a number keeps the arrows as caret movement.
- **An empty value shows `—` everywhere.** `?` is reserved for a value that is present but did not resolve, and it waits out a short delay before appearing: a draft on its way to being valid, `-` before `-1`, is not wrong yet, and must not be told it is.
- **A number something has been pushed at carries a mark, and the mark is one press from what it is made of.** A dotted underline under the derived, and a press opens the shared popover listing every contributor — the source, the bonus type, the amount signed, and for a contributor the stacking rule suppressed, the reason it was not applied. A shape rather than a colour, because the plugin has no colours of its own; the same text also reaches a reader with no pointer, through one builder so the two carriers cannot disagree. A Table's computed cell carries the same thing, folded into the popover that cell already opens for its formula rather than growing a control beside it. **What does not get one**: a column `total`, which has no formula of its own to read a slot with, and a Pool's `max`, which is not a published name — both go through a Card or a Computed component publishing `hp_max = base + mod.self`, and that indirection is a real cost (§13).
- **The whole card is the hit target**, and hovers and presses as one, so the generous target is visible rather than merely present. A click routes to the field nearest it. The padding under the note belongs to the note, not to the number at the top. Because the card is a hover target, a truncated label reveals itself on hover only when it is actually truncated. A tooltip repeating a label already fully legible is noise fired at every pass.

A single-entry Card set and a **Card** are not the same component, which is why both exist. The set shows its key, sizes cards against the grid, and holds one formula that runs per entry. The Card hides its key, fills its cell, and carries a note line. Reach for the set when the cards belong to one and share arithmetic, and for the Card when the number stands alone.

**Pool**. Current and max resource with adjust controls. Covers HP, spell slots, rage, ki, sanity.

- *Config:* `label`, `maxSource`, `max`, `hasTemp`, `hideFill`, `reset`
- *Buffer:* declares `hasBuffer`, so a reset binding may offer `buffer: 'clear'` without the layout editor knowing what temporary points are
- *Data:* `fenced`, `current`, optionally `temp`, and `max` where the character owns the ceiling
- *Sheet view:* increment, decrement, direct entry, a drag on the number itself, and an adjust control for spending or restoring an amount, so damage and healing are one action. The controls sit together in one row under the reading, `− ± +`, and the step buttons move the value by one, or by ten with shift, and repeat while held. A press steps what is on screen rather than what was last saved, so a typed draft is what moves
- *Formula fields:* `max`, `reset.to`

**A pool reads as a proportion, not as two numerals.** A hairline fill under the card carries current against max, because the question at the table is "am I in trouble", not "what integer am I on", and `12 / 54` makes the reader do the division. This is what a `level` column already does: its ring grades its fill so a column can be read as a shape. A pool has more need of it than a proficiency mark does, being the one component whose state is inherently a proportion. The bar clamps at both ends and the value does not. Whether a pool may run below zero or above its ceiling is a rule of the game, so the pool leaves the number free and changes only its colour, which makes the boundary a status rather than a fence.

`hideFill` leaves the bar off, and it is an opt-out rather than an opt-in because a proportion is what a pool usually is. The case for turning it off is the pool whose max is a limit rather than a quantity: a counter of uses spent, where filling up is the ordinary state and an emptying bar would read as damage. The numbers and the boundary colour stay either way, since the bar is the shape of the value rather than the value's status.

**An amount is a control, not a typing convention.** `Adjust` under the value opens a small field for a number and a direction, **Spend** or **Restore**, and applies it, because the amount is what a player has in hand at the table: nobody is holding the number 45. Spend is the default, so the common path is press, type, Enter, with the direction never touched. The amount may be arithmetic, so `2*3` spends six. A typed sign still wins and moves the direction to match it, which keeps the control from ever showing a direction its own outcome contradicts.

It goes through the same path a press does, so the buffer takes it first: no route to a number on this card walks past the buffer. And the card gains a line for the one sentence it could not say anywhere else, `−17 → 50 · temp 0`, previewed before it is applied. A spend the buffer covers whole leaves the big number exactly where it was, which the flash on the pill could only report after the fact. That line sits above the controls rather than inside the row, and stays open whether or not anything is pending. Beside the field it competed for width with a button either side of it, wrapped on a narrow card, and grew every card in the grid row with it.

**This was a typing convention first, and the reversal is the entry worth keeping.** `-17` in the value field read as a change rather than a value. It worked, and it cost nothing on the card, which is why it shipped that way. What it actually cost was that the field then held two incompatible kinds of thing with nothing to tell them apart, and three defects came out of that single ambiguity:

- Everything painted from the field read the amount as the value. Typing `-2` on a pool at 5 drained the fill bar to nothing and marked the number spent for as long as the draft sat there, then snapped back to 3. That is a warning state, the one thing styling here is reserved for, fired for a value nobody asked for.
- A caret landing left of the digits turned a spend into a set. Tapping the left half of `5` puts the caret at offset zero, so typing `-2` produced `-25` and committed **−20**; on a two-digit pool, `6-172` committed **−166**. Both went to the note with no confirmation anywhere.
- A press or a drag arriving before the commit took the amount as its origin. Typing `-2` then pressing plus twice committed 0 rather than 5, because the interpretation flipped at the moment the draft's own sign flipped.

None of the three is a bug in the convention's implementation. They are what a field holding both a value and an instruction costs. The control gives the value field back its invariant, that everything painted from it is true, and buys two things besides. There is no caret to land in the wrong place, because the field starts empty. And the direction being a button is what makes the gesture reachable at all on iOS, whose numeric keypad has no minus key: the amount is bare digits, so the one platform most likely to be at a table can now use it. The cost is a line on the card, and the hint text is three sentences shorter than it was, because two of them existed only to teach that a leading minus meant something other than a minus and then to teach the escape hatch for what a minus no longer did.

**The card divides into what the pool is and what changes it.** The reading takes a row of its own and every control sits in one row beneath it: `− ± +`, with the two directions either side of "by how much". The steppers used to flank the number, on the argument that adjacency is the plainest statement of what changes what. That lost to a grouping argument on every count that could actually be checked. The value now takes the card's full width and centre line, so a sheet of pools reads as a column of numbers rather than numbers interleaved with chrome. The steppers stop being cramped: flanking a four-character field inside a 220px card is why they needed a container query to shrink and an invisible expansion to stay reachable by a thumb. And the card is no taller, because the amount already had a row and the steppers moved into it.

The cost lands only on a pool with a buffer, where `−` now sits nearer the Temp pill than the number it decrements. The steppers do spend through the buffer, so the proximity is imprecise rather than wrong, and the pill's absorb flash is what teaches the rule in any case.

**`− ± +`, and every label on the row is a glyph.** The amount's trigger is `±` at the steppers' exact size, because the three are one set read at a glance and a word in the middle was the odd element. It is a text glyph rather than an icon, because the marks either side of it are text glyphs. `±` also says the right thing: an amount, either way, rather than naming an action the press does not take. What distinguishes it from its neighbours is what the press does rather than its shape at rest. The press replaces it in place with a field, which no stepper does, and that happens on the press, so there is never a moment where nothing appears to have happened.

The direction inside the panel is the sign it will apply, `−` or `+`, joined to the field so that `− 17` reads as minus seventeen and needs no decoding. It was an arrow first, to keep a third minus glyph off a row that already carried two steppers, the same collision the buffer pill refused steppers over. That objection died when the steppers began standing down while the panel is open: at the moment the glyph is read there is no other minus on the card, so the clearest mark is available, and the arrow turned out to be a way of dodging a conflict that no longer exists. The words stay in the accessible name and the tooltip, and a restore is still marked in the accent. The sign carries the direction on its own, and leaving the default unmarked is what makes the exception visible. A glyph that is the only explanation of a control is not a label, which is why every one of these is named twice.

The direction and the amount are drawn as one control rather than two, sharing a seam and a focus ring. They are two halves of one value, this much and that way, and as a square glyph button beside a separate field they read as two things that happened to land next to each other. The field is sized against the button it is joined to for the same reason: left at an input's own defaults it was half the height of its neighbour, which made the thing being typed into the quietest part of its own control.

The controls row and the fill bar travel together. The card's free space collects above the row rather than above the bar, so a pool in a tall cell stretches the gap under the reading and not the one between the controls and the bar. The bar is a picture of the value and the row is what changes it, and those two belong at the foot as a pair.

**Opening takes the row over, and that is a rule about layout under a finger.** The panel is wider than the `±` it replaces, and a centred row answers a growing middle child by pushing its neighbours outwards, roughly 38px each, on pointer-down, while the finger is still resting on the card. Layout must not move under a gesture in progress, least of all the two most-pressed buttons on the sheet, so the steppers stand down while an amount is being entered and the panel has the row to itself. Two other things fall out of it. The compound press that spent an amount and then stepped it again is unreachable, and the row stops carrying four directional marks that mean three different things.

The panel does not float. The card clips its own overflow so the radius can clip the fill bar, and that would clip a popover with it; taking the trigger's place in the row means nothing on the sheet moves either. The swap is motioned like everything else a finger touches here, where the throw coasts, the buffer flashes, the fill eases, and the step gives under the press. It scales about the centre it shares with the glyph it replaces, so the form grows out of the `±` rather than arriving from nowhere, and mirrors on the way out so an abandoned control retraces its path. `transition-behavior: allow-discrete` and `@starting-style` are what let a `display` swap animate at all, and both degrade to the hard cut this started as.

**Leaving abandons the amount, which is the one place this card breaks its own rule.** Every field on a sheet commits on the way out, and that rule is right for a field holding a value and wrong for a control issuing a command. A typed value can be re-read and retyped because it is still on screen; a throw can be caught mid-flight; a step is worth one point. A pending amount was the only gesture here where a stray tap elsewhere spent seventeen points with no notice and left nothing behind to say what had done it. So a mode dismisses where a field commits: Enter and the keyboard's own Done key are how to mean it, Escape abandons it from anywhere in the control rather than from the field alone, which left the escape hatch with a hole in it at the direction toggle, and anything else that takes focus away puts it back.

A commit re-renders the sheet, and focus returns to the `±`: the view captures the focused control by cell and index before rebuilding and restores it after (§7), and the panel's children stay in the DOM whether it is open or closed, so the trigger's index does not move. A run of amounts costs one press of `±` between them.

**The pending amount is drawn on the bar as well as written out.** `−17 → 45` is the outcome as a number. The bar is the card's answer to "am I in trouble", and having the number update before the shape did meant the two halves of one piece of feedback arrived at different times. While an amount is pending the solid bar is the smaller of where the pool is and where it would land, and a faint bar reaches the larger. A spend then reads as "this much stays, this much goes" and a restore as "this much you have, this much arrives", from one rule and one `landing()` call shared with the preview text.

**And it is spoken, not only drawn.** The written line is a shape on a screen and the bar is a picture, so §12's rule was being kept for the eye alone. That rule: where a control's input is not its outcome, the outcome has to be on screen before it is applied. A screen-reader user heard the direction and the amount, and then the result only after committing it, which is the same asymmetry the buffer flash was there to fix for the sighted reader. The pending outcome goes to the card's own live region once the amount stops changing, composed for speech rather than for the eye: `Spend 17, 5 from temporary, HP 50, 0 temporary`, where the line reads `−17 → 50 · temp 0`. It is debounced, or it narrates every digit on the way in, and cancelled whenever the amount clears, so a preview can never land on top of the announcement of a commit that has already happened.

**The value field reads arithmetic on commit**, so `43-7` settles as `36`. The one thing a sheet with an expression parser in it should never do is ask the user to do the sum themselves, and a field that only accepted a settled number did exactly that. This is the rule that *can* live on a value field, and the contrast with the amount is the whole point: it is unambiguous by construction, differing from a plain number only when an operator follows one. So `-7` sets the pool to minus seven, `0-17` sets minus seventeen, and `62-17` sets 45 without touching the buffer. A set is a set. Text that is not arithmetic stays exactly as typed, and it is the same parser the formula engine uses, never an evaluated string.

**Large changes are a gesture, not a count.** A table deals damage in sevens, so a held step button repeats and accelerates, and the number can be dragged sideways to scrub it, tracking the pointer and, on a flick, carrying past where the finger stopped. Every one of those moves the draft alone. The note is written once when the gesture ends, which is the same rule the cards follow and is what keeps a two-second hold from writing the note twenty times. A press below the drag threshold still places a caret, so typing an exact value is untouched.

**A throw coasts, and can be caught.** The pool spends the projected distance over successive frames rather than applying it the instant the finger lifts. Landing it at once is a teleport, and the motion stops being continuous at exactly the moment it should be most so, with the fill bar easing to a value the number had already snapped to. Coasting also gives the gesture the only undo it can have, since a press anywhere on the card catches the throw where it has reached. Nothing is written until it settles. Under reduced motion the value arrives without the journey, which is the one case where skipping the animation costs nothing: the destination was never in question.

**A boundary resists.** Past zero, and past the ceiling, the pointer buys roughly a quarter as much per pixel. Zero is the most consequential value this component renders, and a flat mapping made crossing it cost the same as any other ten points. Resistance makes it a decision rather than a slip, and signals through the hand what the colour signals to the eye. It still does not clamp, so the boundary remains a status and not a fence.

A throw is bounded by a quarter of the pool's ceiling. The projection that suits a scrolling list is calibrated in pixels of content, and a pool is a short range read exactly rather than a long one skimmed: unbounded, a firm flick empties a character in one movement, and the gesture that covers ground fastest is also the one hardest to undo. The bound is what keeps it a shortcut rather than a hazard.

**The layout says where the max comes from: calculated, or the character's own.** `maxSource` picks between them and defaults to calculated, so every layout written before the choice existed reads exactly as it did.

*Calculated* is the original rule and the reason for it is unchanged: `max` is a formula field, the note never stores it, and a stored copy would be the stale derived value Table's storage rules refuse. Every character on that layout has the same expression, and changing it changes all of them at once.

*Character* is for the max that is rolled or assigned rather than derived, hit points being the obvious case. The pool stores a `max` entry beside `current` and renders it as a small field inside the reading, so `22 / 31` is typed where it is read.

**Storing that is not the thing the rule forbids.** What Table refuses is a copy of a value some formula also produces, because the two can disagree and nothing says which is right. A character-owned max is produced by nothing. It is an authored number, the same kind of thing as `current`, and there is no second answer for it to drift from. The modes are exclusive by construction: a calculated max is never written to a note, and a character's max is never computed from one. That is what keeps exactly one answer to "what is this character's maximum".

The old answer to a rolled max was to point the formula at a component holding it: `max_hp` on a Card, and the pool's max reads it. That still works and is still right where the number is wanted elsewhere on the sheet under a name of its own. What it costs is a second card for a number that belongs to this one, and a max shown twice on a sheet whose reading already says it. `hp.max` publishes the same either way (§5), so a formula asking a pool for its ceiling never learns which mode it is in.

A max the character owns is edited plainly. It settles arithmetic like any value field, so `31+7` is a roll added to a total, and the arrow keys step it without touching the buffer. Spending through temporary points is a rule about the pool, and a max is not the pool. The ceiling is read rather than captured, so the fill, the boundary colour and the throw's bound all follow a max being typed before it is committed, and the change is written in the same edit as the value it bounds. With no max stored yet the field shows `—` and the pool has no ceiling and no bar, which is also why the field renders when it is empty: it is the only thing on the card left to press. A `full` reset restores to the stored number, and where there is none it fails and says so. That is the same outcome a formula that will not resolve produces, for the same reason.

A note carrying a `max` entry is read in both modes and used only in one. A calculated pool neither renders nor writes it, so the entry survives untouched per §10, and a layout that later hands the max to the character finds the number already there.

**Temporary points are a buffer, and spending takes them first.** `hasTemp` adds a second value above the maximum. What makes it part of the pool rather than a number parked beside it is that every spending gesture drains it before touching the pool itself, crossing into the pool with whatever is left over. That covers the step down, the arrow key, and a drag alike. Without it the buffer would be a Card the layout could have placed for itself, which is the one thing a declared config field must not be.

Healing never refills it, and the pill has no steppers. A buffer is granted in lumps and replaced, not counted up to: nothing anywhere adds temporary points to temporary points, so typing over the value is the whole interaction. A second pair of step buttons would also put a minus on the card meaning something different from the minus above it. The pill drains its colour while it holds nothing, so its presence on the card carries information rather than sitting there all session saying zero.

**Which event clears the buffer is the layout's to say**, through `buffer: 'clear'` on a reset binding (§6). Every system that has such a buffer empties it on some event and they disagree about which: a long rest in 5e, the end of an encounter in 4e, the next score in Blades. The pool cannot infer that and the plugin must not assume it. Because clearing the buffer is independent of restoring the value, `action` is optional on a binding, so a 4e encounter can end, take the buffer, and leave hit points untouched. A binding must carry one or the other, since a binding that does nothing has no reading.

Per-instance durations are out of scope. A system where each grant of temporary points expires on its own clock is describing a value paired with a duration, and that belongs to whatever granted it rather than to the pool.

**Where the buffer ends and a second Pool begins.** `hasTemp` is the non-stacking, non-healable buffer granted in lumps and spent first. Anything with a maximum of its own, such as Starfinder's stamina or Genesys's strain, is a second Pool with its own `max` and its own reset rather than a flag on this one. That line is what stops the buffer growing into a component.

The fill bar ignores the buffer, and that follows rather than being a separate decision: the bar is the pool's proportion, and while only the buffer is draining the pool has not moved.

**A run of adjustments is one gesture, measured from where it began.** Every step is derived from the values the gesture started with plus its net movement, never applied on top of the last one, and that is what lets it be undone. Applied incrementally, a step down took a point off the buffer and a step up handed it to the pool, so a press and its reversal left the card in a third state that was neither. Derived from the origin, a net of nothing is exactly where you started. Three taps down and one up is one gesture, one write, and the up refunds the buffer the downs drained.

The run is written when it goes quiet, or sooner: leaving either field, releasing a drag, or typing a value all end it. Nothing is written from a card a rebuild has already replaced, since the values would be read out of detached fields.

**The buffer is floored at nothing, and the pool is not.** The argument for leaving the pool unclamped, that whether it may run past either end is the game's rule, does not reach the buffer, because the buffer is this component's own invention. No system has negative temporary points.

A spend that crosses from the buffer into the pool changes two values, and they are written as one change. Two writes for one press would be two saves and two rebuilds, with the second racing the first.

The pool publishes its current value under its bare id, its ceiling as `<id>.max`, and its temporary points as `<id>.temp` where the layout asks for them, so `hp.max / 2` needs no second copy of the expression.

**Track**. A run of segments filled in order. Covers exhaustion, stress, XP, uses per day, death saves, clocks — and, at one segment, the flags a Toggle used to cover: inspiration, equipped, trained.

- *Config:* `label`, `count`, `marks`, `sense`, `rows[]`, `levels[]`, `hideLabel`, `reset`
- *Data:* `fenced`, a single value under `value`, counted in marks, or one entry per row key where `rows` is set. A flag card stores `yes` or `no` instead of a count
- *Sheet view:* the run is one control. Press a segment to set the track there, press the mark the value stands on to clear it, drag across the run to set it in one gesture, arrows to step. The segments are the reading, so there are no numerals beside them. A card may hold several runs, one per row, each with its own length. A flag card draws one ring per run rather than a run of segments, and a press toggles it
- *Formula fields:* `count`, `reset.to`
- *Palette:* **Checkbox**, `count: 1`

**A Track is a run, and a Pool is a quantity.** Both hold a number under a ceiling, which is why §12 called this a simpler Pool, and the difference is what the number is for. A pool is read as a proportion, and the bar exists because `12 / 54` makes the reader do the division. A track is read as a count of discrete things that each mean something, and its segments are already the proportion *and* the count, which is why the card carries no numerals. This also settles the ceiling's name: a pool's is `max`, because a quantity has a maximum, and a track's is `count`, because a run has a length.

**The atom is the mark, not the segment.** `marks` is how many presses fill one segment, one by default, and the stored value counts marks rather than segments. An Ironsworn progress track is ten segments of four marks, and a system that grades progress by difficulty needs the sub-segment. Storing filled segments and a remainder would write one quantity as two numbers and invite them to disagree: `value: 22` cannot be inconsistent with itself where `segments: 5, marks: 2` can. At the default of one the note reads `value: 3`, which is what every track not needing this looks like.

**A card may hold a set of runs, and the set is Card set's shape.** Spell slots are five first-level, three second, one third: runs differing in nothing but their length and their name. That is what `rows` says, with a `key` for the note, an optional `name` for the card, and an optional `count` and `sense` of its own falling back to the component's. The component states what the set means and a row says where it differs, which is what lets death saves paint successes as progress and failures as harm on one card. The storage is Card set's, one fenced block with an entry per key, so a slot card reads as `L1: 2` and stays hand-editable. The alternative is three components in a Group, and it costs three headings for one control, three reset bindings kept in step by hand, and three writes where a rest should be one. A row set publishes per row (`slots.L1`) on §5's rule for a component holding several values; a row's own ceiling is a third level of name and is §13's question rather than a claim made here. `rows` and `levels` do not combine. Named steps are one run's meaning and rows are many runs' identities, and a layout wanting both is describing several ladders.

**Steps may be named, and `sense` says which end is the bad end.** `levels` names the states from none upwards using a `level` column's syntax, glyph after a colon included, and naming them settles how many there are, so `count` is only for a run whose steps are not worth naming. Named steps are what make a threshold track legible, since exhaustion, panic and corruption are ladders where the number is an index into a rule. `sense` is `progress` or `harm`, because the same run of segments fills toward an achievement in one system and a catastrophe in the next and no property of the data distinguishes them. It changes colour only, never whether a press lands.

The bare id publishes filled segments, `<id>.value` the stored marks, and `<id>.count` the ceiling, as `hp.max` is a Pool's. A `formula` reset resolves `to` in segments, taken down to the nearest mark. Track declares no buffer. **A stored value outside the run is rendered, not corrected.** `count` is a formula, so a run's length changes when the number behind it does, and a track that rewrote itself to the new ceiling would destroy a player's data on a level-up (§10).

**A run of one segment is a flag, and that is where Toggle went (§13).** A run whose one segment holds one mark has exactly two states, which is the whole of what a Toggle was — inspiration, equipped, trained — so it stores `yes` or `no`, draws the level ring rather than a segment, and publishes a boolean under its name and under `<name>.value` alike. An entry the note does not have publishes `false`: two states leave no room for a third, and the empty ring on screen says "no" rather than "unknown". `<id>.count` is still 1, because a numeric run publishes its ceiling and a layout lowering `count` to 1 must not take that name away from the formulas reading it; a checklist publishes none, exactly as a numeric row set does, since a set of runs has no one ceiling to name. `full` and `empty` are `yes` and `no`, which is exactly the case §6 names when it says the actions are named rather than numbered, and a flag resolves nothing to apply either. It gains what Toggle had no way to say: `levels` letters the ring, so a threshold flag reads as itself; `sense` says a flag is bad news, though a run of one is its own last segment and so has nothing left to grade; and `rows` makes a checklist of named flags under one heading, one reset binding and one write.

**Being a flag is declared, not resolved, and it is a property of the card.** A run is one segment where `levels` names two states, or where its `count` is a plain integer `1` — never where a `count` written as an expression happens to work out to 1, because the note would then change spelling whenever the number behind it did. And it is the *card* that is a flag or not: every run on it, so one fenced block never mixes `L1: 2` with `L3: yes`. A checklist is a card all of whose rows are one segment; a slot card whose third level holds one slot goes on storing counts. **Both spellings are read on a run of any length**, so a layout that raises a flag's count keeps every note it wrote: `yes` reads as one mark with the first segment filled, and a count on a flag card reads as ticked. Neither is corrected on read, per the rule above.

**Table** (`table`). Repeatable typed records, wikilink-aware. Covers skills and saving throws, and the same block covers inventory, attacks, spells, and features, whose rows the character adds. Openness is one boolean crossed with the rows the layout declares, so there is no second component (§13). An inventory and a features list are palette entries of this type, with their columns prefilled and `openRows` on, and they are not types either (§13). Named for what it is on the page rather than for the job it was built for, per §2; it was called "Skill card" until open rows made the general shape plain.

- *Config:* `label`, `rowHeader` (heading of the column holding row names; defaults to "Name"), `namePosition` (where that column is drawn among the others; 0, first, by default), `rows[]` (each a `label` plus optional `values`), `columns[]` (each a `key`, optional `name`, `type`, `hideHeading`, `total`, `publish`, `modifier`, `modifierType`, and the type's own fields), `openRows` (whether characters may add rows of their own), `hideLabel`
- *Data:* `markdown` table, one row per record, one column per stored column
- *Sheet view:* cells editable on the shared editing rules, computed cells read-only, hovering one reveals its formula, or, where it failed, the name it could not find, since that is the half a reader can act on. A `target` cell is a select over the values this layout takes a modifier for, carrying a stored name the list no longer offers as one extra last line. Where the character may add rows, an **Add row** control sits in the last row of the table and each of their rows carries a delete glyph; where a column is totalled, its sum sits under the table in a foot row labelled **Total**. A wikilink in any cell the card shows as prose renders as a link and behaves like one. A hover is the desktop half of that: a tap on a computed cell and a long press on a level both open the same text anchored to the cell, because a phone has no hover and a glyph with no route to its meaning is a dead end. The row name stays pinned while the table scrolls sideways, so a column of numbers never loses the row it belongs to. The `—` and `?` rule holds here as on a card: a computed column with no formula has nothing to compute and reads as empty, and `?` stays reserved for a formula that is present and did not resolve
- *Formula fields:* `columns.*.formula`, `rows.*.values.*`

The most important component, because it absorbs several system-specific concepts into one generic block. That is what the name does not say, and §2 records why. Each column is typed as `text` (with optional `secondary`), `number` (with optional `min` and `max`), `level`, `toggle`, `computed` (with a `formula` and optional `signed`), or `target` (holding the name of a value published elsewhere on the sheet). A computed column's formula may reference the row's own cells by column key, the row's own values by name, and anything else on the sheet by component id.

**A `level` column and a `toggle` are one control with a different number of states.** A one-level column already *was* an ordinary toggle by this section's own account, and the two now render identically: two adjacent columns doing the same job must not measure differently under the same finger, and a native checkbox had none of the ring's hit target, coarse-pointer sizing, or press feedback. `toggle` goes on storing yes and no, which is what reads well in a file for a flag.

**The rule reaches a card as well as a cell, and a one-segment Track is what it reached.** A Track whose run is one segment is the same two-state control on a card, so it draws through the same painter rather than a lookalike, and it stores the same `yes` and `no` a `toggle` cell stores — one spelling for a flag wherever a flag is kept, so a reader hand-editing a note meets one vocabulary. A flag *card* is the whole card, though, where a column is one cell: every run on it, so a fenced block never mixes a count with a flag. The ring's own gestures come across and the run's do not, because a run has positions between its ends and two states has none.

**A `level` column is one graded control, stored as the level it is on.** It exists because a graded proficiency is neither a number you type nor a set of boxes you tick: a spinner holding 0 to 2 asks the player to know that expertise is spelled "2", and a row of checkboxes offers the states nobody means, none ticked but the second one, or two of the wrong ones. One answer gets one control.

- **It reads as a toggle carrying the level's initial**: a filled circle holding "P" or "E", and an empty ring for none, which is what an unticked proficiency looks like on paper and needs no letter to say so. One glyph keeps the column as narrow as a checkbox would. The full name is a hover away on a pointer, a long press away on touch, and is what assistive tech is given.
- **The fill grades with the level**, mixed from the accent towards the page by how far up the column the cell is: the first grade a tint, the top one the full colour, and the ring at full accent throughout so even the faintest fill still reads as marked. A column of rings then has a shape, how trained this character is, read before any of the letters are. It costs nothing, since the glyph and the name were already carrying the exact answer. Short of the top the glyph reads against the page rather than the accent, because white on a tint is the one place the ramp could cost legibility. Under `prefers-contrast: more` every marked level goes back to the full fill: a shape read down the column is the wrong thing to trade contrast for.
- **`levels`** names the states from none upwards (`["Untrained", "Proficient", "Expertise"]`), and naming them settles how many there are, so `max` is only for a column whose levels are not worth naming, and those show their number as the glyph instead. A named level reads as itself to a screen reader rather than as the number behind it.
- **A level name may also say what its ring shows**, after a colon: `"Proficient:"` for a fill carrying no letter at all, `"Proficient:★"` for a mark of the layout's own. A mark is one character, which is all the circle holds and also what keeps the syntax from changing what an existing file means. `"Trained: the useful one"` is a name with a colon in it, and reads as one. An unnamed column's level count is held to 20 for the same reason a level column is a ring at all: past that it is a number to type rather than a control to cycle, and the editor draws a ring per level. Left alone it carries the initial of its name, which is what every existing layout says and so what it keeps saying. This is what covers 5e, with an empty ring, a plain fill for proficiency, and the fill carrying "E" for expertise, without the plugin knowing anything about 5e. The marker lives in the name because which levels are worth lettering is a per-level answer: a flag on the column could only offer the guesses someone thought of (all, none, the highest), and the layout is the thing that knows. The name is never optional. It is what a dropdown lists and what assistive tech is given, so a level with a mark and no name is a configuration error (§10). The layout editor draws every state of the column beside the field, painted by the same code the sheet uses. Each named level's ring is also the control for whether it carries a mark, because a colon typed into a text field is exact and unguessable while a ring that answers a press is neither. The two write the same string and the field updates as the rings are pressed, so the picture is never a second place the truth is kept. None is not a control, since an empty ring is what none is, and neither is a level with no name to keep a mark in. A mark of the author's own is remembered across the press that hides it: a toggle that loses what it was holding is a trap.
- **`input`** is `cycle` (the default) or `select`. Cycling wraps, so one control reaches every level and returns to none without a second gesture. The arrow keys step without wrapping, for the hand that would rather aim than count. A dropdown suits a column whose levels are many or whose names are worth reading before choosing.
- The stored value is an integer either way, so the arithmetic is unchanged: `Training * prof` covers untrained, proficient, and expertise in one expression, and the note still reads `| Perception | 2 | 0 |` and stays hand-editable.
- With one level it is an ordinary toggle storing 0 and 1, which is what a system with a single grade of training wants. `toggle` remains for the flags that read better in the file as yes and no.

**A row carries expressions of its own as well as a name.** A row's `values` are named expressions evaluated in that row's scope, and they are what let one column formula serve a whole list: the column says `ability + Training * prof + Bonus`, and each row says which ability it means (`ability: abilities.DEX`). Without them a skill list needs eighteen nearly identical formulas, one per row, and the layout stops being a description of the system and becomes a copy of it.

**A row is identified by its position in the note's table**, and that is one rule with several consequences. A markdown table is an ordered list of lines, and the first cell was never promised to be unique: keyed by name, two items called "Dagger" were one row, the second unreachable and then written over by the first's next edit. Position survives duplicates, case, and renaming, because it is not derived from anything the user types. It is safe to use precisely because nothing outside the component ever sees it — no formula can name a row (below), so the renumbering that broke Roll20's macros cannot arise, and an index is only ever held for the render it came from.

**One list holds the layout's rows and the character's, and the claim rule says which is which: a declared row claims the first note row spelling its name, scanning the table top to bottom, case-insensitively; every unclaimed note row belongs to the character.** `openRows` says whether the character may add any.

That one rule covers every case the catalog needs:

- **A skill list** declares every row, and the card behaves as it always did: the layout owns the rows and the character only fills in cells. Correct for skills and saving throws, where every character in the system has the same list and retyping it per character would be absurd.
- **An attack table** declares nothing, and every row is the character's — as for inventory, spells and features.
- **A Blades playbook's load list** declares the printed gear and leaves the blank lines for the gear the player invents, on one list rather than two components.
- **A layout adding a row the character already typed** is not a case at all: the declared row claims the row that is already there. Nothing duplicates, nothing is overwritten, the cells stay put. What changes is that the row's name goes read-only and its delete control disappears, which is visible and is not a loss.

Case-insensitive matching is safe here for the reason it is unsafe in tools that key rows by name: no formula names a row, so what a row's capitalisation can change is which declared row claims it, never what any arithmetic resolves to. The note keeps its own spelling either way, on write as on read. The claim is computed rather than stored, which is also why the card needs no per-row flags: "may not be renamed" and "may not be deleted" are both "claimed".

**A character-added row publishes nothing, and this is a fact about the contract rather than about the component: `<id>.<name>` is a fixed-row mechanism.** A name a formula can write has to be stable and has to be knowable when the formula is written; a name the character typed is neither. `inventory.Dagger` therefore fails as an unknown name, whatever its capitalisation, on the component that wrote it. That rule is untouched by §5's aggregate, which is what makes the aggregate possible: it names the *component*, which is knowable when the formula is written, and reaches the rows as a set whose cardinality the layout does not know. The rows stay anonymous.

**A column total is the one thing an open list can publish**, because an aggregate needs no row name. Any `number`, `level` or `toggle` column may set `total`, which sums the column under the table and publishes the sum as `<id>.<key>`, so an encumbrance rule is arithmetic the layout writes rather than code someone has to be able to write. The total is the sum of the column's own values — a number cell's number, a level cell's level, a toggle's 1 or 0 — which is the same mapping that feeds a cell to a formula, so "how many are equipped" and "what does this weigh" are one piece of arithmetic. It recomputes per keystroke, from the cell being typed rather than from the note, because feedback is continuous and persistence is discrete like everywhere else on a sheet; an unreadable draft keeps the last good total until it settles, on the same delay a computed cell waits out. A blank number cell is 0, by the rule below. Where a cell holds text in a column that wanted a number the total reads `?`, publishes nothing, and names the offending row in its title, per §5's rule that a name which will not resolve publishes nothing rather than a quietly wrong number. A `total` on a `text` column is a configuration error, and so is one on a `computed` column: a total adds up stored cells and a computed column stores none, working one row out at a time over as many rows as the character has. Publishing a single row's derived value and summing a column of them are different questions; the paragraph below answers the first, and **§5's aggregate answers the second** — so the refusal stands as a statement about `total` and names `sum(<id>, <expression>)` as the fix, since every clause in it is about a declarative flag with no scope to evaluate a formula in and no lazy path to a finished sheet, which is exactly what an aggregate has. So is a total on a column whose key is not a name §5 accepts — a key is otherwise free to be whatever the note reads well as, and "Load cost" is a good column heading and an unreadable name. It is refused rather than rewritten, where §5 rewrites a hyphenated component id, because the editor tells an author what their component id became and nothing could tell them what their column had become. Rendering it and refusing to publish it would be one name meaning "publishable, sometimes".

**A declared row may publish its own value, so `10 + skills.perception` is arithmetic the layout writes.** One column per card may set `publish`, and each declared row that wants a name carries a `key`: that row's cell in that column answers to `<id>.<key>`. The column asks and the row names, which is the way round `total` already has it — which value on a row is worth publishing is a property of the column, stated once, not a property repeated on eighteen rows. At most one column may publish, because `<id>.<key>` is two segments and the row is already the second. `text` is refused: the card shows `sword` where the note holds `[[Sunblade|sword]]`, and a name meaning either is a name meaning both. A `computed` column is allowed here where it is refused a total, for the reason above — and §5's aggregate may read one too, on the same reason read once more. The value is produced through `scopeValues`' `compute` (§4.1), from the same row scope the cell on screen is computed from, so the name and the cell cannot disagree about what a row says.

The name is the layout's `key` and never the note's text, so position addressing stays settled: the key says which declared row, and the claim rule says which line of the file that row reads, exactly as the render does. No index leaves the component. A row key must be a name §5 accepts, must not collide with another row's or with a totalled column's key, and means nothing without a published column; each is a configuration error naming the fix, and refused rather than rewritten, because the editor can tell an author what their component id became and nothing could tell them what their row became. A declared row that claimed no note row still publishes: the card renders it with blank cells, a blank cell in a number column is 0, and the name gives the number the reader is looking at.

**A row may declare a modifier against a value published elsewhere on the sheet, and that is the third thing a column can be asked to do.** **One cell holds the whole modifier**, in a column of type `modifier`: `| Belt of Giant Strength | Belt of Giant Strength; armour_class += 1 as item |` moves a Strength card and an armour class card from one row, and neither card names a source. The arithmetic and the namespace are §5's; what belongs here is the shape of the row.

**The cell holds `;`-separated parts, and each is either a name or an assignment.** A part with no `+=` and no `=` is the **name of a modifier definition** the layout declares; a part carrying one is a **typed modifier** written on the row. The discriminator is the operator and nothing else, so a definition may be called `Bracers of Defence +1` and is still read as a name. The canonical separator is `'; '`, the read is tolerant of any spacing around it, and **a part's own bytes survive an edit to another part** — Constraint 3 applies part by part, which is what lets a hand-written cell be edited from the sheet without being reformatted. A blank cell enrols in nothing and is not an error; neither is a half-built typed part, which contributes nothing until it has an amount.

**A typed part's target is a name reference and not an expression.** It never reaches the parser, and `isName` is not the gate either, since a name may be two segments and `isName` accepts one. The gate is the sheet's own name table: the trimmed name is compared byte for byte against what the sheet publishes, which is the Card option rule cited deliberately. A part naming something the sheet does not publish, or publishes without its formula reading a slot, is **rendered, not corrected** — carried as the cell spells it, with the form saying which of the two things is wrong, because snapping it to blank or to the first target would be a layout edit deleting character data, which Constraint 4 and §10 both refuse. A definition the layout no longer declares is carried the same way.

**One `modifier` column is enough, and there is no cap to state.** A cell holds a list, so a row that changes two values is one cell with two parts rather than two columns or two rows, and the amount can no longer be separated from the target it belongs to — which is what the old one-`target`-column rule existed to prevent. A table may still carry a second `modifier` column where an author wants two, and nothing has to pair them.

**A `modifier` column is refused a `total` and refused `publish`.** A total adds up stored numbers and a cell of parts is not one; and §4.2 already refuses a published `text` column because there is no one value a formula could read, which this is worse than — the language has no strings. Each is a configuration error on that card alone, naming the fix. The column takes no other type: it *is* a type, rather than a flag on a `number`, `level` or `computed` column, because what it holds is neither a number nor a choice.

**A modifier row may be an open row, and that is most of the feature.** An inventory of things the character bought is the case, and §4.2's rule that an open row publishes nothing stays exactly true: **a modifier row publishes nothing.** What reaches the sheet is a number under the *target's* name, which the target's own component publishes. `<id>.<name>` remains a fixed-row mechanism, `inventory.Dagger` still fails as an unknown name, and push works for rows the layout does not know about precisely because it never needs a name for the row.

**Nothing about the file format changes for any of it.** A modifier cell is a cell in the markdown table like any other, holding text. Constraint 2 is not reached: the table is `markdown` storage and the cell holds names and assignments rather than links, so a wikilink in a modifier row's *name* goes on working — which is what makes an inventory row a real link and a real modifier at once. A layout that drops the modifier column leaves the cells in the note, unrendered and untouched, on the existing rule for a column the layout no longer declares. A layout that drops a definition, or a bonus type a cell names, also touches nothing stored — the note keeps its words and stops meaning them, which is §10's rule rather than a construction guarantee.

**A published name reads the note; a cell reads the draft.** While a value is being typed, the cell and any total move with it, and a formula elsewhere on the sheet still sees the last committed number, catching up on commit when the sheet rebuilds. That is feedback is continuous, persistence is discrete applied to a name rather than to a card: publishing per keystroke would mean rebuilding the sheet-wide name table on every key.

**Declared rows render first, in declared order; character rows follow, in note order.** The layout's list is a list the author designed — a playbook's printed gear is in playbook order — and it must not be reshuffled by whatever order a character's file happens to hold. Character rows have no declared order, so the file's order is theirs and a new row appends at the end. That is insertion order, and it is the one of the three ordering modes comparable tools offer that nobody has filed a bug against. Reordering rows is deliberately not offered: the note is the order, and Obsidian already ships an editor for moving a line.

**A character row's name is a field, and adding and deleting are two gestures on the row itself.** The name edits on the shared editing rules like any other cell, and a wikilink typed into it stays plain markdown in the note, so backlinks, graph view, hover preview and rename propagation all work — and the sheet draws it as a link, below. An **Add row** control sits in the last row of the table, so it reads as the next row rather than as chrome beside it; the press writes the row and focus lands in its name field. A character row carries a delete control in a trailing column, always rendered and faint, at full contrast on row hover or focus. It is a **trash icon**, taken from Obsidian's own icon set: the layout editor already removes a component, a column and a reset binding with one, and the verb here is the same verb. An `×` was the first answer and reads as dismiss or clear, which is the wrong word for the only irreversible control a component offers — a mark that says the wrong thing at rest asks the arming to carry a meaning the mark should have carried. A claimed row carries none at all rather than a disabled one: its absence is what says the layout owns the row, and eighteen disabled buttons down a skills card is noise. `write` also drops a removal that lands on a claimed row, so a stale index cannot delete a declared row through the back door.

**A wikilink in a cell renders as a link.** `[[Sunblade|sword]]` in a row name or a `text` cell reads "sword", takes the theme's link colour, goes faint where the note does not exist yet, opens the note on a press, opens it in a new tab on a mod-press, and offers Obsidian's hover preview. Editing the cell shows and edits the raw `[[Sunblade|sword]]` — the same text the note holds, which is a note reading one way in reading mode and another in source mode, in one cell. Nothing is stored, published or written differently for it: the note already held the link, which is what markdown storage was chosen for, and what this adds is the two promises the sheet itself owes — that it looks like a link and that it answers a click.

The syntax is parsed in `parse/wikilink.ts` and the anchor is built with plain DOM, because drawing a link needs nothing app-shaped. Only *resolving*, *opening* and *previewing* one does, and those arrive as `RenderContext.link` (§4.1), so a component still imports nothing from Obsidian and a test still runs under happy-dom. That buys wikilinks and no other markdown: a cell holding `*italic*` shows its asterisks, and an embed stays plain text because a row cannot hold an embedded image without breaking its own height. The `link` *column type* — a column whose value is always a note, with a picker and a resolved state as data — is a different feature and stays parked (§12).

Under the hand, the cell is a field over a display layer in one grid cell rather than a swap: the field stays in the DOM and in the tab order either way, which is what keeps focus restoration counting the same controls across a rebuild, and neither layer changes size on focus, so nothing reflows under a pointer already resting on the cell. A cell with no link in it gets none of that machinery.

**Deleting takes two presses.** The first arms the control, which takes a warning tint, marks its row, and names the row it would take; the second commits. The next press anywhere else stands it down, as do Escape and focus leaving the control — the press because a finger has no gesture for moving focus away, and a tap does not focus a button in any case, so without it a phone would be left armed with no way to take it back. The shared confirmation is not available to reach for: `ConfirmModal` takes an `App`, and the render context (§4.1) carries no route to one, so a component's only confirmation surface is the card itself. It follows §12's rule from the Pool's typed-amount reversal, that where a control's input is not its outcome the outcome has to be on screen before it is applied, and deletion is the only irreversible thing a component offers. It also makes the focus behaviour safe: after a delete, focus restores to whatever control now holds that index, which may be another row's delete glyph, and an armed-then-commit control cannot fire on that landing.

**Nothing about the file format changes for any of this.** The same table, the same columns, one line per row. Two behaviour changes reach existing notes, and both are gains: a row whose name differs from a declared label only in case now fills that declared row instead of sitting in the file unrendered, and a row with a blank name cell is no longer dropped on read. Neither deletes anything, and no note is rewritten by opening it. A removal splices exactly one line out and leaves every other byte alone. A section the component cannot read — two tables in one section, which every write would be ambiguous against — is one it refuses to write at all, because an index means the row at that position in *that* body and there is no such body to count in.

Rules the storage follows, each of them a decision rather than an accident:

- **A computed column is never written to the note.** It is derived, and a stored copy of a derived value is a stale copy waiting to happen. The note holds the columns the character owns and no others.
- **A blank cell in a `number` column is zero.** The layout declared the column numeric, and an untrained skill is left blank on every character sheet ever printed. This is the one place a missing value resolves rather than failing, and it is confined to a column whose type the layout stated.
- **A row the layout no longer declares stays in the note**, as does a column and any prose around the table (§10). On a fixed card it is unrendered and untouched; on a card with open rows it is one of the character's own, which is the same rule read from the other side. A second row under the same name is an ordinary second row.
- **A column may leave its heading off the sheet** with `hideHeading`, for the one whose control names itself: a proficiency ring is legible without a word above it, and the word is several times wider than the ring, so the heading was setting the column's width against a control that needed none of it. The heading is still rendered for assistive tech, so the column keeps its name where a name is all there is.
- **A text column may read as a gloss on the row** with `secondary`, which gives it the clothes the abbreviation wears under a card's name: a size down, tracked, and faint, at full contrast while it is hovered or focused. For the column that qualifies the row rather than adding to it, such as the ability behind a skill or the source of an item, where equal weight leaves the eye deciding which of two things per row the row actually is. Opt-in per column, and confined to `text`: muted user data otherwise reads as disabled, and a number is the row's arithmetic rather than a note beside it.
- **The name is always the note's first column**, whatever `namePosition` draws on the sheet. A display preference must not move it: a proficiency mark reads better before the skill, and the file still has to say which skill the row is before it says anything else about it. What identifies the row is its position, not that cell — the first half of this rule is the file format's and survives; the second half was an assumption the file never made.

This is where the design risk concentrates. It is the first component using the markdown storage path, the first holding wikilinks, and the first with per-row formula scope. It is also what forced `formulaFields` to grow paths (§4.1): its expressions live one per column and one per row, so no flat list of config keys could name them.

**Computed**. Read-only formula output. Covers Passive Perception, spell save DC.

- *Config:* `label`, `value`
- *Data:* none, entirely derived
- *Sheet view:* read-only, hovering reveals the formula
- *Formula fields:* `value`

**Rich text**. A free markdown block. Covers backstory, notes, appearance, a Keeper's six short boxes: the prose a sheet is half made of and that no card, table or pool has anywhere to put. Built.

- *Config:* `hideLabel`, and nothing else. `label` is shared config the editor owns. No placeholder key despite Card's `notePlaceholder` — a note line qualifies a value and its qualifier differs per card, and prose does not — and **no width, height or rendering toggle**: the grid is the sizing control (§8), and 27 months of prior art on the closest analogue says a markdown-rendering opt-in is what needs fixing rather than what needs adding
- *Data:* `markdown`. **The section body is the value**, with no fence, no key and no structure, so Constraint 2 is satisfied by construction — this component never writes a fence at all — and so is Constraint 3: `read` hands back the body with the whitespace run at each end removed, and `write` returns the body it was given where the text has not changed and otherwise puts the new text back inside the *same* two runs. A hand-written section keeps its own spacing and an edit changes exactly the prose. A missing section, or one holding only whitespace, writes `\n<text>\n`. **`read` can never fail**: every body is legal text, so this is the one component in the catalog with no read error state at all — a fence, a table or a heading in the body is content. **The one exception is `## ` at the start of a line**, and it belongs to the note format rather than to this component: §3.1 gives a note one `##` section per component, so a block holding such a line would split the note there and show only what was above it. Not escaped — that would put a plugin's syntax into a file the user owns — and `read` is not failed either, since an error would make this the one body that is not legal text. **The *write* is declined instead**, which is the third answer and a correction: this entry once guaranteed only that "nothing is lost from the file", and a user report showed byte survival is not the part that matters — the bytes sat in a section nothing draws while the box emptied and the plugin announced "saved", which is silent destruction from the reader's seat. So a draft holding such a line is not committed, the field keeps it, and the message names the line and the fix (`use "### " instead`). `read` stays total and Constraint 4 is untouched, since nothing is written at all. `#`, `###` and `##` with no space are content
- *Sheet view:* a label, and a box under it. **The placement is the box and the content scrolls inside it.** Stated outright because it is the longest-running complaint in the prior art — a prose block with "no vertical size" that "grows according to its content which does not allow to control its position in the sheet in a stable way", open since 2022, beside three siblings for the same box at zero height, squished, or absent. A component that sized itself to its content is a component ceasing to fill its placement, which §8 forbids, and what it produces is the sheet moving because of something the author never placed. So the box is `height` grid rows tall whatever is in it, a long backstory scrolls, and an author who wants a taller box places a taller component. **"Grid rows tall" is a floor and a measured one**, since the sheet's rows are content-sized and there is no row height to derive: `--sheetsmith-grid-row` is `4.75em` and the delivered height is the greater of that times `height` and whatever the row itself came out at, which can only be wrong upward, where the row grows and the box fills it (`docs/UI.md` §9) No border and no surface of its own: prose beside cards reads as prose rather than as a card with a paragraph in it (`docs/UI.md` §9)
- *Sheet view, the gesture:* the sheet's own stacked edit rather than a second editor. The rendered prose and the field that edits it both fill the box, and the field is in the DOM and in the tab order in both states. The rendered layer answers the press itself: a link owns its own, a drag that selected text is left alone, and everything else focuses the field. Four departures from a table cell's version of the same pattern: the rendered layer is **hidden** on focus rather than left transparent, since the two hold one text in two different shapes and overlaying them would be unreadable; the layer is the pointer target rather than inert, because it is a scrollport and a scrollport that is not a hit target never receives a wheel; the caret is not placed from the click, since a point in the rendered view is not the same character in the source, and lands at the start of the text; and the box never changes size while each layer's scroll extent moves on its own, so the reader's place is not carried into edit mode. Enter inserts a newline and commits nothing, blur commits, and Escape restores the stored value and announces the restore (§5). **A rendered embed is display, not a control** — a task checkbox inside an embedded note is not tickable from the sheet, which is the price of the block being editable at all
- *Sheet view, markdown:* rendered with the app's own renderer, reached through `RenderContext.renderMarkdown` so `src/components/` still imports nothing from `obsidian`. The view owns one child `Component` per render pass and unloads the previous one, since a sheet rebuilds on every committed edit and every embed's listeners would otherwise accumulate. Where there is no renderer — a unit test, the harness — the block draws its text as paragraphs with its wikilinks live and no other markdown, which is `LinkContext`'s own bargain: what is absent without the app is the app, not the component
- *Formula fields:* none. It publishes nothing either: §4.1 names "a block of prose" as the case that leaves `scopeValues` off, and §5's language has no strings, so a published block of prose could be compared to nothing and handed to no builtin. It could only be *written*, and a Pool whose `max` named a backstory is exactly the defect §4.1 warns about (§13)

**Group**. A heading over a region of other components. Covers visual sectioning, and the arrangement a grid alone cannot name: six ability cards each beside their own skills table, under one **Abilities** heading.

- *Config:* `hideLabel`, and nothing else. The heading is the shared `label`, not a `title` of its own — a container has no note section, so `label` is only ever its display name, and two keys for one string is a second name to keep in step. `children` is shared config the editor owns (§4.1)
- *Data:* none. `storage` is `none`, so no section is read and none is written
- *Sheet view:* the heading, a hairline rule under it, and the children on the group's own grid — the group's placed size, `width` columns by `height` rows, so a card inside the group is the same size as the identical card outside it in both directions. No box around the children: a container is a region *behind* the cards, and a border around bordered things reads as the loose chrome §9 of `docs/UI.md` warns about. The group is its own reflow context, so a narrow one stacks its children while the sheet around it stays a grid (§8). An empty group is a layout part-way through being built, not an error
- *Sheet view, what it does not do:* **hide anything.** It shipped with a `collapsible` heading and lost it, and the reversal is worth carrying here because the control looked obviously right. **A collapse is a component ceasing to fill its placement**, which §8 forbids, and what it actually produced was the placement's own space left as a hole: a group's cell is sized by whatever else spans its grid rows, so collapsing one beside a taller neighbour reclaimed nothing at all, while collapsing the tallest one moved the whole sheet below it. One control, one layout, two unrelated outcomes, decided by a property of the placement nothing states and nothing could show the author (§13). Hiding belongs to a container that keeps filling its placement while it hides, which is Tab set
- *Formula fields:* none. A container publishes nothing, and its children publish exactly the names they would publish at the top level

**Tab set**. A strip of names over one region at a time. Covers the multi-page sheet: a wide one at the top of a layout is what a "pages" feature would have been.

- *Config:* `hideLabel`. Its `children` are the tabs, **in the order they are written**, each one's own `label` naming its tab. **A tab may be any component**: a Group where the tab is a region, and the card itself where a tab is one Table. Requiring a container would be ceremony on the second case, and the depth rule already bounds the first. **A tab has no placement**, because it is the whole panel — its `col`, `row`, `width` and `height` mean nothing, the editor offers none of them, and a container tab takes its inner grid from the tab set's own `width × height`. That is the single exception to a container's inner grid being its own placement, and it is why tab order is the child list rather than grid reading order (§8)
- *Data:* none, on the same terms as Group
- *Sheet view:* the strip, then the active tab filling the panel. **Every tab is the whole panel and the panel is the tab set's placement, so all of them are the same box and switching tabs moves nothing anywhere on the sheet.** That is the whole reason hiding lives here rather than on Group: a tab set goes on filling its placement while it hides, which is what §8 asks of every component, where a collapse could only stop filling it. So a tab set three columns by two rows holds a tab that is a Group of a 2×2 beside a 1×2 and a tab that is one 3×2 Table, and the two are interchangeable without anything moving. The panels occupy a stage that is not a reflowing grid, because overlapping elements on one that reflowed would stack vertically and make the set as tall as every tab together. A tab whose children leave inner cells empty leaves them empty rather than shrinking the box. An inactive tab's content stays in the DOM and laid out, hidden with `visibility` and `inert`: out of tab order and out of the accessibility tree, and **not** reachable by find-in-page, which is the one price of the guarantee — content removed from layout contributes no height, and a panel that contributed no height is a panel that could move the sheet. It is still rendered and its formulas still resolved, so hiding is never a way to make a formula not run: a component on a tab nobody has opened publishes, resets, and appears by name in a trigger's confirmation exactly as a visible one does. Every tab is in the focus order rather than the ARIA pattern's single tab stop, which Deque names as a defect: on a control whose whole job is hiding things, a keyboard user who cannot reach the fourth tab without knowing to press an arrow key has lost the content. A tab set whose tabs are containers cannot itself be nested, since those tabs would be the third container; one whose tabs are cards may sit inside a Group like any other second-level container
- *Formula fields:* none

Both are containers (§2), and neither may sit inside a container that is itself inside one. Both are built.

**Image**. A portrait or a symbol: the one thing a character sheet holds that is not text or arithmetic. Built.

- *Config:* `hideLabel`, and nothing else. `label` is shared config the editor owns. **No width, height, fit or crop key, in any spelling.** The convergent prior art is width-and-height where one dimension preserves the ratio and two may distort — Custom System Builder's Picture, and Obsidian's own `|100` and `|640x480` — and the reason not to adopt it as *configuration* is §8's own sentence: a width on the component would be a second sizing control disagreeing with the grid
- *Data:* `markdown`, **one embed**, the source line exactly as written. **This amends the entry's own earlier `fenced` storage holding "a path or wikilink", and the amendment is Constraint 2's rather than a preference.** Obsidian does not index links inside a code fence, so a fenced value would mean renaming the image file silently breaks the sheet — the single most common way a vault reference goes stale, and the failure class every image issue in the prior art belongs to. So the body is the embed the reader would have written anyway: rename propagates, backlinks resolve, the graph sees the file, and **the portrait actually shows in markdown view**, where `path: Portrait.png` in a fence would have shown a code block. It matches Table's precedent exactly — the component that holds links stores markdown — and the storage half is `parse/markdown-body.ts`, shared with Rich text
- *Data, what is refused, and **where**:* a bare path (it would not propagate on rename, which is the whole point), `![](…)` in either local or remote form, and anything before or after the embed. **All of it is refused in `render`, not in `read`, and `read` cannot fail at all** — a body this component cannot use is still a body it can hold. That is a correction with a reason: a failed `read` never reaches `render`, so the view replaces the whole cell and there is no field left, and Image is the first component whose own editing gesture can produce a body it refuses. Typing a web address and leaving the field locked the reader out of a value they had just entered, with the only way back through markdown view. So the message goes in the frame under the label, the field stays and holds exactly what the note holds, and the component prefixes its own message where it drew no heading. **An external URL is refused as policy rather than syntax**, so it gets a message of its own: `AGENTS.md` and Obsidian's Developer Policies both say default to local and offline operation, and an `<img src="https://…">` the plugin wrote is a request the plugin makes on the reader's behalf, on every render of the sheet, to a host named in someone else's note. The positive answer is what keeps it from being a bare refusal, and it is why these two components shipped together: Obsidian renders `![](https://…)` perfectly well in a **Rich text** block, under the app's own settings and the app's own disclosure, so the message sends the reader there
- *Sheet view:* a label, and a frame under it whose height is the *placement* — `height` grid rows, whatever is in it. The picture is **scaled to fit in both directions** with `object-fit: contain`, centred, aspect ratio preserved, **never cropped and never distorted**, with the slack left as the frame's own surface rather than filled by stretching. Up as well as down, and that half was a correction: with `max-width`/`max-height` and no size the element's box *is* the intrinsic ratio shrunk to fit, so `object-fit` never applied and a 48×48 sigil drew at 48×48 in a 205×194 frame — a speck the author could not make bigger. Drawing at native size is the same defect this entry refuses the stored size hint for, with the file's pixel dimensions in place of a number in the note: a 48px file and a 4000px file in one 3-row box would draw at wildly different sizes, with the *file* deciding a box the layout author placed. §8's "the grid is the sizing control" settles it. The cost, since "never cropped and never distorted" does not cover it: a picture smaller than its frame is enlarged and **shows it — a 48px sigil in a three-row box is visibly blocky, not merely soft**, which is what "soft" undersold until a review looked at one in Obsidian. The author's answer is a smaller placement §8 is not bent by this, it is read correctly: the *component* fills its placement, and a picture is what the component draws inside it. A size hint in the stored embed is preserved in the file byte-for-byte and **ignored on the sheet** — honouring a number out of a *character's* note would let one character's portrait float centred in a box the *layout author* sized, which is the first thing §8 forbids, and markdown view goes on honouring it either way. The picture carries a class this plugin's stylesheet owns rather than being a bare `<img>`: content drawn into a themed surface inherits the reader's theme and snippets, and a picture cropped by a rule keyed on its *filename* is a real report
- *Sheet view, click to change:* honoured and narrowed. A press on the picture, on an empty frame, or on an error message focuses a one-line field holding the embed's own text and selects it, so the reader replaces the whole reference — which is what Obsidian puts on the clipboard for a file, so the gesture comes free. **The field is the picker**, and a file suggester is what it is instead of: that would be a context member with its own keyboard model, what it would list is every file in the vault (needing a scoping config key this entry promised not to have), and the plugin's existing answer for "a choice from a closed list" is a `<select>` — a vault is not a closed list. Same `editable.ts` policy as every other stored value: blur commits, Escape restores and announces
- *Sheet view, failure:* **four states, and every one of them is on screen under the component's own label.** That clause is load-bearing, because every image failure in the prior art is silent — an empty div with the diagnosis in the console, a broken-image icon, a value reverting with "console is not outputing any warning nor error". A body that is not an embed is refused in `render`, in the frame under the label, with the field still there to fix it; a target the vault does not hold says `No file in this vault is called "Portrait.png".` in the frame; a file the browser cannot draw says `"Notes.md" is not a picture.` in the frame, **after trying rather than before**, because the plugin holds no list of formats — an extension allowlist is exactly how webp came to render outside a plugin and not inside it, and a test scans `src/` for one. An empty or missing section is **not** an error: an empty frame, the label above it, and a field whose placeholder is the syntax. Nothing on any path writes to the console. The label is drawn before anything can fail, so this component adds no instance to `docs/UI.md` §12's unlabelled-error row
- *Formula fields:* none, and it publishes nothing: §4.1 names "an image" as the case that leaves `scopeValues` off, and §5's language has no strings, so a published path could be compared to nothing, handed to no builtin, and only *written* — a Pool clamping its bar against a file path (§13)

### 4.3 Layout schema

The layout schema is not designed separately. It is the union of the shared contract and each component's configuration, plus three layout-level pieces:

- **Function library.** The layout's own named functions.
- **Reset triggers.** The layout's own named events.
- **Promoted fields.** Which values, if any, mirror into frontmatter.
- **Bonus types.** `modifierTypes`, the list a modifier's type is drawn from (§5).
- **Modifier definitions.** `modifiers`, the named modifiers any row on any character may enrol in (§2). Held as written: whether it is an array of objects at all is the file format's business and refuses the layout, while whether a definition is *usable* — no name, a name twice, a target this layout does not publish, an amount that will not parse — is contents, reported in the editor while every sheet on the layout goes on rendering.

A layout is therefore metadata, a function library, a trigger list, a promoted field list, a bonus-type list, a modifier list, and an ordered list of component configurations. Every time a component is added to the catalog, the schema grows by exactly that component's config block and nothing else.

## 5. Formulas

- **Any numeric field configured in a layout accepts a literal or a formula.** A Pool's max, a Track's box count, an ability's derived display, a Table's computed column. There is no separate "computed field" concept to learn.
- **Formulas reference other components' values by name**, and the name is the component's `id`, never its label, because renaming a label must not break arithmetic. An id must therefore be a name the expression parser accepts: letters, digits, and underscores, never starting with a digit. A hyphen would read as subtraction, since `armour-class` is "armour minus class", so an id carrying one is rewritten when the layout loads (`armour_class`) rather than rejected. An unreferencable id is one nothing can be pointing at, which is what makes renaming it safe, and blanking a whole sheet over it would not be. A component holding one value answers to its bare id (`armour_class`); one holding several answers to `<id>.<name>` (`abilities.DEX`). What a component publishes is declared by its `scopeValues` (§4.1), and a name the sheet does not publish fails to resolve rather than defaulting to zero.
- **A bare name gives what the card shows, not what the note stores.** `abilities.DEX` is the +6 in large type, not the 22 behind it: the sheet has already decided what that ability means, and a formula reading it should get the same answer the reader does. Where a component computes nothing, the two are the same thing. The stored value stays reachable as `<name>.value`, so `abilities.DEX.value` is 22, for the formula that genuinely wants the raw score. The rule reads one level down unchanged: `skills.perception` is the number on that row of the card, and `skills.perception.value` is the cell the note stores, which on a computed column is nothing at all, so a formula reading it fails as an unknown name. **A dropdown card is the one place the card shows something no name gives**, and it is not an exception to the rule so much as the rule read from the other side: an option's label is what the layout decided the reader should see for a stored value, where a `derived` is what the sheet worked out that a stored value *means*. The meaning is the thing stored, so `race` and `race.value` are both the option's `value`, and the label is display (§4.2).
- **A name is worth what the component says it is worth**, through one of the three sources in §4.1: the stored value, a `display` naming one of the component's own formula fields, or a `compute` the component runs with the finished sheet in hand. The third is what lets a name mean something no declaration could state — a Track's filled segments, a Table row's cell — at the cost of being opaque to the save-time check below. A name whose source will not resolve publishes nothing rather than falling back to the stored value: handing back 22 where 6 was meant is a worse answer than none at all.
- Names resolve nearest-first: a scope internal to the component (one ability's `value`, a table row's cells), then the component's own data, then the sheet. A card's `value` therefore always means its own.
- **A formula may aggregate over the rows a component holds**, which is what covers the rows a character added: `sum(<component>, <expression per row>, [<condition per row>])` and `count(<component>, [<condition per row>])`. `sum(inventory, Weight)` is the total weight, `sum(inventory, Qty * Weight)` is a pack's encumbrance, `sum(inventory, Weight, equipped)` is the weight of what is carried, and `count(inventory, equipped)` is how many things are. Which rows there are is `scopeRows` (§4.1), and only Table publishes any.
  - **The language gains no collection.** No expression evaluates to a list, before or after this: a row set lives for the duration of one builtin's own frame and is never a value. That is the guard, and it is what the type not existing buys — a value in this plugin is one typo from `applyReset` writing it into a note, and a Pool whose `max` is a list clamps its bar against a list and restores to one. The cost is that the language grows by builtin rather than by composition: `avg`, "the heaviest item", and "the names of what is equipped" each need a new builtin or cannot be written, and a filtered set cannot be named and reused.
  - **The first argument is a component reference, not a value**, and it is the one position in the language where that is true. `inventory` there is read as identifier text and never resolved through the name table, so a component publishing a bare name of that spelling is not read as that name there. Stated as a rule rather than left to be discovered: the alternative is a quoted string, and the tokenizer has no quote handling at all, so adding string literals to the grammar so that one argument can be quoted is a larger and more permanent tax — and it would make that argument look like a language inside a string.
  - **The remaining arguments are evaluated once per row, in the row's own scope**, which extends the layering above by one: the row's names, then the caller's internal scope, then the component's own data, then the sheet. **The row is the nearest scope there is, nearer than a function's own parameters**, so `load(Weight) = sum(inventory, Weight)` sums the column rather than the parameter — the harder surprise is a row expression that cannot see a column because a parameter happens to share its name, and the meaning is still fixed at the definition because the table is named in the same expression as the shadowing. A column key that is not a name this section accepts is unreachable to a row expression, exactly as it is untotallable: one limit, one rule.
  - **A function body still sees only its parameters and the sheet.** `sum(inventory, weight_of(Qty))` is fine; `weight_of` reading `Weight` off the row is not, and fails as an unknown name. A function is not a text substitution, and a row is not an exception to that.
  - **An aggregate may read a computed column**, because it is handed a resolver bound to the finished sheet — which is what `total` never had. It is often unnecessary, since the second argument is an arbitrary row expression: `sum(inventory, Qty * Weight)` needs no `Load` column to exist.
  - **A yes/no column is counted, not summed.** A `toggle` cell is `true` to a formula, which is the same rule that stops a computed column writing `Training * Worn`, so `sum(inventory, Worn)` is refused and names `count(inventory, Worn)` as the fix. The totals row maps a toggle to 1 on its way into its own sum, so `total` on that column publishes the same number the count does; what differs is the spelling, and the language gains no numeric meaning for yes and no that its operators do not have.
  - **One unreadable row fails the whole aggregate, and the error names that row.** `Row "Rope": sum() needs a number, got "coil".` That is the totals row's rule extended rather than a second answer to the same question — reporting the row beats adding up the rest, because a quietly wrong number is worse than a missing one, and silent wrongness is the failure the closest comparable tools actually ship. **An empty row set is 0**, not a failure: an empty inventory weighs nothing, and a new character's sheet must not be full of `?`. That last is also why `min` and `max` over rows are not offered — neither has an answer over no rows.
  - **An aggregate is an edge a reader can see**, unlike a `compute`: `sum(inventory, Load)` names `inventory` in a formula field, so the save-time check below has something to follow. The edge is coarse, reaching the whole component including every computed column the walk evaluates, so a component-level reading may report a cycle where none exists at runtime. Reading it precisely means following which names the walk actually touches, which needs the row scope, which is the component's.
- **The sheet publishes one modifier slot per published name, under a reserved `mod.` namespace, and a target reads its own as `mod.self`.** That is how a modifier row reaches the value it names (§4.2): the authoring is push, and the engine stays pull.

  ```
  derived = value + mod.self
  ```

  - **`mod.X` is 0 where `X` is a published name nothing pushes at**, on the aggregate's own empty-set rule: without it every target's formula would break on every character who owns no magic items, which is every character on the day they are made. **`mod.X` fails as an unknown name where `X` is not a name the sheet publishes**, which is what stops the zero rule swallowing a typo — `value + mod.armor_class` on a sheet publishing `armour_class` must not quietly read zero. The domain of the namespace is exactly the published-name set, structurally: the slot pass registers `mod.<name>` for each name already registered.
  - **A push at a name the sheet does not publish is not an error.** It is a cell holding a value the layout no longer offers, and §4.2's ruling on exactly that is that it is rendered, not corrected — surfaced at the row that wrote it, which is where the fix is.
  - **`mod.self` is that name's slot, inside the evaluation of a formula whose result is published as a name.** It is the shape `value` already has, read one layer out: `value` is the number this evaluation is *about*, and `mod.self` is what has been pushed at the name this evaluation *becomes*. The relative spelling is not a convenience — **a Card set cannot spell its own target**, because its `derived` is one formula computed per entry and no absolute name inside it can say which entry it is running for, so without it the six ability scores, the canonical modifier target in every system surveyed, could not be modified at all. The absolute form works too where a component has a bare id, exactly as `value` and `<name>.value` both do. **`mod.self` is 0 where the evaluation publishes no name**, which is what lets one Table column formula read a slot down every row and show numbers rather than `?` on the rows that carry no key and so cannot be pushed at.
  - **It does not collide with a layout's own `mod()`.** `mod.self` and `mod.armour_class` tokenise as one name token each, while `mod(score)` is a bare `mod` followed by `(`, and a no-argument `mod` in a library is untouched because bare `mod` is never registered — only `mod.<something>` is. Every 5e layout writes `mod(score) = floor((score - 10) / 2)` and the two live side by side with no rule needed. **`mod` as a component id is rewritten rather than refused**, by the same path a hyphenated id already takes, because a component with that id would register `mod.DEX` beside `mod.armour_class` and one name would mean two things. Sections key on the label, so no character data moves.
  - **Reading another target's slot from inside a modifier amount is refused**, and there is a third guard for it: the modifier walk's own, without which the walk re-enters itself. Whether it is refused is measured rather than reasoned — asked cold it is refused naming the row, and asked after anything else has walked, the name table's guard fires instead, memoises the slot, and the same expression resolves. So the outcome turns on which card drew first, which is the same grid-order cost this section already records for the two existing guards, left alone for the same reason. Reading a slot anywhere *else* costs nothing and is how a sheet shows a target's modifier total beside the number.
  - **One unreadable amount makes the whole slot publish nothing, and the error names that row.** `Row "Belt of Giant Strength": ability is not defined on this sheet.` The aggregate's rule exactly, and it is why the mechanism is a thrown failure rather than an absent value: it reaches the reading component's own explanation, which is what puts the sentence under the reader's eye. Nothing caches the refusal.
- **Modifiers of one declared bonus type do not stack: the best bonus and the worst penalty of a type apply, and the types add.** Stated precisely, because "highest within a type" is wrong for penalties: for each type, the largest positive amount plus the smallest negative amount, summed over the types, plus every untyped amount in full. Applying "highest" naively to negatives would keep the *weakest* penalty, which is the opposite of what every system says. Zero contributes nothing either way and appears in no breakdown.
  - **The rule belongs to the set and not to any one modifier**, which is why there is no per-modifier operator: whether a given +2 applies depends on what else is present. Three of the four systems surveyed combine by maximum somewhere — Pathfinder 2e by type, D&D 5e for the same spell cast twice, Lancer for accuracy at magnitude two or more — so no amount of operator vocabulary would have reached it.
  - **Untyped modifiers all stack**, each its own kind rather than all one kind, which is both what Pathfinder 2e says and what the default has to be: with no types declared anywhere the feature is plain addition, which is what an author who has never heard of bonus types expects.
  - **A type lives in configuration and never in the expression language**, on the decision §13 already took about strings: the layout declares the list in `modifierTypes`, a modifier names one of them, and the formula never sees the word.
  - **A note may name a type, and that sentence replaces a guarantee.** This entry used to read "nothing stored ever names a type", and the type lived on the column so that a layout edit dropping one could not orphan character data — §10 satisfied by construction. A typed modifier's `as` clause is stored in the note, so the guarantee is gone and **§10 carries a rule instead**: a type the layout no longer declares is rendered, not corrected, the effect applies and contests as its own kind, and the layout editor's bonus-type field reports it. What it buys is the thing the column model could not do — a table whose rows carry different types is one column, where it used to be one column per type with most cells blank.
  - **It stays one number per target, which is what keeps the single pass.** Max, min and `+` are all commutative and associative, so the result does not depend on the order the pushes are walked in, and **v1 therefore needs no priority field** — asserted by shuffling rather than claimed. The sum runs through the same float-safe helper the totals row and `sum()` share, so the breakdown's total, the number on the card and a formula reading the slot cannot disagree about `0.30000000000000004`.
- **Which names accept a modifier is computed from the layout, statically, and coarsely at the component**: a published name `X` accepts one when some formula field on the component publishing `X` mentions `mod.self`, or when any formula field anywhere on the layout mentions `mod.X`. A text scan over configuration, for three reasons. It is **lazy-proof**, where an observed set would report `if(equipped, value + mod.self, value)` as accepting nothing on a character whose item is stowed. It **needs no render**, so the layout editor and the sheet reach one answer from one input and neither needs a character in hand — which is what the target cell's picker is over. And it is coarse in the aggregate's own direction, **over-reporting**: a Table where only the computed column reads a slot reports every name that Table publishes as accepting, including a column total, so the picker may offer a target that ignores the row. The sheet's stray line is the backstop and cannot fire for an over-reported target; making it exact needs the name-to-field pairing a `compute` is opaque to by design.
- **Each layout defines its own function library.** This is what makes the plugin system-agnostic: no game's arithmetic is built in. Definitions are written one per line, as in `mod(score) = floor((score - 10) / 2)`. One taking no arguments is a named value, written as a bare name: `prof` rather than `prof()`, though both are accepted rather than one being made an error over punctuation. Lines starting with `#` are the author's own notes.
- **A function body sees its parameters and the sheet, and nothing of its caller.** A function is not a text substitution, so `mod(score)` means the same arithmetic wherever it is called. The calling component's nearer scopes, an ability's `value` or a table row's cells, are not visible inside it, and only its parameters and the sheet are. Parameters shadow the sheet. A name the sheet publishes wins over a no-argument function spelled the same, so a component keeps the meaning of its own id.
- **A definition that will not parse is reported, not fatal.** It stays out of the library and is named in the layout editor, where it can be fixed, while a formula calling it fails on its own component like any other unknown name. One typo must not blank every sheet the layout serves. A function defined in terms of itself, directly or through another, is refused on the same terms. That is the runtime floor under the save-time cycle check below, and it exists for the same reason.
- **The shape of the key is not forgiven the way its contents are.** What a line says is the library's business; that the key is a list of lines at all is the file format's, and a `functions` that is anything else refuses the layout, as a bad `columns` does. The two are not in tension. A typo is a mistake inside something the user can see and correct in the editor, and a wrong shape is a file the editor cannot open at all, so saying so plainly beats ignoring the key and leaving the author to wonder where their arithmetic went. Two things the editor does not yet check are a cycle between functions and a definition shadowed by a component of the same id. Both are reported on the card that calls them, which names the reason but says it a long way from where it was written.
- A layout may not redefine a standard helper, since a formula reading `floor` must mean the one thing everywhere. `sum` and `count` are reserved on the same terms.
- Standard helpers are available: floor, ceil, round, min, max, abs, a conditional, and the two aggregates above. `min` and `max` are scalar and variadic and stay that way: giving either a component reference in its first argument would give one name two grammars.
- Computed values are read-only in sheet view.
- **A name that will not resolve publishes nothing**, rather than falling back to the value behind it. Handing back 22 where the +6 was meant is a worse answer than none: the formula reading it fails, and its own component says so.
- Circular references are caught when the layout is saved, not at render time. Because published values are computed, one name can depend on another, so the sheet-wide table is also lazy, memoises what resolves, and refuses a name that needs its own result. A cycle leaves both components unresolved and every component outside it working. That runtime floor is not a substitute for the save-time check. It is what stops a two-line cycle taking the app down with it while the check does not exist. It also covers a cycle *inside* a component, since the guard is keyed on the published name and two published rows of one Table are two distinct names: both publish nothing, both cells show `?` beside the name they could not find, and everything else on the sheet keeps working. What the save-time check cannot see is a cycle running through a `compute`, which is code rather than a named edge — the cost §4.1 records against that member.
- **A row set being walked cannot be walked again**, which is the second half of that runtime floor and covers the rings no published name runs through: a table whose own row formula aggregates over it, two tables whose formulas each aggregate over the other, or any longer ring of them. None of them recurses through anything the name table can see, so without this they would not terminate. **Every walk in the ring is refused, not only the attempt that re-entered one** — the ring being the walks from the re-entered one inwards, which at two is indistinguishable from "the innermost pair" and at three is not. Otherwise a walk in the middle completes, so it would otherwise be held as a whole row set with the column that reached across silently absent, and one formula reading that table would get an answer where another did not, which is the same disagreement one row scope exists to prevent. It would also make which of them broke depend on where the sheet started, and that is grid order. **And nothing outside the cycle is refused with it**: a table whose own formula merely reads one that loops is not in the loop, so it fails on its own terms — the value waiting on the broken table is absent from its rows and `?` in its cell, which agree — while every aggregate over what it does hold keeps working. So each cell in the loop shows `?` and says a formula on its rows reaches back to it, directly or through another table, and the rest of the sheet stays live and editable.
- **What it costs is that two guards can catch one ring, and they do not agree.** A published name aggregating over a table whose row formula reads that name back is a ring with a name in it, and either guard may be the one that closes it. Reached at the name, the name table's guard answers `undefined`, the row formula goes unresolved, and the aggregate over the table's other columns is fine — which is the coarse edge above, working as described. Reached at the rows first, by a card holding an aggregate over that table and drawing earlier, the row table's guard closes it instead and refuses that whole walk, so that card shows `?` while the identical formula on a card drawing later shows the number. It is one evaluation and it corrects itself, since the name resolves on the next attempt and the row set is then built and memoised; what it costs is a `?` whose appearance depends on grid order. Closing it means the two guards knowing about each other — the row table letting a walk complete where the ring passed through a name thunk, and refusing it only where the ring is entirely its own — which is a coupling neither has today and is not this feature's to add.
- **That refusal lasts the walk and no longer, and the name table caches only what resolved.** Both halves are the same rule read from two sides: a refusal is about one evaluation, not about a component. Held against the component, the coarse edge above stops being coarse — a published name aggregating over a table whose column reads that name back is refused for good if some formula happens to reach the column before the name, and then every unrelated aggregate over that table is refused with it. Cached as a name's value, the same transient miss decides what the name is worth for the rest of the render. Either way it is evaluation order, and so grid order, deciding whether the sheet works. A genuine cycle still terminates on the guards and simply recomputes its own refusal, which is the price already paid for explaining a failed field twice.
- A formula referencing something missing shows an error on that component alone. The rest of the sheet keeps working.

Worked examples, both drawn from the original brief:

A 5e layout defines its own functions.

```
mod(score) = floor((score - 10) / 2)
prof       = ceil(level / 4) + 1
```

A skill row's computed total, where `Training` and `Bonus` are cells on the same row, `prof` is a component elsewhere on the sheet, and `ability` is one of the row's own values, defined by that row as `abilities.DEX`. That gives the +3 the ability card shows rather than the 16 behind it, by the rule above.

```
ability + Training * prof + Bonus
```

`Training` is a level column named untrained, proficient, and expertise, so the same formula covers all three, and the rule for each level is arithmetic the layout wrote rather than a concept the plugin knows. A system whose levels are not evenly spaced writes the rule out instead:

```
ability + if(Training == 2, prof * 2, if(Training == 1, prof, 0)) + Bonus
```

A feature's uses per day, expressed as a Pool max.

```
mod(Abilities.WIS)
```

A loaded pack's encumbrance, over an inventory whose rows the character owns. Nothing here names a row, and the layout does not know how many there are.

```
sum(inventory, Qty * Weight)
```

A Call of Cthulhu layout would define entirely different functions (`half`, `fifth`) and the plugin would not notice the difference.

## 6. Reset triggers

- Each layout defines its own named triggers. A 5e layout declares Short Rest and Long Rest. A Blades layout declares Downtime.
- Any Pool or Track can bind to as many triggers as it needs, each with its own action.
- Per binding, the reset `action` is one of `full`, `empty`, or `formula`, and only `formula` carries an expression, in `to`. It is optional, because a binding may instead, or also, carry `buffer: 'clear'` for a component that declares a buffer. One of the two is required, since a binding that does nothing has no reading.
- Sheet view shows one button per trigger.
- Applying a trigger confirms first and is undoable.

**A component binds to a list of triggers, because the triggers a system declares overlap.** In 5e a long rest restores everything a short rest does, and not the reverse. A component that could name only one trigger could not describe the system at all: bind ki to the short rest and a long rest leaves it spent. Each binding carries its own action, which is the part a trigger hierarchy could not express. A pool may regain one use on a short rest and all of them on a long one, and that is two different answers to two different events rather than one answer inherited.

A single binding may be written on its own rather than as a list of one, the way §5 accepts `prof` beside `prof()`. Two bindings on one trigger refuses the layout: the button would apply both in file order and the second would win unannounced, which is no reading anyone intended.

The cost is real and worth stating. The rule "a long rest covers a short rest" is a fact about the triggers, and writing it per component means repeating it on each, with a new short-rest pool failing to restore on a long rest until someone remembers. A trigger that declared it included another would say it once. That is deliberately not built: it is sugar over this, expressible by expanding one binding into several at the moment a button is pressed, and it needs no change to what a component implements. The list is the base case, and it is the one that can say things the hierarchy cannot.

**The action is a key of its own, and the states are named rather than numbered.** `to` is declared a formula field on Pool and Track (§4.2), so it is handed to the evaluator as an expression, and a `to` that also had to hold the literal word `max` could not be. One string cannot be both a formula and a sentinel standing in for one, and the way to find out is to write a layout that resets to `max` and watch the evaluator look for a name nothing published. `full` and `empty` name the states rather than the numbers because the same three actions have to cover a Track's flag, where they are yes and no, as readily as a Pool, where they are its max and zero. That case arrived after this was written, and it is the one that would have paid for numbering them: a flag card resolves nothing to apply either action, which a `to` holding the ceiling could not have done.

**A binding the plugin cannot act on refuses the layout**, as a bad `columns` does and for §5's reason: `reset` is shared config the plugin itself reads, not a component's private business, so a missing or unknown `action` is a wrong shape rather than a typo to report in the editor. The pre-split `{ trigger, to: "max" }` is refused rather than migrated. Nothing has ever written this key, so unlike a hyphenated id there is no file in the wild the refusal could cost. An expression left beside `full` or `empty` is kept and simply not run, so changing the action in the editor and changing it back does not throw away what was typed.

**A trigger name that matches nothing is contents, not shape.** Whether `reset` is a binding at all is the file format's business and refuses the layout. Whether its `trigger` names one the layout declares is the library's, and follows §5's rule for a function that will not parse: reported in the editor where it can be fixed, while every sheet on the layout goes on rendering. The component simply binds to nothing and no button reaches it. The check cannot live where the rest of the binding is validated in any case, since a component is parsed without the layout around it and nothing at that point knows which triggers exist.

The same rule covers the declarations themselves. A blank name is dropped and reported, because a binding stores the name it matched and an empty one would match every component that set no trigger at all. A name declared twice keeps its first appearance and reports the second, since two buttons with one name could not be told apart. A declared trigger that nothing binds to yet is not a problem yet. That is what a layout part-way through being built looks like.

**A trigger applies what it can and names what it could not.** A Long Rest that resets three Pools and finds the fourth's `to` unresolvable leaves that one as it was, resets the rest, and says which one failed. This is §5's rule, that one failure must not take the sheet down, and being a button rather than a render does not earn an exception. Refusing the whole rest because one component is misconfigured is a worse answer than a rest that happened and reported a gap.

**Undo restores the note as it was just before the trigger, and declines if the note has moved since.** Between the confirmation and the undo the player can edit a field, and a restore that swallowed that edit unannounced would destroy more than it reverted.

This is the only place the sheet performs an action rather than holding values.

## 7. Layout editor

Until the grid canvas below ships, a form-based editor lives in a workspace pane of its own: create layouts, add and remove components, edit each component's shared and declared config fields, declare the layout's reset triggers, and write its function library. **The pane is a tree of everything the layout holds beside a panel configuring whichever one is selected**, and the tree's first row is the layout itself — selecting it puts the grid's column count, the function library and the trigger list in that panel, so there is one selection rather than two and the panel needs no chrome of its own. The two columns become one below a threshold derived from the panel's own working width, and the schematic then sits above the tree with the panel under it. Settings keeps two preferences and a button that opens the pane. A component that can act on a reset, meaning one implementing `applyReset` (§4.1), gains a binding of its own: which trigger restores it, which of §6's three actions it takes, and the expression where that action is `formula`. Components that hold no state are never offered one, so the field appears exactly where it means something. It renders forms from `configFields`, so it grows automatically as components are added. **Its add menu offers palette entries beside the bare types**, each entry indented under the type it prefills and its description shown below the row, and adding one writes an ordinary component the author then edits. Types stay on the list: an entry is a starting point rather than a variant with capabilities of its own, and an author who wants a plain Track has to be able to ask for one. The editor is a workspace view rather than a settings tab because an authoring tool needs width, undo scope, and a sheet beside it. **Two of those three arrived with the pane and undo did not**: nothing in the editor has ever had undo, every mutation writes immediately, and the grid canvas below should not ship before undo does.

A schematic of the grid sits above the forms, and the block is the control: drag it to move, drag its bottom-right corner to resize, arrow keys and shift+arrows for the same two things. `col` and `row` anchor the top left while `width` and `height` grow right and down, which is why one corner is enough. The other three would have to move a block and resize it at once, and moving is what dragging the block already does. Both gestures write the same four numbers the form shows, so neither is the real editor and the position fields are never the only way in. A block cannot be pushed or grown past the last column. One already out there, from a hand-authored file or a `columns` reduced under it, is left where it is rather than snapped back.

The full editor:

- **Manage layouts**: create, duplicate, rename, delete, import, export.
- **Grid canvas**: a responsive grid. Drag components in from a palette, move them, resize by grid units. The palette offers entries rather than types (§2): one type appears in it several times with configuration prefilled, as Table does under Inventory and Features and Card set under Currency, and dropping one in writes an ordinary component the author then edits (§13). Grid rather than free positioning, so sheets reflow to a single column on a phone instead of breaking.
- **Configuration panel**: select a component, configure it in a side panel. *Shipped with the pane.*
- **Function library editor**: define the layout's own functions.
- **Trigger editor**: define named reset triggers.
- **Bonus types**: declare the list a modifier's type is drawn from. *Shipped.*
- **Modifier editor**: declare the layout's named modifiers — a name, what each changes, whether it adds or sets, an amount, a bonus type and a condition — with a report under the list naming every definition the layout cannot use and why. *Shipped.*
- **Promoted fields**: choose which values, if any, mirror into frontmatter.
- **Preview**: render the layout with sample values while editing.

**A modifier definition may arrive from a character's sheet, and it is the first thing in this plugin that edits a layout from one.** A reader looking at a typed modifier on a row may name it and press **Save to the layout**; the definition is appended and the row becomes a reference to it. The order is the whole of it — **the layout write lands first, and only then is the cell rewritten** — so a refused or failed write leaves the note exactly as it was (Constraint 4). Four things refuse the name: blank, one that would not round-trip through a cell, one the layout already declares, and one that is not a usable definition. Other rows holding identical text are untouched; finding them would be the migration §10 declines to perform.

**Editing a definition moves every character on the layout at once, and there is no undo in this pane.** That is the tier's point and its exposure together: nothing is cached, so the change is visible the next time a sheet is opened rather than fossilised in notes. The sheet says so where it can — a row enrolled by name draws its fields read-only, with a line saying where they are edited.

Layouts are independent of one another. "DnD 5e Standard" and "DnD 5e Caster" are separate files, duplicated and diverged rather than inherited.

## 8. Sheet view

- Notes carrying `sheet-layout` open in sheet view by default.
- A command and a toggle switch between sheet view and plain markdown view, in the Excalidraw manner.
- Any stored value is editable directly in its component. Changes write back to the note body.
- Computed values are read-only.
- Wikilinks are clickable and navigate. Hover preview works, backlinks resolve, and renaming a linked note updates the sheet, all because links live in plain markdown rather than inside a code block.
- Reset trigger buttons are available.
- **A component fills its placement.** A card sized two columns wide occupies both, rather than holding a tile width and floating centred in the slack. The grid is the sizing control: an author who wants a small card places a small component, and a component that second-guessed the placement made the grid look broken wherever it disagreed. Card set's `fixed` sizing is the deliberate exception, and it is opt-in and still grid-derived, at one card per grid unit.
- **The grid fills the pane.** A sheet is a dashboard, not prose: its width is a column count the author placed components into, so reading width would leave a wide pane empty on both sides while squeezing the cards meant to fill it. The `--sheetsmith-sheet-max-width` custom property caps it for anyone who wants reading width back. Prose the view writes itself, such as the missing-layout notice, still holds that width.
- The sheet reflows to a single column on narrow panes, in grid reading order, top to bottom then left to right, regardless of the order components sit in the layout file. That order also drives tab order in the normal grid.
- **A container's children are read where the container sits, in the container's own grid reading order, before the container's next neighbour.** So the order is a depth-first walk with each level in its own reading order, which is the sentence above applied per level rather than once, and it is what a heading over a region promises: the region reads together. Both the single-column reflow and keyboard focus order follow it. **The exception is a container whose children have no placement**, such as a Tab set's tabs: there is no grid order to read, so both the strip's left-to-right order and the focus order through it are the order the layout wrote them in. ("Tab order" is avoided in these two bullets on purpose — it means keyboard focus order everywhere else in this document, and a Tab set gives the phrase a second reading.)
- **A container is its own reflow context.** A group four columns wide inside a wide pane is narrow even though the sheet is not, so its inner grid collapses to a column on its own width, by the same *rule* the sheet uses rather than the same number: a grid stops being worth having when its columns would fall under 40px, which is what the sheet's own 480px across twelve columns already says. So twelve columns collapse at 480px as they always did, and four collapse at 160px. Answering 480px for a container of any width was one number applied to as many questions as there are column counts, and it left a two-column container unable to place two children side by side at any pane width. A container also collapses whenever the sheet itself has, which its own width cannot tell it: once the sheet is one column every component has the whole pane, so a container is *wider* there while having less room to spend. This is also why the reflow is a container query rather than a media query, restated one level in — a media query cannot see a container's width at all.
- **Content a container has hidden is in the DOM, still laid out, and in neither order.** An inactive tab's panel is not tabbable and not announced, and find-in-page does not reach it — the one price of the bullet below, since the spelling that would keep find-in-page working (`hidden="until-found"`, on `content-visibility: hidden`) is the one that removes the content from layout, and a panel contributing no height is a panel whose appearance changes its container's size. It is still rendered and its formulas still resolved: hiding changes what the reader sees, never what the sheet computes, so a reset trigger reaches a component whether or not the reader had it open.
- **A container's inner grid is its placed size: `width` columns by `height` rows.** Both halves of the placement, not just the width. So an inner column is a sheet column and an inner row is a sheet row, and a child declared two wide and two high is the same size as the identical component declared two wide and two high outside the container. A container that holds alternatives gives each one the whole of that grid, so they are all the same box and none of them can be the tallest — and such a child has no placement of its own, which is the one exception to this bullet and the reason the next one has an exception too.
- **Hiding never changes a container's size, because the size is declared and not derived.** This is "a component fills its placement" read as the rule it always was: a container occupies the `width × height` it was given whatever it is currently showing, so switching between alternatives moves nothing anywhere on the sheet. It is also why a Group cannot collapse — a collapse is a component *ceasing* to fill its placement, which this bullet forbids outright, and what it produced was the placement's own space left as a hole (§13).
- If the named layout is missing, show a clear message and offer to pick another rather than failing silently.

## 9. Promoted fields

Optional, off by default.

A layout may mark specific fields to be mirrored into the character's frontmatter, making them queryable by Bases and Dataview. The use case is a party table listing every character's level and current HP side by side.

Nothing is promoted unless explicitly chosen, so a user who does not want this keeps frontmatter at a single key.

## 10. Data safety

Character data is the user's, and a layout edit must never destroy it.

- **Removing a component from a layout does not delete character data.** The section remains in the note and stops rendering.
- **Unmapped data is preserved**, never discarded. A section the layout does not map simply does not render, and the sheet stays quiet about it rather than reporting it as a problem, since a note carrying sections beyond its layout is ordinary rather than an error.
- **Renaming a component** offers to migrate matching sections in existing characters.
- **A malformed section shows an error on that component only.** The rest of the sheet renders and stays editable.
- **A section without a data block is empty, not malformed.** It renders editable exactly like a missing section, and the first edit writes the data block into the section, preserving any prose already there.
- **Hand edits made in markdown view** are picked up when sheet view reopens.
- **A renamed or deleted modifier definition leaves every enrolment where it is.** A note stores the definition's *name*, so a layout that drops one leaves the word in the cell, unresolved and unchanged: the row stops applying the modifier and the form says the layout declares no such modifier, with the stored spelling on screen as the thing the reader has to recognise as theirs. Nothing is snapped to blank or to the nearest name, and no search-and-replace across the vault is performed — that migration is the one §10 declines, on the rename rule above. This is the price of the reference model and it is the right way round: a stale name is visible and fixable, where a silently retyped one would have moved arithmetic on every character.
- **A bonus type a cell names and the layout no longer declares is rendered, not corrected.** The effect applies and contests as its own kind, the form carries the stored word marked as undeclared, and the layout editor's bonus-type field reports it. Until a typed modifier could carry an `as` clause, nothing stored ever named a type and this was a construction guarantee rather than a rule (§5).

## 11. Non-goals

Explicitly out of scope for v1, recorded so they do not creep back in:

- **Dice rolling.** Decided out. Delegate to an existing dice plugin if it is ever wanted.
- **Bundled rules content.** No spell lists, no item databases, no SRD import.
- **Level-up automation.** Requires a content database, which requires the point above.
- **Layout inheritance.** Layouts are independent files.
- **Importing from D&D Beyond** or other external services.
- **Shared or real-time multiplayer sheets.**

## 12. Build order

| Milestone | Delivers |
|---|---|
| **M1 Render** | Read a hand-written layout file and character note, render a read-only sheet |
| **M2 Edit** | Edit values in sheet view, write back to the body, round-trip safely |
| **M3 Formulas** | Expression evaluation, layout function library, computed values |
| **M4 Editor** | Grid canvas, component palette, configuration panel. The workspace pane, its tree and its configuration panel have shipped; the canvas and undo have not |
| **M5 Finish** | Reset triggers, promoted fields, layout export and import, mobile reflow, error states |

The order is deliberate. The file model is the hardest thing to change once characters exist, so it gets proven first. The layout editor is the largest interface investment and comes only once the thing it edits is known to work.

Within the milestones, work proceeds **component by component rather than layer by layer**. The shared contract in 4.1 comes first, then each component is taken all the way through read, write, and render before the next one starts. The layout schema assembles itself as components are added, rather than being designed up front against requirements not yet met.

Component order, chosen by what each one forces you to solve:

| # | Component | Forces you to solve |
|---|---|---|
| 1 | **Card** | The shared contract, the config and data split, fenced storage, read-only render |
| 2 | **Card set** | Multi-entry fenced storage, per-scope formula evaluation: the row scope Table needs, proven on a simpler component |
| 3 | **Pool** | Editing interaction, a formula-capable config field, reset triggers |
| 4 | **Table** | The markdown storage path, wikilinks, fixed versus open rows, per-row formula scope (mechanism proven by Card set) |
| 5 | **Track** | Discrete state, granularity below the stored unit, and a gesture over a run of targets rather than a single field |
| 6 | **Group** | Containment: a component that holds others, an inner grid that is the container's own placement, and one depth-first walk every reader of a layout shares |
| 7 | **Tab set** | Hiding that moves nothing, which is a container answering for its own height, and the one child whose placement is its parent's |
| 8 | **Rich text** | Reaching the app for something a component cannot draw alone, and what stands in where the app is not there — plus a box whose size is the placement and never the content |
| 9 | **Image** | Nothing new, which is the point: it extended Rich text's seam by one member and reused its storage rule, its box and its gesture. What it added was a *third* place a value can fail — the app, the browser, and the note — each needing its own message |

Table jumped Pool for the same reason Card set jumped Card: a skill list was wanted, and it is a fixed-row record block rather than a component of its own. Fixed rows shipped first, with `text`, `number`, `level`, `toggle`, and `computed` columns, and open rows followed on `openRows` and the claim rule rather than as a second component. `link` columns wait for some case that is not the inventory, which does not need them (§13).

`level` was not in the original column list. It arrived once the skill list was on screen and a spinner for a two-grade proficiency turned out to be the wrong control, then changed shape again, from a row of marks to one cycling control, because a set of checkboxes can express states the value cannot. Both corrections came from looking at a rendered sheet, which is the argument for building a component all the way through render before starting the next.

Pool followed, and inherited two things: the editing gesture already shared by cards and cells, and a function library its `max` can call. The library was built before it rather than after, since a formula-capable config field written against a half-finished engine would have been written twice. It shipped without its reset binding, which was at the time the one thing on its §4.2 entry it did not implement. That was deliberate. Reset triggers are a layer across several components rather than a part of any one of them, and a Pool that renders is what the trigger machinery gets to be built against. The split cost one thing worth naming: `applyReset` and `reset.to` were absent from the component until that layer landed, so the contract's rule that declaring one implies the other held vacuously in the meantime.

Reset triggers followed it rather than arriving inside it, and that split is worth recording because the build order says component by component. A trigger is not a part of any component. It is declared once per layout, drawn once per sheet, and applied across several components at once. What belongs to the component is only `applyReset`, and that turned out to need the binding rather than a finished value. A caller that could compute "full" would have to know a Pool's max from a Track's count, which is the per-type knowledge the contract exists to keep out of it. So Pool shipped first without a binding, and the layer went across it afterwards: the trigger list on the layout, the binding in the editor, the buttons on the sheet, and the batched write underneath so a rest is one write and one undo rather than one per component.

Its one surprise was that the max could not be character data. The §3.1 example had stored one since before `max` was a formula field, and the two could not both be right, since a stored copy of a derived value is the thing Table's columns already refuse.

Its one reversal was the typed amount, and the lesson generalises past this component. `-17` reading as a change was cheap, needed no new control, and matched what a player says at the table. Every argument for it was sound, and it still had to go, because a field that holds both a value and an instruction cannot tell them apart and neither can anything reading it. The three defects in §4.2 were all downstream of that, and none was findable by reasoning about the convention: each turned up by driving the rendered card and watching what it committed. **Where a control's input is not its outcome, the outcome has to be on screen before it is applied.** The drag and the held button already followed that rule, and the typed route did not.

Card set (built as "Abilities", then "Stat group" until §13 named it for its shape) was not in the original order. It jumped the queue on demand once Card worked, and looked at the time like a replacement for it, so Card was dropped and then rebuilt on top of the set's card once the standalone numbers turned out to want a component of their own. The detour paid for itself. It forced the render contract to grow a per-scope field resolver, which is the same mechanism Table's computed columns need per row, discovered while the codebase was small, and it left a shared card module for the Card to render through.

Track was scheduled as "a simpler Pool", and that was right about the machinery and wrong about the component. What the two share is a ceiling, a debounced write, and a gesture that moves a draft: real reuse, and none of it visible on the card. What separated them was one question the schedule had not asked, which is what the number is *for*. A pool's is a quantity, so it prints its numerals and draws a bar to save the reader the division. A track's is a count of discrete things, so its segments are already both the count and the proportion and the card carries no numerals at all. The ceiling's name followed from the same question, `max` for a quantity and `count` for a run, and so did the mark, which exists because a run can be graded below its own unit and a quantity cannot.

Its real value was being the reset layer's second implementor. That layer was designed against Pool alone, and this is the first evidence it generalises. `applyReset` took the binding unchanged, and the two cases it exposed were both ones the contract had already made room for: `full` needs a resolved `count` and fails exactly as a Pool's `max` does, which is what `ResetResult` exists to carry, while a run whose steps are named cannot fail at all, because naming them settles the length.

The one thing the contract could not express was the publication. The bare id has to be the filled segments a reader can see and `<id>.value` the stored marks, and `ScopeEntry` could say "this stored value" or "this formula field" and not "this number computed from the data". So the component restated `value` as a named entry and relied on the name table registering `named` after `self` to overwrite it. It worked, and a test drove it through `buildSheetScope` rather than through the declaration, so a refactor of that order would have failed loudly. But it was a workaround for the shape of the contract, and Track was the second component to want a computed publication and route around it; Table's declared rows were the first, which is what made it evidence rather than a second problem.

`ScopeEntry.compute` is what settled it, and Track was the case that chose the mechanism over the alternative branch — a declarative entry can name a formula field and a scope of formula fields, and it still cannot say `floor(value / marks)`. So the workaround is gone: the entry states the marks as its stored value and the filled segments as a computed one, under one name, with no restatement and no dependence on registration order. The row set gets the same correction one level down, where it had been publishing segments under both `slots.L1` and `slots.L1.value`, which was wrong on the second name. The test kept both of its assertions and lost only the comment explaining why the order mattered.

One correction came only from driving the gesture. Leaving the run and pushing past its end are opposite instructions, the first abandoning the pending outcome and the second being where the run gives a few pixels and holds, and they look identical to a hit test that asks "is the pointer inside the control". Written that way, the boundary resistance was unreachable: every drag that reached an end was reported as having left. Leaving is vertical, and an end is horizontal, and neither sentence in the component's own spec says so because each is obviously true on its own.

The remaining one is a variation on problems those solve: Computed is a value-less card fed entirely by a formula. Rich text was scheduled as the third of that group and turned out not to be a variation on anything: what it forced was a seam nothing before it had needed — how a component reaches the app for something it can only draw with the app's help, and what stands in when the app is not there — settled on `LinkContext`'s own terms as an optional `RenderContext` member, so the component layer still imports nothing from `obsidian`. Its second lesson was that "barely touches the formula system" was the wrong axis to schedule it on. What made it interesting was the *box*: it is the first component that would have been tempted to size itself to its content, and §8's "a component fills its placement" had never been tested against something whose content has no natural height. Image shipped beside it, specified in the same pass and coupled by one decision neither could take alone — Image refuses external URLs because Rich text carries them, under the app's own settings and the app's own disclosure rather than through a request this plugin makes.

**Image is the entry that says whether the seam was designed or merely built**, and the answer is that it cost one member. `resource` sits beside `link` and `renderMarkdown` on the same terms, the view supplies it from two calls it already made, and nothing else moved. What it did force were two corrections to work that looked finished: the whitespace framing both markdown-storing components need went from private to `parse/markdown-body.ts`, because two copies of *where the text starts* is the drift Constraint 3 exists to prevent and a guard test could only assert they still agree; and the grid-row token was renamed off Rich text's name, because a reader raising it to give backstories more room would otherwise have silently resized every portrait on the sheet. Both are §1's one-step tier, and both were invisible until a second consumer existed — which is the argument for building component by component rather than designing the shared parts up front.

Its own lesson is about *where* a value can fail. Every component before it had one failure surface, the note. This has three — the note (a body that is not an embed), the app (a target the vault does not hold), and the browser (a file it cannot draw) — and each needs a different message, because each has a different fix: write the bracket form, change the filename, use a different file. The prior art is what made that worth designing rather than discovering: every image failure in two trackers is a resolution failure and every one of them is silent, split between plugins that logged where the reader was looking at an empty box and plugins that said nothing at all. So the rule this entry adds is **report what happened, never what you predicted** — the plugin holds no extension list, asks the app whether the file exists and the browser whether it can draw it, and a test scans `src/` for a list rather than trusting the absence of one. Toggle was a fifth until it turned out to be a Track of one segment (§13), which is the catalog's third correction of the same kind and the first one taken before the component was built rather than after; Field was a fourth, and "a simpler single-value card" turned out to be the literal answer rather than a description — it is a Card, and what it wanted that Card lacked was one config field (§13). That is the catalog's fifth correction of this kind and the second taken before the component was built.

Table's contract was worth writing early even though it was scheduled fourth, because it is the component most likely to expose a flaw in the shared contract, and that is cheapest to discover while few components depend on it.

The aggregate over a table's rows came after all five, and what it exposed was in the *formula* layer rather than in a component: the three field-resolver factories had been growing a trailing parameter per sheet-wide thing a formula could reach, and were at five before this feature made it six. That is what building component by component defers rather than avoids — each component asked the resolver for one more thing and each was right to. The correction was an environment object, and it paid for itself immediately: the aggregate needs the name table and the row table to be *mutually* lazy, since a published name may hold an aggregate and a row's computed column may read a published name, and neither could have been passed to the other as a positional argument at all.

Its own surprise was smaller and is worth the sentence, and it took two goes to get right. The re-entry guard on a row set had to refuse the whole walk rather than the attempt that re-entered it: refusing only the inner attempt terminates just as well, and leaves the outer sum succeeding over rows the offending column is merely absent from — so the cell shows a number, and the same table read from anywhere else does not. One row scope exists so a cell and a published name cannot disagree about what a row says, and a guard that reported "no" downstairs and "yes" upstairs would have reintroduced exactly that. The second go was that "the whole walk" is the whole *cycle*: written against the self-summing column, the guard marked the one walk that was re-entered, which is right when there is only one and wrong the moment there are two tables each summing the other. Then the end that was asked for first is refused for ever and the other is held as a complete row set with a column missing, and which card breaks is decided by grid order.

The third go was the one worth the paragraph, because the first two corrections caused it. Marking the cycle is right; *keeping* the mark is not. A refusal held against a component rather than against the walk that found it condemns the coarse edge above — which is not a cycle at all — and takes every unrelated aggregate over that table with it, in one evaluation order and not the other. The same mistake was one layer up in the name table, which cached the `undefined` a transiently-refused thunk produced. Two guards and a memo, each correct against the case it was written for, composing into a sheet whose arithmetic depended on which card drew first. **A guard is about one evaluation; a cache is about an answer. Neither is about a component, and a failure is not an answer.** The check that finds this is not reading the guard — all three readings looked right — it is driving the same cycle from both ends and comparing, which is now what the tests do.

The containers came last, and Group is the entry worth reading twice, because what it teaches is about the *order* rather than about containment. It landed alone and read as thin — a name for a region, an inner grid that reflows on its own width, twelve cards that relocate by moving one block — and the reason is that it is the support and Tab set is the payoff. Building the support first is what §12's own rule asks for, and the cost of that rule is a component that looks like it was not worth having until the next one arrives.

Its correction is the largest this section records, and none of it was reachable by reasoning about the code. Group shipped with a `collapsible` heading: every test passed, the control was accessible, its state survived a rebuild, and the disclosure was drawn the way `docs/UI.md` §7 asks for. What the harness showed was a one-card group closing beside a group four rows tall and the sheet not moving — a hole the exact height of what had just been hidden, because grid rows are sized by the tallest thing spanning them — while the same control on the tall neighbour moved everything below it. So the defect was not in the control. **A component fills its placement** was already §8's rule, and a collapse is a component ceasing to fill its placement; what the grid then showed was that rule being broken rather than a quirk of row bands. The corollary is what put hiding on Tab set instead: **a container's size is declared and not derived, so hiding must never change it.** A tab set goes on filling its `width × height` while it hides, because every tab is the same box; a collapse can only stop filling it. The withdrawal also fixed something the build had wrong on its own terms — an inner grid was `width` columns with implicit rows, so a container's declared `height` did nothing at all, and a child two rows high inside a group was not the size of the identical component two rows high outside it. An inner grid is the placement, both halves of it.

Four of the corrections recorded above are the proficiency spinner, the typed amount, the drag that could not reach a boundary, and the collapse. All four were found by driving a rendered component and none by reasoning about the code, which made "look at it" the most productive rule in this section and also the most expensive one to follow, since looking meant launching the app. It is now a harness that builds the sheet, the layout editor pane and the settings tab outside Obsidian against the real stylesheet, described in `CLAUDE.md`. It is development tooling and ships with nothing, but it belongs in the build order because it is what the next component's corrections will come from.

## 13. Open questions

- **Whether a set of runs is a second component rather than a config field.** Track takes `rows` and stays one component, on the grounds that a run and a set of runs differ only by a name beside each run. The catalog's own precedent cuts the other way, since Card and Card set are two components differing by about as much. The cost of the choice is a config form with two mutually exclusive pairs in it, `count` against `levels` and `rows` against `levels`, both enforced when a layout is read rather than by the shape of the thing.
- Whether a character may override a single formula locally without forking the whole layout.
- **How deep a published name may go, and what a Track's rows publish across themselves.** A Track's row set publishes `slots.L1`, and its ceiling would be `slots.L1.count`, one segment past what `<id>.<name>` reaches. That is not a gap in the mechanism the resolved entry below settles: `compute` changes how a name's value is produced, not how many names deep a component may go, and `isName` refuses a dot in a published key on purpose, because a third segment collides with the `.value` every entry already answers to. Partitioning that suffix namespace is the actual question, and nothing yet needs it badly enough to answer it. The aggregate across the rows is a different half and is no longer blocked — the resolved entry below settles it, and a component that computes its own published value can sum its own rows besides — but what a slot card should call it, and what "left" means on a run whose `sense` is harm, is undesigned rather than unreachable. So "how many slots are left" still cannot be written, and it is the first formula a slot card invites.
- **Whether a tracker belonging to a scene or a party has a home here.** A Blades clock, a 2d20 momentum pool and a Cortex doom pool are trackers the whole table reads, and none of them belongs to a character. Track lives in a character note because every component does, and §11 rules out shared sheets. A clock on a GM's own note is a single-player question rather than a multiplayer one, though, and it is the most common tracker the catalog currently cannot express.
- **Whether the two runtime cycle guards should know about each other.** A ring that runs through a published name can be closed by either the sheet-wide name table's guard or the row table's, and which one catches it is decided by which end a formula reaches first. Entered at the name, the column reading it goes unresolved and every aggregate over the table's other columns is fine. Entered at the rows, the row table refuses that whole walk, so a card holding an aggregate over the table and drawing earlier shows `?` where the identical formula on a card drawing later shows the number. Both catches are correct in themselves and the outcome self-corrects on the next evaluation, so what it costs is a `?` whose appearance depends on grid order. Closing it means the row table letting a walk complete where the ring passed through a name thunk and refusing it only where the ring is entirely its own, which is a coupling neither guard has and which the aggregate deliberately did not add (§5). Recorded here because the alternative is a reader rediscovering it from the guard's code, where all three readings of the rule look right.
- **Whether a Track ever renders as a clock face.** Left out for the reasons in §4.2, and recorded here because the file model does not care either way, so it stays a decision that can be taken later without a migration.
- **Whether a card's options may come from somewhere other than a literal list.** `options` is a value and never an expression, which is what makes it decidable that it is not in `formulaFields` (§4.2). The demand is real and was granted in the closest analogue: two independent Custom System Builder issues thirteen months apart (#81 in 2022, #271 in 2023) asked for a drop-down's choices to come from a dynamic table's column, a third (#528, open) wants a reusable lookup list feeding several, and the wiki now documents three sources — Custom, Dynamic Table, and Formula, the last returning an array "e.g. from `lookup()`". Across systems it is the same shape: Lancer's mounts follow the frame, a Blades playbook's friend and rival come from that playbook's own NPC list, a 5e subclass follows the class. **It is deferred rather than merely unbuilt, and by a decision already taken**: a formula source needs an expression that evaluates to a list, and the aggregate entry below refused a collection value outright and gave the local reason — a value here is one typo from `applyReset` writing it into a note. A rows source needs a component reference in a config field, widening the exception §5 states is "the one position in the language where that is true" from one argument of one builtin to a config key. So this waits on whichever of those two is reopened, and neither is reopened for this.
- **Whether Table gains a `select` column type.** Out of scope where the entry below settles the card, and open rather than refused, because the *model* half is settled by it and only the editor's shape is missing: a select cell would store the option's `value`, hold no default, render a stray value rather than correcting it, join `text` in the types a total is refused on, and join the publishable ones for the reason the entry below gives. What it has no home for is the options list itself, which is a list inside one row of `columns[]`, which is a list inside a config field — and `list-fields.ts` renders records whose cells are scalars. **The surface half of that is now answered and the field-kind half is not.** What the sentence above names is two things: a field kind — a list whose cells are themselves lists — which lives in `list-fields.ts` and is unaffected by where the editor is drawn; and the fact that there was nowhere to *put* such a field, a nested disclosure inside a row of a columns table inside a settings-width control column having no room to be legible. The second was a fact about a 620px settings pane rather than about the field kind, and the editor pane's configuration panel has the room the settings tab did not. So this is blocked on the field kind alone, which is a smaller question and a different one, and it is still an editor feature rather than something to smuggle into a component. Two smaller things wait with it: `COLUMN_TYPES` is ordered and its own header records that the order decides the default, and a control in a cell has to carry row identity, which is the defect Custom System Builder #351 reports on exactly this control — a drop-down working inside a dynamic table with no per-row default and "when selecting an option for one of the rows it will often change the selected option in other rows". A `level` column already covers a *graded* choice in a cell, which is the only cell-level choice the catalog has actually wanted so far.
- **What a string type in the expression language would unlock, and whether the first thing it unlocks is worth it.** Recorded when Rich text shipped publishing nothing, because that decision is a *consequence* of §5's language having no strings rather than a judgement about prose. §4.1 names "a block of prose" as the case that leaves `scopeValues` off, and the closest analogue disagrees — Custom System Builder's Picture requires a key, can be used in formulas, and may take a default that must "resolve to a picture path in the end". The disagreement resolves on a fact rather than on taste: the tokenizer "has no quote handling at all", so a published path or a published paragraph could be compared to nothing, concatenated with nothing, and handed to no builtin. It could be published and never read — and it could be *written*, which is the argument against publishing it at all: a Pool whose `max` names a portrait clamps its bar against a file path and restores to one, which is §4.1's own warning with a path in it. So what is deferred is one decision, not two. **What it costs, stated so it is not rediscovered as a gap:** a layout cannot say "show the portrait the class card names", cannot compute a path, and cannot vary a symbol by a stored value. Rich text and Image are the first entries to revisit if the language gains strings, and the aggregate's refusal of a collection value (below) is the sibling question — a string type and a list type are the two the grammar declined for the same reason.
- **Whether the render seam should grow an `editMarkdown` member.** Rich text's field is a plain `<textarea>`, so it has none of Obsidian's own editing machinery: no bracket auto-close, no list continuation on Enter, no `[[` suggester. That follows from §4.2's "the sheet's own stacked edit, not a second editor" and is recorded as a cost in the feature doc rather than as a defect. **Only the suggester actually waits on this question**, which is the correction an attempt produced: bracket closing and list continuation need nothing from the app, and `bindMultiline` is in `interaction/`, so the component boundary this question first leaned on never applied to them. The suggester needs the vault's filenames and nothing local can invent those, and it is the one that bites, in the one component built around wikilinks being live. Three ways to answer it and the trade is genuine: keep the textarea, which is free; run an owned CodeMirror 6 instance, where `@codemirror/*` is already a build external and bracket closing and list continuation are a small extension set — but Obsidian's own extensions, editor settings, theming and suggester are all absent, so it is a second visibly different editor inside the app, which is the thing §4.2 rejected on principle, and `EditorSuggest` cannot help because it binds to Obsidian's `Editor` and not to an element of the plugin's; or reach for the app's internal embedded editor, which canvas cards and callout editing use, which gets everything including the suggester and is undocumented, unsupported, version-fragile and a plugin-review risk against the developer policy `AGENTS.md` carries. **The architecture already answers where it would go, which is the good news.** A component may import nothing from `obsidian` beyond `setIcon` — `components/isolation.test.ts`'s `FROM_OBSIDIAN` allowlist, with its reasons in `PATTERNS` §2, and not Constraint 5, which scopes `parse/` and `formula/` — so an editor cannot live in the component whichever option wins. It would arrive as a fourth `RenderContext` member on `link`'s terms, exactly as `renderMarkdown` did. The seam this feature spent its design budget building is precisely the mechanism that would carry an editor later, and nothing has to be undone to get there. A follow-up feature with its own spec, not a fix to that one.
- **Whether a bonus type the layout does not declare should be refused on the card as well as reported in the editor.** **Amended: the stated reason is no longer true.** It read that the check "is handed a config and never the layout, so no component can see the declared list" — true while the type lived on a column, and false now that a typed part carries its own `as` clause: the type arrives in a *cell*, the form holds the layout's declared list, and it already draws a stored type it does not recognise as `<type> (not declared)`. So the sheet does say it, on the surface where the word was typed. What is still open is the *card*: a number pushed at by an undeclared type computes as though the type were declared, and nothing beside the number says so. The original entry's remaining substance follows. Every other refusal a modifier column earns lives in the component's own configuration check, and this one cannot: that check is handed a config and never the layout, so no component can see the declared list. It is reported by the layout's own parse of `modifierTypes` and surfaced in the editor's bonus-type field instead, so the *editor* says it and the *sheet* says nothing — a layout carrying an undeclared type computes as though the type were declared, which is arithmetic that is right for a reason nothing on the sheet states. **The sheet half was never established as impossible**, which is why this is open rather than closed: `RenderContext.modifiers` already carries sheet-wide knowledge a component cannot reach for itself, and the declared list could ride the same member. What that costs is one more thing a component knows about the layout, on a member added for the accepting set. The feature doc's criterion 12 is deliberately unticked and its text unchanged, so whichever way this goes changes what that criterion should say rather than being read back into it.
- **What a card should say when a modifier table will not configure.** A table refused by its own configuration check publishes nothing and pushes nothing, so **every bonus it was pushing silently withdraws** and the cards it was modifying show plausible wrong numbers with no mark. The table itself says it is broken; nothing else does. **The precise fix is impossible rather than large, and that is the valuable half of this entry**: a table refused by that check never read a row, so neither side knows which target names it *would* have named — the component has no rows and the sheet has no pushes to miss. So the exact "this number is missing a bonus" cannot be drawn from either end. What is buildable is a sheet-wide caution, with false positives by design: any card reading a slot could be marked whenever any modifier table on the sheet is broken, which is right for the ones that lost a bonus and wrong for every other. Half of it shipped — the table's own error box now names the consequence in a sentence, so a reader fixing the table is told that numbers elsewhere come back with it — and the marking half is what is open.
- **What `.sheetsmith-list-scroll`'s height cap is for.** A modifier column puts seven controls on a column's detail line in the layout editor, so the line wraps and a four-column table exceeds the columns list's fixed `20em`, clipping between a column's row and its options — which reads as an absence rather than as an overflow. `docs/UI.md` §12 holds the measurements at both widths and the reason it was not fixed in the pass that found it: the cap is shared by every list field in the panel, and it carries no comment saying what `20em` was chosen against. Recorded here rather than only there because it was **expected to be superseded**: the authoring surface above replaced the two columns that overran the line. **Amended, half answered by deletion.** The instance is gone — a modifier column's detail line is one line again, and the columns list no longer overruns — but the cap itself is untouched and still carries no comment saying what `20em` was chosen against, on a class four list fields share. The sheet's own anchored panel deliberately did **not** reuse it and states its own cap as a measurement instead, which is the shape an answer here would take.
- **Whether the layout editor's configuration panel has a copy budget.** The panel is now teaching a stacking-rules system through field descriptions and footnotes: what a target column is, that the target's own formula has to read the slot, that one type's best bonus and worst penalty apply, and which values this layout takes a modifier for. Each line is individually justified — §4.1 requires a description, and this document's own rule is that a description states the consequence — and together they are the largest block of prose in the pane, twice over: one round of review found the same 141-character sentence on screen twice, about 340px apart, and cutting it took two rendered lines off a description that still runs to five. **Also expected to be superseded**, since a popup with four named fields is where an explanation of a modifier would live instead of under a columns list. Recorded so the next surface is designed with a budget rather than inheriting the absence of one.
- **Whether an unnamed two-state control says "Yes" or "No" to a listener, or lets `aria-pressed` say it.** `stored-flag.ts` holds the reading as policy and neither component that draws a flag reaches it: a Table computes it for a toggle cell and takes neither branch that would carry it, since `aria-pressed` holds the state and `aria-label` is the column and row, and a Track guards both its call sites on `levels` being set — where a named level says itself and the reading is not wanted. So the flag branch is only ever taken to be thrown away, which is a policy with no application rather than a coverage gap, and it is why the reading is the one member of that module `PATTERNS` §10's condition cannot hold. Both answers are defensible and that is the whole of the question. **Against saying it:** `aria-pressed` is the platform's own word for exactly this, every screen reader already reads it, and a custom "Yes" beside it is a second name for one state — which is the argument the two components' comments already make, and if it is right they are not dead branches but correct ones with a dead helper behind them. **For saying it:** a ring with no level names is a shape with no reading, and "pressed" is a word about a button rather than about the thing the flag holds. Recorded rather than taken because deleting an export across two components ships behaviour either way, and because the two comments arguing it are the closest thing to a prior decision and were written per component rather than as a rule. `PATTERNS` §11 holds the code half.

- **Whether a modified number's mark should follow the narrow set while the picker keeps the wide one.** A breakdown is offered wherever a name accepts a modifier, and that set is two rules ORed: this component's own formula mentions `mod.self`, **or** any formula anywhere mentions `mod.<name>`. Only the first can make a value move, so a card on the wrong side of the OR draws the dotted mark and lists contributors while its number never moved. The value itself no longer lies — the total line prints the number the caller drew — so what is left is a *listed contributor with no effect*. The sharper predicate is already computed; gating on it would change which cards draw a mark at all, which is wider than the finding, and the picker and the editor's report must keep the wide set because they are about what an author *could* wire. `docs/UI.md` §12 holds the measurement.
- **Whether the anchored panel should follow the vault's text size.** The panel hangs off `document.body` and sets `font-size: var(--font-ui-small)` on itself, so neither the sheet's inherited size nor the reader's **Text** setting reaches it: measured 390 x 479 at both the default and `text=24`, beside a sheet that grew 650px. That is Obsidian's own regime — every panel the app draws is `--font-ui-*` — and §1's ban on a type scale of this plugin's own is why it was not made to follow the sheet. What is open is whether a reader who enlarged their sheet should meet a panel at the app's UI size, which is a question a screenshot can put and prose cannot; `harness/shot.mjs` now renders it.

Resolved: **there is no Field component. A Card gains `options`, and declaring any is what makes it a dropdown.** §4.2's Field entry is withdrawn. A labelled text or number value was already a Card with its note hidden — no new code, no new type — and the only thing Field carried that Card did not was a closed set of choices, which is one config field. Asked the question the entry above asks of a palette entry, in the form §12's rule puts it: name in one sentence what Field has that a Card does not. Nothing survived the sentence. It is the catalog's fifth correction of this kind, after Abilities became Stat group, Skill card became Table, Toggle folded into Track and the card pair was renamed, and the second taken before the component was built.

**The evidence cut both ways and the load-bearing half is which key was added.** Against folding: three independent catalogs split this category rather than merging it — Custom System Builder ships Text field, Number field, Drop-down list, Radio buttons and Checkbox as five entries of seventeen; Sandbox System Builder has Simple Text, Simple Numeric, List, Radio Buttons and Checkbox as five property types of ten; Meta Bind names twenty-one input field types. Not one of them ships a single field entry with an input-type setting, and the one counter-shape, Notion, is a database rather than a sheet builder. So SPEC's Field entry, one component with `input` as a config field, was exactly the shape nothing examined ships. **That objection is answered by not adding `input`.** What Custom System Builder's own two fields diverge on is the argument in miniature: its text and number fields share `key` and `label` and then split over allowed characters and maximum length against decimals, bounds, relative modification, increment buttons and a slider — and a Card has none of those on either side. Here text and number are already one control that reads its own content: §4.2's arrow rule steps a value that is a number and moves the caret in a value that is not. So the fold adds `options` and nothing else, and the merged configuration form the prior art warns about never exists. That is the Toggle fold's rule applied to a control rather than to storage: the thing follows from what the layout declared, and a flag beside it saying the same thing again would be an authored fact disagreeing with an authored fact.

**A chosen option stores a declared value, not its label and not an index.** Four tools converge on the first — Custom System Builder ("you can only reference the value of the key in formulas, it's not possible to do so with the Label"), Meta Bind (`option(bad)` stores the text, `option(1, bad)` stores `1`), Roll20 (the option's `value` attribute, read by a sheet worker as `eventInfo.newValue`), and Notion (an option carries both an `id` and a `name`, and "the name and color of an existing option cannot be updated"). The index is the strategy nobody else uses, and it is the one already in this codebase, on a `level` column. **So the plugin now holds two storage strategies for one control, and that is right**, because the two are not one control: a level is *ordered and graded*, so its position is its arithmetic — `Training * prof` covers untrained, proficient and expertise in one expression precisely because 2 means twice 1 — while an option is unordered, so its position is display order and storing it would move every note the moment the list was reordered. Every builder holding two dropdowns splits them by *control*, a dropdown against a radio group, over one storage; this plugin does the opposite, one control over two storages, and the opposite is the better axis: a control is a rendering and the file is the thing that has to survive. It is also the split this catalog already made one level down, where a `level` column and a `toggle` are one control storing an integer and a yes.

**What made the key-and-label split load-bearing here is local rather than borrowed.** The expression language has no string literals, refused with the aggregate below on the grounds that adding quote handling so one argument could be quoted is a permanent tax on the grammar. So a value a formula can do anything with has to be a number, and a dropdown storing words publishes something nothing can compare or add to. The split is what lets an author put the arithmetic in the value — which is precisely what users asked the closest analogue for, in #423: "there is no option in the Dropdown to add a value for each of the options in the Dropdown", wanting a training level worth +2, +4, +6 or +10. What it costs is #312 in the same tracker, "I want to show the dropdown list label (not key)... but only show key. Is it possible to show the label?", which is structural in that tool and structural here: **a label is unreachable from a formula**, and §5 says so rather than leaving it to be found.

**A select value publishes, and §4.2's refusal to publish a `text` column does not reach it.** That refusal is not about text: it is about a cell whose display and storage can disagree with nothing to say which the name means, "sword" over `[[Sunblade|sword]]`. A dropdown's two halves cannot disagree, because the layout wrote the mapping down — the value is the meaning and the label is its presentation — so the name is worth the value, and it needed no new machinery at all: a Card already publishes its stored value under its bare id, and a card with no `derived` already has those two answers be the same thing.

**What a Field would have got wrong is the note line, and that is the argument the prior art gave for free.** Across game systems the demand is not a bare dropdown: in Blades in the Dark, heritage, background and vice are each a closed choice plus a written line — "Choose a vice from the list, and describe it on the line above with the specific details and the name and location of your vice purveyor" — and the detail is where the content is. "Ore miners, now war refugees" is the heritage; the listed option is the bucket. The component that already holds a value and a note line is Card, so the fold puts the choice where the line already is, and a Field built beside it would have shipped the choice without the line and then needed a second component under it. The **Dropdown** palette entry therefore prefills two placeholder options and does *not* prefill `hideNote`. It earns its place on §4.2's rule the way Checkbox does: the job is one field away, and nobody wanting a dropdown looks for a component called Card.

**The option's two halves are spelled `value` and `label`, not `key` and `name`.** A Card already has a `key`, which names its entry in the fenced block, and a second `key` on the same component meaning a stored choice is one word saying two things — the exact defect the card pair's rename was taken to fix, where "group" was already the catalog's word for a container. The cost is that the editor's `{ key, name? }` list field, which is otherwise the field this wants, has to be parameterised over the two property names and the two headings it prints, rather than reused as it stands. One side-effect worth recording: that rename entry's list of names already taken cited **Number** as "a Table column type and a Field kind", and half of that reservation lapses here.

**The storage is a consequence of the length, and refusing to make it a config field is the load-bearing half.** A declared `storage: boolean` — or an `asFlag` flag — is the obvious alternative and it is worse than the two mutually exclusive pairs the row-set entry above already records as a cost. Those two are an authored thing disagreeing with another authored thing; this one would be an authored thing disagreeing with a *number*. A flag turned on beside `count: 6` has no reading at all, and a flag left off beside `count: 1` writes a count for a control with two states, and either way the author is being asked to hold a fact the layout already states. So a flag card is one the layout *describes* as one, and there is nothing to keep in step.

**Declared, not resolved, and per card rather than per run.** Both bounds were chosen against a case that is reachable. A `count` written as an expression is never a flag even where it resolves to 1, because `level - 4` is 1 for a fifth-level character and 3 later, and a spelling that followed the resolved number would rewrite how a note is spelled the moment somebody levelled up. And the card is the unit, because a set of spell slots takes its last row's length from the component's `count` fallback: per run, `count: 1` on a slot card would write `L1: 2`, `L2: 1`, `L3: yes` down one fenced block, and one spelling per card is what a hand-editable note needs. What the per-card rule buys is the checklist, which is a card *all* of whose rows are one segment.

**Both spellings are read on a run of any length, and that is what makes the fold safe.** A layout raising a flag's `count` from 1 to 3 would otherwise turn every note it had written into an error card, since Track reports a value that is not a number as a malformed section. So `yes` on a ten-segment run reads as one mark with its first segment filled, and a count on a flag card reads as ticked or clear, and neither is corrected — §7's rule that a stored value outside the run is rendered rather than fixed already covered exactly this. The component owns the coercion: the fence keeps values as raw strings on purpose, and the expression language has no numeric meaning for yes and no anywhere else.

**A flag draws the level ring and never a checkbox**, which is §4.2's `level`-against-`toggle` ruling applied one level up: a card and a cell doing the same job must not measure differently under the same finger, and a native checkbox has none of the ring's hit target, coarse-pointer sizing or press feedback. The ring's own gestures come with it and the run's do not — the drag, the mark-level hit test and the give at either end all exist because a run has somewhere in between to be, and a flag does not.

What it costs. **`sense` is inert on a flag**, and honestly so: harm grades a run from its first segment to its last, and a run of one is its own last, so both senses land on the same colour. The alternative is a colour that says "bad", which the pool's boundary rule refuses outright for a plugin that knows no game. **`count: 1` is now a load-bearing literal**, so an author who writes it as `1 * 1` gets a different note format from one who writes `1`, and nothing on the card says which they have. **A flag publishes a boolean where a run publishes a number**, so `10 + exhaustion` works and `10 + inspiration` is an error — right in both cases, and a difference between two cards of the same type. And **an unset flag publishes `false` where an unset run publishes nothing**, which is the answer a two-state control has to give and is an asymmetry inside one component; whether a blank run should publish 0 is a separate question nobody has needed answered.

Resolved: **a container may hold containers, one level deep, and tabs are a second container rather than a display mode of the first.** A Group's `children` are placed on the group's own grid, which is the group's width in columns by its height in rows; a container inside a container may hold only leaves, and a third level refuses the layout in `parseLayout` (§4.1, §4.2, §8). The planned `display` field taking stacked, collapsible or tabs is not added, and neither is the `collapsible` boolean it would have replaced — **hiding belongs to the container that answers for its own height, which is Tab set and never Group.** So §13's six-up "card beside its skills" block, which the five-blocks entry above named as the one waiting on this bullet, is an outer Group of six Groups each holding a Card and a Table.

Depth 2 is the branch, and it beat both neighbours. **Leaves only** was refused because it answers the only arrangement this bullet ever named with "spell it differently" — one Group of twelve leaves, letting the inner grid do the pairing that was the meaning. **Unbounded depth** was refused because no tool in the comparable set documents or enforces a limit, so it is undefended rather than argued for, and the defect record says exactly where the cost lands: across roughly forty Custom System Builder issues the nesting ones are the severe ones, and #425 is the whole trap in one — moving a complex panel of nested panels freezes the sheet and then the entire browser, F12 included, the template is unrecoverable, reopening "triggers the same freeze every time", one incident cost nearly two hours, and the reporter's workaround is duplicating templates as manual backups. Alongside it, #503 has editor CSS cascading into child panels and #536 has alignment failing only inside a tabbed panel. **Nesting fails in the editor, not in the rendered sheet**, and there is not one tab-specific defect in the set — nothing on tab state, default tab, tabs on mobile, or tabs and printing. That is a direct warning about the M4 grid canvas, and the argument specific to this codebase is that bounded depth is what keeps `preview-grid.ts` unchanged: `clamp`, `lastColumn`, `describeCell` and `findOverlaps` each take a flat component list plus a column count, and a container's children *are* a flat list plus a column count, so the schematic is that same pure module called once per open container rather than a tree-aware rewrite of it.

**The refusal is the layout parser's**, and that is a decision rather than a detail. `children` becomes shared config the plugin itself reads, the category §6 already puts `reset` in beside `position`, because the parser must run `parseComponent` over every child for its position, its id migration and the id-and-label uniqueness that keys note sections *globally*, and the sheet view must flatten the tree before the name table can be complete. Once the parser walks `children`, depth is shape, and §5's rule applies: the shape of the key is not forgiven the way its contents are. The check is structural rather than type-aware — a `children` key on a component two containers deep, whatever its `type` — so `src/parse/` still imports nothing from `src/components/` and the rule holds for a container type nobody has written yet.

**Tabs leaving for their own entry is the half that reversed the plan**, and three independent tools converged on it: Custom System Builder ships Panel and Tabbed Panel as two entries in a catalog of seventeen, with the Tabbed Panel holding a panel per tab; Sandbox puts tabs above panels and its root accepts nothing else, "Template Actors can only hold Tabs and/or cItems"; Palantir Workshop, a different industry entirely, does the same with sections inside layouts. The convergence is evidence and the argument is local. A group's children are shown together and a tab set's are alternatives, so one `children` key would say two things, which is the rule §4.1 already applies to `display` against `compute`. Two further arguments were made here and **both have since eroded, which is worth recording rather than quietly leaving them standing.** One was that a tab must be a region where a card need not be, so a tab set carries a constraint on its children that a group does not — withdrawn, because a tab may be any component and requiring a container is ceremony on a tab holding one Table. The other was that `collapsible` would be inert in tabs mode while the strip would be inert outside it — half withdrawn, since `collapsible` no longer exists. So the decision now rests on the first argument alone. It is the load-bearing one and it holds, but a reader should know it is carrying the weight by itself. With tabs gone `display` would take two values, and a two-valued select is a boolean spelled longer. Two properties then fall out of the depth rule rather than needing rules of their own: a tab set whose tabs are groups cannot itself be nested, because those groups would be the third container, which is Sandbox's root rule arrived at from the other end — one whose tabs are cards is an ordinary second-level container; and a top-level tab set spanning the full width is the whole-sheet multi-page idea a "pages" feature was reaching for, with the phone argument intact, since a tab set never changes the sheet's height where a collapse does.

**Containment is not addressing**, which is what keeps the depth-of-name bullet above untouched: a child inside two containers publishes exactly the name it publishes at the top level, and no container publishes anything at all. That is unanimous in the prior art rather than merely convergent — CSB's own word for a Panel is "invisible", Roll20 attribute names are flat regardless of surrounding divs, Sandbox property keys are global, and CSB's `fetchFromParent` looked like the exception and is not, since it walks document ownership and the wiki says it "doesn't work on Actors, only Items, because Actors don't have parents". Nesting has cost nobody a name segment anywhere. The character note is untouched for the same reason: a container has no section, so the body stays a flat list of `##` headings, one per leaf, and Constraints 2 and 3 hold by not being in the diff. `StorageKind` gains `'none'` so that "a container holds no data" is checked rather than asserted, and the sheet view then skips `getSection` and `read` for one.

**Group shipped with a collapsible heading and it was withdrawn, which is the correction this entry exists to record.** It was in the plan, it was built, and looking at the rendered sheet is what killed it. In the harness a one-card group beside a group spanning four rows closed and the sheet did not move: it left a hole exactly the height it had saved. The same control on the tall neighbour moved everything below it. One control, one layout, two unrelated outcomes, and which one an author got was decided by a property of the placement that nothing states, nothing enforces and nothing could show them.

The rule that explains it was already in §8 and neither the spec nor the build recognised it: **a component fills its placement.** A collapse is a component *ceasing* to fill its placement, so the hole was not a side effect of grid row bands — it was that rule being broken, and the row-band reasoning above is the symptom rather than the cause. The corollary is what puts hiding on Tab set: **a container's size is declared and not derived, so hiding must never change it.** A tab set goes on filling its `width × height` while it hides, because every one of its tabs is placed on that same inner grid and is therefore the same box; a collapse can only stop filling it. That also means the sizing question a tab set would otherwise have — which tab decides the height — does not arise, and the guarantee is structural rather than measured.

The original spec wrote "hiding has to reclaim space" as an argument for subgrids and never asked whether reclaiming space *inside* a container shortened the *sheet*, and the brief's own note that a tab set never changes the sheet's height where a collapse does was read only as an argument for tabs when it was equally one against collapse. The correction also fixes something the build got wrong on its own terms: an inner grid was `width` columns with implicit rows, so a container's declared `height` did nothing, and a child two rows high inside a group was not the size of the identical component two rows high outside it. **An inner grid is the placement, both halves of it.**

What that leaves Group is deliberately modest, and worth stating so it is not quietly re-grown: a name for a region at a rank above the labels the cards inside it carry, an inner grid that reflows on its own width, twelve cards that relocate by moving one block, and the panel a tab will hold. The last is the only unconditional one, which is also the honest answer to why Group read as pointless when it landed alone: it is the support and Tab set is the payoff, and building the support first on §12's component-by-component rule is what made that visible.

Three smaller decisions survive the withdrawal, each of which had a default waiting to be taken silently, and all three now belong to Tab set. **Hidden content stays in the DOM and stays laid out**, hidden with `visibility` and `inert` rather than removed: out of tab order and out of the accessibility tree, and **not** reachable by find-in-page. That last is the one thing the no-shift guarantee costs, and it is a genuine loss on a reference document — "where is my Stealth" answered with nothing found, on a sheet that has it. `hidden="until-found"` is the spelling that would have kept it, and it runs on `content-visibility: hidden`, which removes the content from layout: a panel contributing no height is a panel whose appearance changes the container's size, which is the whole thing being ruled out. Movement on every tab press is the worse failure, and a strip at least says there is content unopened where a hole said nothing. **It is also evaluated and rendered**, because §5's name table is driven by whoever reads a name rather than by whoever draws it, so a hidden card's value is already being computed for the pool elsewhere that reads it; skipping the draw saves the draw and not the arithmetic. The corollary is the one worth writing down: **hiding is never a way to make a formula not run**, so a component on an unopened tab still publishes, still resolves its `max`, still resets on a long rest and still appears by name in that trigger's confirmation. **And a container is offered no reset binding and offers none for its children.** §6's binding carries an action only the component can interpret, and a container binding beside a child's own binding on one trigger is precisely the two-bindings ambiguity §6 refuses a layout for, one level up and with no file shape to refuse it in.

One question the withdrawal takes off the table rather than answering, and it is worth naming because it was researched and argued. **Where hiding state lives** is the one place the two nearest prior arts disagree outright — Obsidian keeps fold out of the markdown entirely, per a developer, "the 'fold' state information is not part of markdown, and is not stored inside the note itself", while Sandbox stores it as a checkbox property in the character's own data. Obsidian's answer is the right one here, because our notes are files people hand-edit and because a container storing anything would end the premise this entry rests on. Which tab is active is that question again, and Tab set will have to answer it; nothing about the answer changed, only which component owes it.

What it costs. **The editor is where this is paid**, and the prior art says so loudly: the interim settings form grows a level of disclosure, a destination for the add row, and a second schematic, and the M4 canvas inherits a tree where it expected a list. Depth 2 bounds that work but does not remove it. **Two container types mean two entries in the palette for one idea**, and an author who wants tabs and finds Group first has to notice that Tab set exists. **A tab cannot hold a sub-region of its own**, since that would be the third container. **And the case for two container types is now carried by one argument** where it was written with three, the other two having been withdrawn above. **And Group alone is thin**: until Tab set exists it buys a heading and an arrangement, which is a real but modest thing to have added a catalog entry and a shared config key for. **The inner grid's columns agree with the sheet's exactly**, because the container adds no box of its own: a component *W* columns wide occupies `W·T + (W-1)·G`, and dividing that into *W* columns at the same gap gives `T` back. Held by a guard on the stylesheet, since it is what lets a group be legible from alignment alone and so need no border. **And nothing enforces taste**: a sheet may nest to the limit everywhere, and the limit is the only thing stopping it.

Resolved: **the formula language aggregates over a component's rows as one builtin call, and gains no collection value for it.** `sum(<component>, <expression per row>, [<condition per row>])` and `count(<component>, [<condition per row>])`, evaluated once per row in the row's own scope (§5). So an inventory's encumbrance is `sum(inventory, Qty * Weight)`, the weight of what is carried is `sum(inventory, Weight, equipped)`, and how many are equipped is `count(inventory, equipped)` — the three things this entry said were out of reach. The rows arrive through one new optional member on the contract, `scopeRows` (§4.1), which only Table implements.

Both halves of the question the entry named. **What an aggregate is written as**: one expression in a formula rather than more configuration on a column. Every tool in the comparable set sits there, Notion moved from the second to the first and said why, and every tool that put the aggregate somewhere other than the expression language generated a documented workaround genre — a `filter` beside `total` in a column's config is the exact shape Notion abandoned. **Whether the language grows a collection**: no, and this is the load-bearing half. The convergent prior art says the expression should *name* a collection which some other expression consumes, and that is declined for a reason specific to this codebase rather than a preference. In every one of those tools the destination of a collection is a display surface the tool owns; here a value has five destinations and none of them is one — a `FieldResolver` returns one and every component's `render` prints it, `ScopeEntry` carries one into the name table, `coerceValue` produces one from anything a note holds, and `applyReset` resolves one and **writes it into the note**. Widening the value type would put a collection one typo from `write`, and an author who means `sum(filter(inventory, equipped))` and types `filter(inventory, equipped)` into a Pool's `max` has written a Pool whose maximum is a list, whose bar clamps against a list, and whose long rest restores it to one. Every guard the prior art offers is a guard against that, and each costs something this codebase cannot pay: a documentation warning leaves the engine doing it, a runtime dispatch table leaks where a Table cell is a string, a static type check needs a type phase `src/formula/` does not have, and implicit reduction is named by Microsoft's own history as the mistake. **The guard here is that the type does not exist.** A row set lives for the duration of one builtin's frame and has no way to reach a card, a name, or a note.

What is kept of the declined half is the two lazy argument positions, which do the work `map` and `filter` do: `sum(inventory, Qty * Weight, equipped)` carries the expressive content of `sum(filter(map(rows, r => r.qty * r.weight), equipped))`. What is lost is *holding* the intermediate. So the departure is `SUM(FILTER(MAP(…)))` with the parentheses collapsed into argument positions, not SUMIF.

What it costs, and it is worth being plain about. The language grows by builtin rather than by composition, so `avg`, "the heaviest item" and "the names of what is equipped" each need a new builtin or cannot be written, where four tools in the set get all of those from one collection value and two combinators. A filtered set cannot be named and reused, so two aggregates over one filter walk the table twice and spell the predicate twice with nothing keeping the two spellings in step. There is no `first()`. And if a second collection consumer arrives the language widens after all and these builtins become special cases of the general thing — which is the real risk, though it is strictly additive: `sum(inventory, Weight)` names a component rather than a collection and would keep meaning what it means.

It also buys one exception, stated in §5 rather than left to be discovered: the first argument is a component reference and not a value, which is the only position in the language where one text has two meanings. A string literal is what the closest prior art uses precisely to avoid that, and the tokenizer has no quote handling at all, so adding string literals to the grammar so that one argument can be quoted is a larger and more permanent tax — besides making that argument look like the one thing the prior art is unanimous against.

What it does not settle: the depth question above, which is still what "how many slots are left" waits on. And it did **not** deliver item modifiers, despite the board saying that card waited on this one. The prior art was a counter-example worth acting on — both Foundry builders answer item modifiers by *push*, a row declaring a modifier against a named target — because a pull aggregate requires the target to enumerate every source that could modify it, which is the thing push exists to avoid. That card's dependency was re-examined rather than acted on, and the resolved entry below is what came of it.

**One sentence of this entry was wrong and is corrected here rather than edited away.** It said one of the two builders "is deprecating its own pull-side system in favour of" push. Custom System Builder deprecated **Item Modifiers, its own *push* system**, at 4.5.0 and removed it at 6.0.0, telling authors to use Foundry's Active Effects instead: it moved from a builder-owned push system to the *platform's* push system. The direction was always push, and the lesson is a different one — **Obsidian has no effects layer underneath**. Whatever is built here is maintained here forever, and there is no platform mechanism to hand it off to in two versions' time.

Resolved: **the five blocks still on the list are three palette entries and two layout patterns, and the catalog does not grow.** A currency block is a Card set with its denominations as entries; an inventory and a features list are Tables with `openRows` on and their columns prefilled; a spellbook and a card with its skills are several components placed together, which is an example layout rather than anything the editor offers as one item. §4.2 gains no entry, and none of the five wanted a capability the catalog lacks.

That is the inventory precedent below applied four more times, and it was worth applying one at a time rather than assuming, because each of the five was written down as work in its own right. The check each had to pass is whether the generic block covers the job or merely nearly covers it, and the two that turned out to be patterns are exactly the two the check separated: a palette entry is one component with its config filled in, so a job needing two components has nothing for one entry to be.

Currency was the only one where both mechanisms fit, and it beat Table on what a denomination is. Five declared rows with a number column stores and publishes the same five numbers, and it is the wrong shape for them: Table earns its apparatus on a row carrying several typed cells, and here `rowHeader`, the claim rule and per-row values buy nothing while a name column repeats the key that is already the card's own abbreviation. The one thing Table adds is `total`, and a total is the wrong arithmetic here, since copper plus silver plus gold is a quantity of nothing. What a currency block actually wants is weighted — `coins.gp + coins.sp / 10` — which is a Computed component reading names Card set publishes exactly as Table would have.

The prefills, because a palette entry nobody can state is not settled. **Currency**: Card set, entries `CP`, `SP`, `EP`, `GP`, `PP` carrying their full names, horizontal, no `derived`. **Inventory**: Table, `rowHeader` "Item", a `Qty` number column and a `Weight` number column with `total` on, no declared rows, `openRows` on. **Features**: Table, `rowHeader` "Feature", a `Source` text column with `secondary` on and a `Notes` text column, no declared rows, `openRows` on.

Where such an entry lives is what decides whether any of this is buildable before M4, and the answer is that it lives in no file. A layout stores the component an entry produced and never the entry itself, so the list is code, and when this was written the interim editor built its add-row dropdown straight from `listComponentTypes()` and pushed a component with no config at all. That leaves two homes: a table in `src/editor/`, or an optional member on the component definition. The second, because the first hands the editor Table's column shape, and nothing outside a component knowing that component exists is the rule the catalog is built on. It is buildable now either way — the interim editor's dropdown is a list of entries as readily as a list of types, and M4's palette reads the same list — which is why this is recorded as a decision rather than as work waiting on the editor. A prefill flavoured by one system costs the plugin no neutrality: the type stays generic, the entry is a starting point the author edits, and that is the same reason a palette entry may be named for a job where a component may not (§2).

Two of the five ran into a limit, and neither is an argument for a type. An inventory's encumbrance is quantity times weight summed down the list, which is a total over a computed column and refused on purpose — and the aggregate entry above is what answers it instead: `sum(inventory, Qty * Weight)`, which §363 names as the fix where that refusal stands. So the prefilled `total` on `Weight` is the weight of one of each item, and a loaded pack is one expression away rather than out of reach. And a features list holding paragraphs is not a table at all, since a cell is one line: a feature whose text runs long is a wikilink to its own note or a Rich text block beside the list, and a feature with uses per day is a Pool, as §5's worked example already has it.

The two patterns. A spellbook is an open Table of spells beside its slots, and the slots are a Track row set or a Pool for each level, so it is two components and there is no single item to offer. What it invites first is "how many slots are left", which is the depth question open above rather than anything this entry settles. A card with its skills is a Card beside a Table of declared rows, and a Group holding those two is a Group of leaves, which works whichever way nesting falls. **That block is the one waiting on the nesting bullet**, and only for its six-up arrangement: whether one outer Group can gather the six under a heading is that question and is not answered here.

One thing this makes decidable and does not decide: §12 has `link` columns waiting for the inventory that needs them, and this inventory does not need them. The item is the row name, and a wikilink in a row name already renders as a link, stores as plain markdown, and propagates on rename (§4.2). A column whose value is always a note, with a picker and a resolved state, is waiting on some case that is not this one, and it stays parked.

What it costs is that the palette becomes the place system flavour collects, with nothing enforcing a limit on it. A wrong entry is cheap, being config an author could have typed; many entries are not, because a dropdown nobody can read is worse than the type list it replaced, and there is no rule here for which jobs earn one beyond the block already covering them.

Resolved: **a declared row publishes through the component rather than through its declaration: `ScopeEntry` gains `compute`, a value the component produces itself with a resolver in hand.** A column may ask to be published, a declared row carries a `key`, and that row's cell in that column answers to `<id>.<key>`, so `10 + skills.perception` is the passive perception the original brief wrote and it is computed from the same row scope the cell on screen is computed from (§4.1, §4.2). The name is the layout's `key` and never the note's text, so position addressing is untouched: the key says which declared row, and the claim rule says which line of the file that row reads, exactly as the render does. A character-added row still publishes nothing, because the entries are built from the layout's `rows` and a row the character typed has nowhere to appear in them.

It beat the other branch this entry offered, growing the scope entry a way to *name* an expression to evaluate, and what settled it was Track rather than Table. A declarative entry can name a formula field and a scope of formula fields; it cannot say `floor(value / marks)`, which is what a Track's bare id has to be. So that branch would have left §12's workaround standing and added a second mechanism beside it, and it would have owed the sheet-wide name table a two-stage scope construction — cells first, then the row's own values layered over them, an unresolved one omitted rather than zeroed — whose only client is one component, in the one place that is supposed to know about none of them. The chosen branch replaces the workaround instead: a Track states its marks as the stored value and its filled segments as a computed one, drops the restated `named.value`, and stops depending on the name table registering `named` after `self`. The test driving that through `buildSheetScope` keeps both of its assertions — the bare id is segments, `.value` is marks — and loses only the reason the registration order mattered.

What it costs is that a computed publication is opaque to anything reading the layout without running it. A `display` names one of the component's own formula fields, so a reader can in principle follow the edge; a computed entry is the component's own code, and §5's save-time cycle check can never see a cycle that runs through it. That is the trade taken, and it is why `display` stays and is the one to reach for: a computed entry is for a name the component can only produce itself. The runtime floor is what guards it, unchanged — the name table is lazy, memoised, and refuses a name that needs its own result, so a row naming a second row that names the first leaves both cells showing `?` beside the name they could not find, and every component outside the cycle keeps working.

What it does not cover: a third level of name, which stays open above, and the aggregate over a computed column. A `total` on one is still a configuration error. Publishing one declared row's value and summing a column of derived values across however many rows a character has are different questions, and only the first is answered here — **the second is answered by the aggregate entry above**, which reads a computed column for the same reason this entry publishes one, a resolver bound to the finished sheet, and which leaves the `total` refusal standing as the statement about `total` it always was.

Resolved: **open rows are a boolean, not a second component, and the block is called Table.** `openRows` crossed with the `rows[]` the layout already declares covers a skill list, an inventory, and a Blades load list on one rule (§4.2), so there is no second component. That settled the half §13 said had to be settled first, and with one component there was one name to choose. It widened, taking the second of the two branches this entry offered.

The argument first written here against widening — that it would cost a migration across every layout's `type: 'skill-card'` — was checked and found false: nothing had been released, so no layout existed outside this repository's fixtures and a throwaway vault. What remained was §2's rule that a component is named for what it is on the page, and under it "Skill card" was the catalog's only exception and the only name that read wrong over four of its own five jobs. The rename cost no character note, since a note holds no component type, and no formula, since formulas reference a component's `id` rather than its `type`.

What the catalog may eventually want is a second *palette entry* — the same component type offered as "Inventory" with `openRows` on and Item, Qty, Weight columns prefilled — which is a layout-editor concern needing no new type.

Resolved: **a row is identified by its position in the note's table**, not by the text of its first cell (§4.2). That is what the file format always said; keying rows by name added a uniqueness constraint markdown never had, and it was invisible only while the layout author wrote every row name.

Resolved: **two opposed runs are two rows of one Track.** Death saves were a Group of two components while a Track held one run. `rows` made them a row set, and "whichever fills first" stays a rule of the game the plugin does not know either way. The refusal it replaced was argued from the cost of adding a per-system flag to a component, and that argument stops applying the moment a general field meets the same need. It was also incomplete until `sense` could be set per row: folding several components into one loses whatever each of them could configure for itself, and the check is to name those fields before the move rather than after.

Resolved: **body sections are keyed by the component's `label`**, which doubles as its heading, keeping the note readable. The `id` is the stable identity formulas reference, so renaming a label breaks no formulas, and section 10 covers migrating existing characters when it happens.

Resolved: **layout files live in `Sheetsmith layouts` by default.** The folder is configurable in settings. An empty or whitespace-only value falls back to the default rather than silently pointing at the vault root.

Resolved: **item modifiers are push, and the push lands in a `mod.` slot the target's own formula reads by name.** One row of a Table declares a change against a value published elsewhere on the sheet; the value names no source however many rows push at it. The aggregate entry above said this card's dependency deserved re-examining rather than acting on, and it did: the aggregate delivered none of it, and the answer turned out not to need it.

**Push rather than pull, and the prior art is unanimous.** Foundry core Active Effects, Custom System Builder's Item Modifiers, Sandbox System Builder's MODs and Roll20's 2024 Modifier Builder all declare a modifier the same way — a target key, an operator, a value. Nothing in the category answers this by pull. Roll20's older custom sheets have no push at all, and their documented workaround is a sheet worker summing a repeating section into a named attribute, which is exactly the pull aggregate already shipped here as `sum()` and `count()`. A pull aggregate requires the target to enumerate every source that could change it, so an armour class whose formula names the six items that might touch it has to be edited when the character buys a seventh.

**The obstacle, and what got past it.** Two tools independently forbid a modifier landing on a value the reader types into: Custom System Builder states it as a limitation — modifiers work only on a number containing a Label, not on input-field components — and Foundry practice reaches the same rule from the other side, targeting `system.attributes.ac.otherMod` rather than `ac.value`, because a derived-only field is one the sheet never submits. §3 puts every component's value in the character note, so the naive target is exactly the case both tools refuse. The answer is that **the sheet publishes one number per target, under a reserved `mod.` namespace, and the target's own formula reads it** — `derived = value + mod.self` (§5). So the authoring is push and the engine stays pull, which is where this codebase's guarantees already live.

Three things make that the answer rather than a compromise. **It needs no new evaluation pass**: the slot's thunk sits in the existing lazy, memoised name table behind its existing re-entry guard, and the walk that produces the pushes runs each component's own resolver — the same one the name table already builds for a `display` or a `compute`. One pass, three guards, two of which were already there. **It therefore does not have the best-documented failure in the category**: Foundry's dnd5e#3900, where an effect adding `@abilities.con.mod` silently adds nothing because core effects apply before the system's derived data runs, and for which an entire widely-installed module exists to add a second pass. Here `derived`, `compute` and a column `total` are *all* derived, so this project was more exposed to that bug than Foundry is; with one pass there is no ordering to get wrong, and a ring is closed loudly by the guards rather than silently. **And it does not reopen the published-name depth question** above: a slot is not a component's entry, answers to no `.value`, and is registered by the sheet.

**Stacking is typed, and it belongs to the set rather than to any one modifier** (§5): the best bonus and the worst penalty of a type apply, types add, untyped modifiers all stack. That is the finding the design most had to survive — three of the four systems surveyed combine by maximum somewhere — and it is why there is no per-modifier operator, since whether a given +2 applies depends on what else is present. It stays one number per target, which is what keeps the single pass and what makes a priority field unnecessary rather than deferred.

**Provenance is the breakdown, at the number, and that is the differentiator.** Sandbox colours a modified attribute green; Custom System Builder ships a separate Active Effect Displayer with an origin column. Both are separate surfaces from the number, and two independent tools deciding a sheet must at minimum *show* that a value was modified is what makes a mark the floor. Here the modifier rows are on the sheet and each names its target, so a modified card lists its own contributors — including the ones the stacking rule suppressed, with the reason, which is the line the whole breakdown exists for: a reader who bought two rings of protection and watched the number not move will otherwise conclude the plugin is broken.

**What it costs, and none of this is softened.** A target that never writes `mod.self` into a formula **silently ignores every modifier pushed at it** — the mirror image of the bug this shape avoids, moved somewhere else. It is *knowable*, which is why both halves are surfaced: the layout editor names the values this layout takes a modifier for and says so where nothing on the layout reads a slot, and the sheet says it at the cell, because a target cell is character data the editor has never seen. The accepting set is coarse at the component and **over-reports**, so the picker may offer a target that ignores the row, and the sheet's stray line cannot fire for that case. A **component that forgets to pass its published name to its own resolver reads `mod.self` as 0** with nothing saying so, which no registry check can see and which costs a test per publishing component. And **a target has to be given a `derived` to become modifiable**, which changes what its card looks like — mostly a gain, since the modified number over the base is the provenance floor for free, but an appearance change forced by an arithmetic decision.

**What it does not deliver**, each deferred with a reason rather than merely unbuilt. **Multiply and override operators**, which are precisely the ones that cannot fold into one number per target: taking them forces the second application pass, plus a priority integer and an operation order, which is what both Foundry and Custom System Builder carry. **Grouped conditional modifiers**, whose ungrouped case is already expressible — a toggle cell plus `if(Mood, level, 0)` in a computed amount column — and whose missing half is one switch governing many modifiers and a surface to show it on. **A row naming two targets**, and **a row whose type differs from its neighbours'**: one target column per table and the type on the column, so a row changing two values is two rows and a table carrying two types is two modifier columns. **A modifiable Pool max or column total reached directly**, both of which go through a published name that has a formula of its own. And **dice**: Lancer's accuracy and Call of Cthulhu 7e's bonus dice change the *dice* rather than the number and resolve by cancellation, so §11 rules them out — which is worth stating, because it establishes that "a modifier is a number applied by an operator" is a 5e-shaped assumption rather than a general one.

Five things stayed closed and are named so they are not reopened by accident: the depth question above, which a slot does not touch; the collection value and the string type the aggregate and the prose entries declined; the two cycle guards' mutual ignorance, which gained one more entry point and no change to the rule — and which is why the slots stay lazy, since warming the name table in a fixed order would decide which guard wins; and Table's `select` column type, whose blocker is a field kind and which neither of this feature's two new cell controls carries an options list for. **The authoring surface itself was reopened by this entry and is now settled below**; the model this entry settles is what that surface was built on, not something it replaces.

Resolved: **a modifier lives in one of two tiers, and one cell holds both.** A row's modifier cell carries `;`-separated parts, each either the **name of a definition the layout declares** or a **typed modifier written on the row** — `armour_class += 2 as item when Worn`. The `target` column and the separate amount column are withdrawn; the column type is `modifier`, and one is enough because a cell holds a list.

**The tiers answer two different questions and neither collapses into the other.** A definition is a thing the layout knows — a Ring of Protection every character may wear, edited once and moved on every sheet at once — and a typed modifier is a thing one row is, an item that is *almost* the Ring. Reference-only was chosen over copy-on-enrol deliberately: a note stores a name and never a copy of what it says, so no character can hold a stale duplicate of the layout's arithmetic. The cost is stated where it lands (§10): a renamed or deleted definition leaves the word in the cell and the row stops applying it, visibly, rather than silently.

**The discriminator is the operator, and it is the load-bearing decision in the cell format.** A part carrying `+=` or `=` is typed; a part carrying neither is a name — which is what lets a definition be called `Bracers of Defence +1` without the arithmetic in its name being read as arithmetic. Constraint 3 holds part by part rather than over the whole cell, so a hand-written spacing survives an edit to a different part.

**Two things the two-column model could not do**, and they are why the surface changed. A row could modify one target, because an amount had no way to say which of two target columns it belonged to; a cell of parts has no such problem, so one row now changes as many values as it names. And a table whose rows carried different bonus types needed one column per type with most cells blank; the type now rides on the definition or on the part's own `as` clause. What that costs is the guarantee §5 gave up: a note can name a bonus type, so §10 gains a rule where it had a construction argument.

**The authoring surface is one glyph per row opening a form anchored to it** — a list of the row's modifiers, one open at a time, six labelled fields committing one at a time on the sheet's own editing gesture. An override operator ships with it (`=`), the phase split it forces is in §5, and **promotion** — naming a typed modifier and saving it to the layout — is §7's, and is the first thing in this plugin that edits a layout from a character's sheet.
