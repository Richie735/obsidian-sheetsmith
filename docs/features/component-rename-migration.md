# Component rename migration

Status: shipped, bar the manual vault walkthrough (criterion 20), which is blocked on the fixture
Board card: `docs/SPEC.md` §10 — "Renaming a component offers to migrate matching sections in existing characters."

## Model question

Not a §13 open question — the owner already settled the scope in conversation, before this doc, on this principle:

> The promise migrates any name a component declares as the address of its own stored character data — the section label, which addresses the section itself, and a declared entry key, which addresses one entry inside that section's fence. Renaming either leaves data in the note under a name the layout no longer looks for; the harm and the fix are the same shape in both cases.

Two surfaces follow from it and three do not:

- **In scope: a component's `label`** (SPEC §3.1 — the section heading) **and a declared entry key** (Card's `key`, a Card set entry's `key`, a Track row's `key`, a Passport's `nameKey` and a field's `key`, a Record set field's `key`, and a Roster stat's `key`). The boundary is not "Card and Card set," which is what the model question named as the surfaces under discussion, but every author-declared name that addresses one entry in a `sheet` fence — and that has to be checked field by field against the real code, not assumed from a component's name. `grep -n "readFenced|writeFenced" src/components/*.ts` finds eight hits, not six or five, and each earned its place in or out on its own:
  - **In, and fence-addressed exactly like Card set's `entries[].key`:** Card, Card set and Track (all three declare `storage: 'fenced'` directly), plus Passport and Record set (both declare `storage: 'markdown'` but still call `readFenced`/`writeFenced` on the `sheet` fence nested in their body), plus **Roster's `stats[].key`** — its own `configFields` description says it outright, in Card set's own words: "A key names the entry in the note... renaming one does not move a stored value — the old entry stays in the note under the old key" (`roster.ts`, the `stats` field). `RosterData.stats` is, in the component's own comment, "the fence's own entries by stat key."
  - **Out: Pool.** It imports `readFenced`/`writeFenced` too, but against three fixed constants (`CURRENT_KEY`/`TEMP_KEY`/`MAX_KEY`, i.e. `current`/`temp`/`max`) the author never names in any config field. There is no declared name here for a rename gesture to target — the same absence of a target that excludes an id, one surface over.
  - **Out: Table**, and **out: two of Roster's own three `key`-shaped fields, for two different reasons that both happen to land on the same component.** `columns[].key` (Roster) and a column's own `key` (Table) are not fence entries at all — both are pipe-delimited markdown-table header text, read and written through `parse/table.ts`'s `readTable`/`writeTable`, a format the fence primitive cannot touch; Roster's own validation message for it ("cannot contain a pipe or a line break, because a pipe separates one cell from the next") is copied verbatim from Table's, because it is the identical mechanism. `rows[].key` (Roster) is a third kind again: its own doc comment calls it "the name a formula reads this row's published value by, as `<component id>.<key>`" — a formula-facing publish name, the same shape as a component's own `id`, not a note-facing storage address at all. Nothing in a character note is ever keyed by it; renaming it changes what a formula may reference, exactly the id-rename problem the model question already excludes as surface 3. (A row's actual identity in the note is `row.label`, matched by `parse/row-claims.ts` against the table's own name column — a third addressing scheme again, and not one either the owner's settled answer or this feature's brief named as in scope; it is left alone here rather than folded in by inference.)

  The editor wiring confirms the same boundary independently: `stats` is `field.kind: 'entries'`, routed through the shared `renderEntriesEditor` this feature already hooks (below); `columns` and `rows` are the separate `field.kind: 'columns'` and `field.kind: 'rows'`, each routed through its own editor function (`renderColumnsEditor`, `renderRowsEditor`) this feature never touches. So the exclusion is not just a storage-format argument — it falls out of which commit site the migration is wired into at all.
- **Out of scope: id (surface 3).** No character note ever stores a component's id — only its label and its declared keys do. Renaming an id breaks formula references *inside the layout file itself* (other components' formula fields, the function library), which is a layout-internal rewrite problem with no promise in SPEC today and no mention in §7. Nothing here touches it.
- **Out of scope: layout name (surface 4) and modifier definition name (surface 5), and the principle above does not actually reach either, on inspection.** A layout's name addresses the note-to-layout mapping, not one component's data — renaming it would have to migrate every character's `sheet-layout` frontmatter, which §7 already declines for that reason. A modifier definition's name is typed free-form into arbitrary cell text by a character, not read from one declared address — §10 already declines it because fixing every occurrence is an unbounded search, not a rewrite at one declared key. So both were already declined for a structurally different reason, not merely deferred by the same argument this feature settles. Recorded here as the one-line note the brief asked for, in case a future session is tempted to read this feature as the first half of either.

## What it does

Renaming a component's label, or a declared entry key, in the layout editor now finds every character note pointing at this layout and rewrites the matching section heading or fenced `key: value` line in place — byte-identical otherwise — so existing characters keep reading correctly the moment the author renames something, instead of going quiet under a heading or a key the layout no longer looks for.

## Smallest version

Rename the label or a key, the layout saves, every applicable note is rewritten, one summary line appears if anything changed. No confirmation dialog, no preview, no retry command, no undo of the migration itself — undoing the rename in the layout editor's own undo stack puts the layout back to the old spelling and leaves already-migrated notes exactly as they are (see Deliberately not doing).

## Design

**Trigger: the existing commit, not a new gesture.** No "Rename" button is added anywhere. The Label field in `config-panel.ts` already commits a single old-value-to-new-value change on blur/Enter (`config.label = label`), with both values in hand at the moment of commit; the shared entries editor (`renderEntriesEditor` in `list-fields.ts`, used by Card set's `entries[]`, Track's `rows[]` (as `track-rows`), Roster's `stats[]`, and — via `entryFlag` — Passport's `fields`) already commits a key the identical way (`entry[primary.key] = next`, with `stored`/`next` both in hand); Card's own `key` field and Passport's `nameKey` commit the same shape directly in `config-panel.ts`; Record set's per-field `key` commits it once per declared field. Every one of these is already an *explicit* rename with a known before and after — this is what research finding #7 asks for (an explicit rename op, never inferred from diffing two saved configs) and every one of them already satisfies it without new UI. Roster's other two `key`-shaped fields commit through `renderRowsEditor` and `renderColumnsEditor` instead — different functions this feature does not hook, which is what keeps them out (Model question, above) at the wiring level and not only by argument. What changes is what the commit does afterward, not how it is made.

**Eager, not lazy.** The migration runs at the commit, not the next time each character's sheet opens. Every surveyed tool that keys storage by a human-readable name — Excel, Foundry's dnd5e system, Obsidian's own core property rename — rewrites eagerly with no prompt (research finding #2), and this codebase has no precedent for a per-note migration version stamp (Roll20's `codeversion`, Foundry's `systemMigrationVersion`) and no place to put one: a character note holds one frontmatter key and values only, and a stamp would be new bookkeeping this file model has never carried. SPEC §10's unmapped-section guarantee would make lazy *safe* here in a way it is not in Roll20 (an orphaned attribute there is invisible and undeletable; an unmigrated section here just does not render, silently, with nothing lost), but safety is not the same as being simpler to build, and eager is both simpler and the convention every precedent actually uses.

**No confirmation, and this is a considered departure from MetaEdit's precedent, not an oversight.** MetaEdit — the one surveyed tool that asks — gates its dialog on whether *existing values are at risk of being overwritten*. Nothing here is: the fence's own `writeFenced` never merges two entries, and the rename either finds a clean target and moves the key, or finds a collision and leaves that one note alone (below). No path in this feature overwrites a stored value, so the condition that earns MetaEdit's modal is never met. A per-rename confirmation would also fight a layout's own translation pass, where one job produces many identical renames (research finding #6).

**Write ordering: the layout lands first, always, and the open sheets bracket the scan.** `installLayoutSource`'s own comment about the modifier-promote flow — "the layout write lands first, and only then is the cell rewritten" — is the precedent the first step follows. The commit hands its rename intent to `persist()` rather than firing the migration itself, and `persist()` then runs four steps in this order:

1. **Write the layout file.** `persist()` is the one place that calls `modify` on it. If this write fails, it returns and no character note is touched — no flush, no scan, no notice.
2. **Flush every open sheet** (`flushSheets`), so a value the reader typed seconds ago is on disk before anything reads it. Why this is needed at all is the next paragraph.
3. **Run the migration** (`reportComponentRename`), which is the whole of the scan and the one `Notice`.
4. **Reload every open sheet** (`reloadSheets`), so a sheet showing a note the scan rewrote draws the new text rather than the text it still held. This replaces the older `refreshSheets()` on this path and the rename path returns rather than falling through to it, because a reload renders too — refreshing without re-reading is what drew a renamed component blank.

**Three host members and not one bracket.** A single `withSheetsFlushed(fn)` was weighed and refused for now: it would make it impossible to remember *half* the bracket, which is a real but narrower fault than the one it is named for — forgetting it entirely is exactly as easy either way, since a writer has to choose to call it. Against that it puts control flow into a host interface that is otherwise five state accessors and a redraw, for one caller, where `docs/PATTERNS.md` §1 extracts a policy at its second site. And the convention is scaffolding for something we expect to delete: the real fix is the vault event in the view, which makes the bracket unnecessary rather than tidier. The trigger is a second vault-wide writer, which is what `docs/BACKLOG.md` now carries.

If the layout write succeeds and the migration is then interrupted (the app closes mid-scan, a note's own write fails), the layout is already correct and any note the migration has not reached reads as an ordinary unmapped section under SPEC §10 — inert, not lost, fixable by hand the same way a note is fixed today. **That guarantee is about the file, and it does not extend to a sheet already open on it**: this was written as though it did, and believing it is what let the reload be omitted in the first place. A note nothing has open is inert and recoverable. A sheet open on a note the scan reached but step 4 did not — because the app closed between them — is showing stale text until it is reopened, and reopening is the whole of the repair. Nothing is lost either way; the difference is that one of the two states looks like data loss to the reader, and saying so is what stops the next reader of this paragraph drawing the conclusion it originally invited.

**Open sheets: a debounce before, an absent vault event after, and a conditional write to close the gap between.** This is the half the first draft of this document did not have, and its absence is why the feature shipped with a bug the owner found by hand in the app: a value typed into a card, then that card's label renamed within a couple of seconds, migrated nothing, reported *nothing at all*, and left the card blank with its value still in the file.

**The platform is not passive here, and an earlier draft of this paragraph said it was.** `TextFileView.onload` registers `this.registerEvent(vault.on("modify", this.onModify, this))`. So the base class `SheetView` extends *does* own a vault event, and the true statement is the narrower one: **`SheetView` registers none of its own and overrides no `onload`**, so it inherits that handler rather than lacking one. Read out of the installed app's `obsidian.asar`, the handler is `onModify(f) { this.saving || (f === this.file && this.loadFileInternal(f, false)) }`, and `loadFileInternal` re-reads the file, and where the view is **dirty** three-way merges the reader's text against it — base being what the view last saved — and announces it: *"{{file}} has been modified externally, merging changes automatically."* Its `save` also refuses to write when `lastSavedData === getViewData()`.

Two platform facts then bite, and one thing the platform cannot do for us. **`requestSave` is a two-second debounce** — `obsidian.d.ts` says "Debounced save in 2 seconds from now" — and `SheetView.commit` is the sheet's only write path, so for two seconds after a reader leaves a cell the value they typed exists only in the view's `data`. Nothing in the platform brings that forward when something is about to *scan* the vault: a scan reading the file in that window finds nothing to rename and correctly says nothing, which is indistinguishable from a rename that had nothing to do. **Hence step 2, and it is the one step of the four that is genuinely this feature's own.**

**Step 4 is a deterministic, immediate version of what the platform would do on its own event.** The handler above would eventually update a clean view on the migration's write; doing it ourselves, in a known place in the sequence, is what makes the ordering stateable and the behaviour testable, rather than a race against an event the tests cannot drive. That is its whole justification — not that the view would otherwise stay stale forever.

**So step 4 must decline a dirty view.** Where the reader committed a keystroke between step 2 and step 4, `reload` would overwrite `data` and lower the flag, discarding an edit the platform's own handler would have *merged* and reported. That is worse than the staleness step 4 exists to fix and worse than doing nothing, so `reload` returns early when the flag is up and leaves that view to the handler — which is genuinely reached, since `onModify`'s guard is `this.saving`, and step 2 awaits each save to completion before step 3 writes. For the same reason `setViewData` lowers the flag only when its `clear` argument is set: `onLoadFile` sets it, an external-change update does not, and a merge arrives through the unset door still carrying the reader's edit and still owing a write of it.

**The conditional write, and an honest account of what it buys.** `SheetView` tracks whether it holds an edit nobody has saved — raised by `commit`, the one door into `data` a reader can reach; lowered by a completed `save`, by `clear`, and by `setViewData` only on a new file — and `save` writes only when it does. The temptation is to say this closes the debounce race, and it does not, because **the platform closes that race too**: after step 2 the view's text *is* what it last saved, so the base class's own `lastSavedData === getViewData()` check returns early from the late call without any help. What the flag actually buys is three things worth having anyway. It is the same protection expressed in members the typings admit, rather than resting on a private field; it is testable, which `lastSavedData` is not from outside; and it suppresses a redundant write the platform would make after step 4, since `reload` moves `data` without touching the platform's own bookkeeping — which is what keeps the fixture's modified-time check meaningful. Reaching for the `Debouncer.cancel` the runtime object probably has was refused on the standing ground: an untyped member a release can remove silently, the hazard `docs/BACKLOG.md` records against the suggestion popup's `suggestEl`.

**The flag is also the right question for the flush itself.** An earlier draft compared the file's bytes against the view's, which answers "does the file differ" and not "does this view have an unsaved edit". The two come apart when something *else* wrote the note (a Markdown pane in a split, which `view/auto-open.ts`'s per-file override makes a supported state; Sync; another plugin; an earlier rename), and on that branch a byte comparison writes the view's *older* text over it — forced on every rename, on a note the reader never touched.

**Scope: found through `metadataCache`, not by reading every file.** `app.vault.getMarkdownFiles()` filtered by `metadataCache.getFileCache(file)?.frontmatter?.[LAYOUT_KEY] === layoutName` — the same cheap frontmatter read `commands.ts` and `view/auto-open.ts` already use to answer "is this a character note for this layout," so no note's body is parsed until it is a real candidate. **Not scoped by the character folder setting, and the first draft of this paragraph said the opposite.** That setting is a *creation destination* — its own description reads "New characters are written here", and `characters.ts` is the only other reader of it, which uses it to decide where a new note goes. Reading it as a residence rule shipped, and orphaned the owner's entire vault on the first hand-run: their characters live in `Characters/` while new ones are written to `Characters/new`, so a label rename through the panel reported nothing, wrote nothing, and left the note rendering empty under a heading the layout no longer named — the exact silent orphaning this feature exists to prevent, caused by the feature. It also contradicted Acceptance criterion 1 ("every character note whose `sheet-layout` names this layout"), which is the promise and wins. The frontmatter read is what makes a whole-vault scan cheap; the folder was never what made it cheap. A note pointing at a *copy* of the layout file is correctly and invisibly out of scope — it is a different layout by name, the same as every other feature in this plugin treats a copy, and surfacing that distinction would need the plugin to detect two files are byte-similar, which nothing here does and which would go stale the moment either file is edited. Not surfaced.

**The rewrite itself is two new pure functions, not a new file format.** `parse/fenced.ts` gains `renameFencedEntry(body, from, to)`: find the line whose trimmed key equals `from`, and either report "not present" (nothing to do), report "collision" (`to` is already a key in this fence — refuse, touch nothing), or rewrite only that line's key token, keeping its separator, its value and its line ending exactly as `writeFenced` already keeps a value's own spelling. `parse/character.ts` gains `renameSectionLabel(note, from, to)` on the same three-way shape, applied to a `## ` heading rather than a fenced line, copying `renameRecord`'s own trick of preserving the heading's prefix and line ending and returning the note unchanged when there is nothing to rename. Record set's per-record fields call the fenced version once per record inside the section, since each record carries its own fence; every other keyed component calls it once against the section's single fence. Neither function touches `obsidian` — both stay exactly where `parse/` already lives, tested the way `fenced.test.ts` and `character.test.ts` already test byte-preservation.

**The vault-wide part lives outside `parse/`, because it has to.** A new top-level module (a sibling to `layouts.ts`, not inside `parse/`, `components/` or `formula/`) owns the scan and the per-file write: given the app, the folder scope, the layout name and one rename intent (a label pair, or a section-plus-key pair), it lists candidates via `metadataCache`, and for each one calls `app.vault.process(file, (current) => …)` with the pure `parse/` function decorating the current text — a callback that is a pure function of `current`, satisfying the same caveat `appendModifierDefinition`'s own comment names: `process` may retry the callback, so nothing outside the callback's own return value may carry a decision across calls. **A file `process` finds nothing to change in is never touched** — the callback returns `current` unchanged, and a caller that skips calling `process` at all for a candidate the parsed note already shows no match for costs nothing and touches no mtime, honouring research finding #4 (Foundry's non-empty-changes guard; the Obsidian bug report calling an unnecessary rewrite "(meta)data loss" in its own right).

**Collision: refuse and report, never merge.** Where the target section (for a label rename) or the target key (for an entry rename) already exists in a given note, that note is left exactly as it was and counted separately in the summary. This is Notion's own cautionary tale read backwards (research finding #7: never infer a rename from a diff, and never let a rename silently become a merge) and it is the one place this feature could destroy data if it did not refuse — two components' values landing under one heading, or two entries under one key, with no way to tell them apart afterward.

**Reporting: one `Notice`, fired once, only when something happened.** Every other multi-note outcome in this codebase already reports through `Notice` (`sheet-view.ts`'s `commit`/`repointLayout` failures) rather than a global banner, which is the UI.md §10 instinct applied here even though §10 itself is written about a single component's own error. The difference from a silent eager rewrite (Excel, Foundry, Obsidian core) is that those rewrite something already on screen; this rewrites files nowhere in view, so the operation needs its own acknowledgment or the author has no signal it happened at all. Zero notes matched (the ordinary case while a layout is still being drafted, before any character exists) shows nothing — a Notice on every keystroke of an unused layout would be exactly the noise research finding #6 warns a per-rename gate produces. Where at least one note was touched or skipped, one sentence names the count and, where any were skipped, the reason: `Renamed "AC" to "Armor class" in 12 character notes.` or `Renamed "AC" to "Armor class" in 11 character notes; 1 left as "AC" because it already has a section called "Armor class", so move it by hand.`

**The sentence is a head clause and up to two more, and only the head is ever a success.** A summary carrying the renames alone reported an all-clear over two outcomes that are not one, both found in review: a Record set note where one record was renamed and a sibling kept the old key (`; 1 note has a record still under "Level".`), and a candidate note the scan could not read or parse at all (`; 2 character notes could not be read and were left alone.`) — a hand-edited note being exactly the population likely to be in that state, with its data left under the old name and nothing else to say so. Where nothing was renamed the head says so rather than claiming a rename "in 0 character notes": `Nothing was renamed: 2 character notes already have a section called "Armor class", so each keeps "AC" and needs moving by hand.` **The article belongs to the noun and never to the author's own key** — "a section" and "an entry" are the only two nouns these sentences have and both are fixed words, where choosing it off the key's first letter read "an Uses" for a Record set counter and "a hour" the other way.

**No new config field, no new gesture, and each description speaks only for what it addresses.** Seven descriptions said something this feature makes false and all seven change: the Label field's own ("Existing notes keep their data under the old heading; rename those headings manually") and, on six components, a key field's clause saying a rename "does not move a stored value".

**Label speaks for the heading and nothing else**, and this is a correction to an earlier draft of this paragraph, which put the whole promise on Label — "Renaming it, *or any key below*, renames that heading or entry…" — and had the six key fields merely lose their false clause. That is backwards, because **Label renders for every component in the catalog with no capability guard**: "or any key below" is false on Table (whose column keys migrate nothing), on two of Roster's three key-shaped fields, and on Pool, Group, Image and Rich text, which have no keys at all. Worse than merely false — a rename that matches nothing shows no `Notice`, so an author who renamed a Table column would get exactly the silence a successful migration produces, having just been told it migrates. So Label carries the heading clause only ("Also the section heading in character notes. Renaming it renames that heading in every character note using this layout.") and the promise sits on the key fields that actually keep it.

The design measurement that refused the repeat still governs the *shape* of those clauses rather than their placement: one near-identical 144-character sentence on Label and again on every key field put two copies 186px apart on a Card set and three within 372px on a Passport, where SPEC §13 records a past review cutting one 141-character sentence repeated at 340px. So each key field gains **one short clause**, far off that budget — Card's and Passport's `nameKey` "Renaming it moves that entry in every note on this layout.", Card set's "Renaming a key moves that entry in every note on this layout.", Record set's naming the record too ("…in every record, in every note on this layout"), and Roster's `stats` carrying the one caveat that is genuinely its own, since its key is also a name a formula reads and only the note half migrates: "renaming one moves it in every note on this layout, and leaves any formula that read the old name to be updated by hand."

Track's `rows` carries it too, inside its own longer description ("Each key names the entry in the character note, and renaming one moves it in every note on this layout"), so **all six key surfaces state the promise and Label states only the heading** — which is the shape this paragraph originally got backwards.

**The heading's own trailing whitespace is dropped, not preserved.** `renameSectionLabel` keeps the heading line's prefix and its line ending and discards any run of spaces after the old name, so `##   AC  ` becomes `##   Armor class`. That is `renameRecord`'s settled rule one level up, in its own words: the run "belonged to the old name, and preserving it would put spaces after a name nobody typed them for". Constraint 3 is untouched — it governs a note where *nothing changed*, and this is the one line that did.

## Config fields

None. This feature adds no `configFields` entry to any component; it changes what already happens when an existing field — a component's `label`, or one of the fence-addressed declared entry keys enumerated in Model question — commits a change.

## Data and file model

- **What is read.** `metadataCache.getFileCache(file)?.frontmatter?.[sheet-layout]` to find candidates, cheaply and without parsing a body that will not match. `parseCharacter` on each candidate, the same parser every save already goes through.
- **What is written.** At most one section heading or one fenced `key: value` line per note, through `app.vault.process`, preserving every other byte — Constraint 3 holds for the batch exactly as it holds for a single edit, because each note's rewrite is `renameSectionLabel`/`renameFencedEntry` composed with `serialiseCharacter`, the same round-trip machinery every write already uses.
- **What never happens.** No character note gains or loses a section that was not already there (Constraint 4); **this feature's own rewrite never opens a note it finds nothing to rename in** — the `process` call is skipped entirely for such a note, which is what Acceptance criterion 10 pins; a collision is refused rather than merged; nothing is ever inferred from comparing two saved layout configs — the rename intent always comes from one field's own commit, with both values already in hand.
- **The one write that is not this feature's.** The clause above used to read "a note with nothing to rename is not opened for writing at all", flatly, and the flush in step 2 makes that false as written: a note whose sheet is open *with an edit the reader has just made* is written by this gesture, and its modified time moves, even if the rename then finds nothing in it to change. Narrowed rather than engineered around, for a reason worth recording — flushing only the sheets the scan is going to touch is not merely costlier, it is circular: whether a note holds the old name cannot be known until it is read, and it cannot be read correctly until the flush has landed. What is actually written is the reader's own pending edit, brought forward by at most the two seconds it was already scheduled for, and a sheet with nothing pending is still never written at all — which is what keeps the fixture's modified-time check meaningful.
- **What is not this feature's problem.** An id rename, a layout rename, a modifier definition rename — see Model question. Nothing added here changes any of those paths.

## Acceptance criteria

Ticked from `/spec-review`'s per-criterion verdict, never from this session's own
reading of the code. **Criteria 1 to 15 are the original set and keep their
numbers** — the doc's own reference to "Acceptance criterion 10" still resolves —
**16 to 19 were added by the open-sheet work**, and the manual vault check moved
from 16 to 20.

The four the review first marked met in a weaker form than written are now met
outright, each by the closing case the review itself specified: **4** by a
Passport `nameKey` commit (a migration off its `whenBlank` default, Card's case
on a second component) and a Passport `fields[]` commit, taking the commit path
to all seven key surfaces; **6** by pressing a Table column key and asserting no
migration and no `Notice`, rather than resting on the absence of a hook; **9** by
a layout write that *rejects* rather than one that hangs, asserting no `process`
call; **12** by an actual close and reopen, for a label and for a key, rather
than the live path alone.

**20 is the only criterion left unticked.** It is the manual walkthrough, and it
is blocked on the vault fixture rather than on the code: `Characters/Untouched.md`
holds an `## AC` section it should not, which changes two of the walkthrough's
stated `Notice` counts and defeats its modified-time check. The fixture is
outside this repository and the owner's to correct.


- [x] Renaming a component's `label` and committing rewrites the matching `## ` heading, and nothing else, in every character note whose `sheet-layout` names this layout and that already has a section under the old label.
- [x] A note with no section under the old label is left byte-identical and is not counted in the reported outcome.
- [x] A note that already has a section under the new label is left byte-identical under the old label, and is counted as skipped with a reason, never merged.
- [x] Renaming a declared key — Card's `key`, a Card set entry's `key`, a Track row's `key`, a Passport's `nameKey` or a field's `key`, a Record set field's `key`, a Roster stat's `key` — and committing rewrites the matching `key: value` line inside the relevant `sheet` fence (each record's own fence, for Record set) in every applicable character note, keeping the value and the line's own separator and ending unchanged.
- [x] A fence whose target key already exists is left byte-identical and that note is counted as skipped, never merged.
- [x] A Table column's declared key is unaffected by this feature end to end — no migration is offered for it, and its config description is untouched.
- [x] Pool's fixed `current`/`temp`/`max` keys are unaffected — there is no config field for them to rename in the first place, and nothing in this feature adds one.
- [x] Renaming a Roster column's declared key (`columns[].key`) or a Roster row's publish key (`rows[].key`) triggers no migration — verified directly, not only by absence of a hook, since both are also named `key` and a careless wiring pass could reach them by mistake.
- [x] The layout file is written before any character note is touched; a layout write that fails leaves every character note untouched and triggers no migration attempt.
- [x] A note `process` finds nothing to change in is not passed a rewritten body — its file is untouched by this feature's own write, verified by mtime or a vault-write spy in the test, not by eye.
- [x] After a rename that touches at least one note, one `Notice` reports a count; after a rename that matches zero notes, no `Notice` appears.

## Vault fixture

The fixture lives outside the repository, so its recipe lives inside it
(`AGENTS.md`, Testing). One layout, `Sheetsmith layouts/Rename variations.json`,
and three characters in `Characters/`, each of which is a different outcome of
the same rename:

- **`Renames.md`** carries the walkthrough itself — five gestures, in order,
  each with the exact `Notice` sentence it should produce — and is the note
  every one of them rewrites. Its sections are `## AC` (a Card that declares
  no key, so the note stores `value` — the default a first naming migrates
  off),
  `## Abilities` (a Card set, `STR`/`DEX`), `## Spells` (a Record set, two
  records each with a `Level` entry) and `## Skills` (a Roster: a `WIS` stat in
  the fence, a `Training`/`Total` markdown table under it).
- **`Collisions.md`** already holds the new name for four of the five gestures:
  an `AC` entry beside the default `value` in `## AC`, a second section under
  `## Armor class`, a `Dexterity` entry beside `DEX`, and a Record set where
  "Fireball" already has `Spell level` while "Shield" does not — the one note
  that is part refused and part rewritten, and the case that decides a
  multi-fence note's aggregate verdict.
- **`Untouched.md`** points at the layout and holds none of the old names, so
  no gesture may open it for writing. Its modified time is the check.

The five gestures, in the order the walkthrough runs them: typing `AC` into the
Card's blank **Key**, which renames `value` → `AC` because a blank field means
the component's own default and that is what every note stores — the one path
with no other manual demonstration; the Card's **Label** `AC` → `Armor class`; the Card
set's first entry key `DEX` → `Dexterity`; the Record set's field key `Level` →
`Spell level`, whose notice carries both clauses — two notes renamed and one of
them still holding a record under the old key; and on the Roster, the stat key
`WIS` → `Wisdom` (migrates), the `Training` column key (no migration, no
`Notice`) and Insight's **Publishes as** key (no migration either). The order
matters: the Card's key gesture runs before its label gesture so that the key
rename still resolves its section as `AC`. Undoing them afterwards is what
shows the layout going back while the notes stay migrated.

**A sixth gesture, and it is the one the other five cannot show.** Every gesture
above renames a name that is already on disk, so none of them exercises the open
sheet at all — which is exactly how the debounce bug reached the owner through a
fixture that looked complete. The sixth reproduces it, and it has a stopwatch in
it:

6. **A value typed seconds before the rename.** Open **Renames** as a sheet,
   click into the **AC** card, type `15` and press Tab — then, **within two
   seconds and without closing the sheet**, switch to the layout editor and
   change **AC**'s **Label** to `Armor class`. The notice must read *Renamed
   "AC" to "Armor class" in 1 character note* (plus Collisions' own clause), the
   note's heading must be `## Armor class` **with `value: 15` under it**, and the
   still-open sheet must show 15 in the card rather than an empty one. Before
   the fix all three failed at once: no notice, no migration, and a blank card
   whose value was still in the file. The two seconds are the whole test —
   `requestSave` is a two-second debounce, so waiting longer lets the sheet's own
   write land first and tests the ordinary path the other five already cover.

   A slower variant worth one run on a large vault: do the same but let the
   rename's scan overlap the debounce, which is what the conditional write in
   `SheetView.save` exists for. There is nothing to press differently; it is the
   same gesture on a vault with enough notes that the scan takes a second or
   two, and the check is the same — `value: 15` under `## Armor class`, not
   `## AC`.

## Commit boundaries

1. `parse: add byte-preserving rename for a fenced entry's key and a section's heading`. `renameFencedEntry` in `parse/fenced.ts`, `renameSectionLabel` in `parse/character.ts`, each pure, each tested for the not-present, collision, and identity (renaming to the same name) cases and for leaving every other byte untouched.
2. `add vault-wide migration for a component rename`. The new top-level module: candidate scan through `metadataCache`, per-file `app.vault.process` composing the two functions above, a summary of counts. Tested against `src/test/obsidian-stub.ts` with a small set of character notes covering match, no-match, collision and already-correct.
3. `wire label rename in the layout editor to the migration`. The Label field's commit captures the old value, hands the rename to `persist()`, fires the migration only after the layout write resolves, and reports through one `Notice`. The field's description is corrected.
4. `wire declared-key rename to the same migration, across every fenced component`. Card's own `key` field, the shared entries editor's primary field (covering Card set, Track, Roster's `stats` and, through `entryFlag`, Passport's `fields`), Passport's `nameKey`, and Record set's per-record field key — each captures old/new and reaches the same migration and the same reporting path. Roster's `columns` and `rows` fields are untouched by this commit, on purpose: they render through `renderColumnsEditor` and `renderRowsEditor`, not the shared entries editor, so leaving them alone is the default rather than something this commit has to opt out of.
5. `docs: add this feature note and vault fixtures demonstrating the migration`. A small fixture in the throwaway test vault — a layout with two or three characters — exercising a label rename and a key rename by hand, per this repository's convention that a change the harness cannot render is demonstrated in the vault instead.

## Deliberately not doing

- **id rename, layout rename, modifier definition rename.** See Model question. None of the three gets any new code in this feature.
- **No confirmation dialog, no preview, no dry run.** Nothing here risks an overwrite (the condition MetaEdit's own dialog is gated on), so there is nothing for a confirmation to protect against that the collision rule does not already refuse.
- **No retry command for a skipped or unreached note.** Fixed the same way an unmigrated note is fixed today: by hand, in the note — and **the `Notice` is what says so**, not the Label field's description: `1 left as \"AC\" because it already has a section called \"Armor class\", so move it by hand.` The route is in the sentence because UI.md §10 asks error text to name the fix, and this is the cheap place for it: conditional copy that fires only on a rename that actually skipped something, where a standing sentence in the description would have charged every author of every layout for a case most never hit. The Label description having carried that instruction before this feature is why it read as the natural home; a design review measured what putting it back would cost the one field every component in the catalog shows, and it is not worth it.
- **The `Notice` names a count and not the notes.** It says "2 left as \"AC\"", never which two. A `Notice` is transient and neither selectable nor clickable, so a list of names in it is not a route to the files — while the count plus the old name is one, because the old name is exactly what a vault search finds those notes by, at twelve of them as readily as at two. This is a stopping point rather than an omission, and the thing that would change it is a surface a name could be *acted* on from, which this feature does not add.
- **No per-note migration version stamp and no lazy, on-open migration.** This file model carries a character's own values and nothing else; a stamp would be new bookkeeping invented for this feature alone.
- **Undoing a rename in the layout editor's own undo stack does not reverse a completed character-note migration.** It restores the layout's old spelling, which leaves already-migrated notes reading correctly under the new one and the layout looking for the old one again — the same "unmapped, not lost" state SPEC §10 already tolerates, healed by redoing the rename forward (old→new, since that is now what the layout needs) rather than by an inverse transaction this feature does not build.
- **Table is untouched.** `storage: 'markdown'`, no `readFenced`/`writeFenced` — its columns keep today's behaviour with no migration offered, because the fence primitive this feature builds has nothing there to operate on.
- **Pool is untouched**, despite importing `readFenced`/`writeFenced` like every in-scope component. Its three keys (`current`/`temp`/`max`) are fixed constants no config field ever exposes, so there is no author-declared name for a rename gesture to target — the same missing-target reason that excludes an id, not a storage-format reason.
- **Two of Roster's own three `key`-shaped fields are untouched, and for two different reasons than Table's or Pool's.** `columns[].key` is Table's own column-key problem restated inside a different component — a markdown-table header via `parse/table.ts`, not a fence entry — so it is excluded on Table's own reasoning, not a new one. `rows[].key` is excluded on a third reasoning again: it is a formula-facing publish name (`<component id>.<key>`), the same shape as a component's own `id`, and no character note is ever keyed by it — renaming it is the id-rename problem (Model question, surface 3), landing inside a component that also happens to have a real, in-scope, fence-addressed key one field over (`stats[].key`). The two are wired through entirely different editor functions (`renderColumnsEditor`, `renderRowsEditor` versus the shared `renderEntriesEditor`), so nothing about building this feature's one hook risks reaching either by accident.
- **No surfacing of a character note pointing at a copy of this layout.** Out of scope invisibly, the same way every other feature in this plugin treats a copy as a different layout by name.
